The turnover branch is a first-class parent now

Worktree branch wtgui/make-the-turnover-branch-a-first-class-df6ca4, cut from main. What was wrong, what changed, and what was actually run.

The defect in one sentence. A tree's parent was whichever branch the project's checkout happened to be standing on, so for a repo parked on master every tree read master as its parent, and branchLandingLine told every worker to push a new remote branch and open a pull request.

The fix in one sentence. A project can now name its turnover branch; a cut for that project starts from it, records it as the parent, and the worker is told to merge back into it locally and not push.

1. The defect, with the evidence it was found from

lib/branch-policy.js said, before this branch:

//   parent is main / master            -> do NOT merge into it. Push the branch and open a pull request: the parent
//                                         is a landing branch and the house rule is one reviewable PR per branch.

and the cut had no way to say otherwise. assistants/assistant-3/notes.md at 2026-11-10T22:02Z recorded the missing half: "the panel has no way for a SPAWN to name its base branch". With the checkout on master, startRefOf answered master, the parent record said master, and the paragraph told the worker to push. That is how the pictureviewer and RUNG-4 branches reached git.sefl.com as children of a turnover branch that had never landed.

Two separate facts were conflated: where the checkout stands (a property of one working directory) and where this project's work rolls up (a property of the project, which the reader knows and the panel did not ask). This branch separates them.

2. The setting: a project names its turnover branch

The branch lives on the project's own config.json row, beside mainBranch and remoteBranchPolicy:

{
  "name": "optym-integration-multi",
  "pushNewBranches": "always-ask",
  "turnoverBranch": "feature/optym-turnover"
}

Reading is forgiving, writing is strict. lib/project-turnover.js normalises whatever a hand-edited file holds: refs/heads/feature/x reads as feature/x, padding collapses, a number or an object reads as "no branch". A save is refused with the reason when the name is one git cannot carry, is HEAD, or is a landing branch (main, master, trunk, develop). Clearing ("") is a real save and removes the key. A row the writer invents for a discovered project carries the name and the branch and no path: discovery owns where the repository is.

The reader names it in the project settings. The project head line now draws a fourth chip beside host, rules and board: turnover: none or turnover: feature/x, green when a branch is named. Pressing it opens one field with the branch, a save and a close, and a sentence saying what a tree cut from it will be told. The save goes to POST /api/project-turnover, which writes the file, the in-memory config, the registry record and the store's project record, so the very next SPAWN cuts from the new branch without a restart.

3. The cut: a tree for that project starts from the turnover branch

Jobs.turnoverStartRefOf resolves the configured name against git before the cut, in this order:

The branch existsWhat the cut doesWhat is recorded
locallygit worktree add -b <run branch> <tree> <turnover>parent = the turnover branch, parentSource: "cut"
only on a remotecreates the local branch at that commit (git branch --no-track, a local write, never a push), then cuts from itsame, and the paragraph says it is remote-backed
nowherefalls back to the checkout's own ref, and logs one line saying the configured name does not exist herethe checkout's branch, exactly as before

A name in a config file is not evidence that a branch exists, so the middle row is the only one that creates anything, and it creates it locally. The fan-out base (from), a round's frozen commit and a stage's from still win over the setting: those cuts are pinned by their caller, and a lane that started anywhere else would not share the commit its siblings were cut from.

The parent record reads it. makeWorktree used to take the chart parent from the resolved ref, which was the checkout's branch. A turnover start now carries its own name, so all three records agree: the job's parent/parentSha, the durable parent book, and the tree's own logs/branch-parents.json entry.

4. The policy: one new case, and the permission for a new remote branch is now conditional

ParentWhat the worker is told
the project's turnover branch, remote-backed or local onlymerge into it LOCALLY, do not push, do not open a pull request; report the merge commit
a landing branch, and the project has a real turnover branchdo not merge into main, do not push a new remote branch; roll up into the turnover branch locally
a landing branch, no turnover branch configured or none on originpush and open a pull request, and the paragraph says this is permitted only because there is no turnover branch
any other branchmerge into it locally, do not push (unchanged)

The two clauses the brief asked for are literal in the paragraph: this project's turnover branch for the parent case, and A new remote branch is permitted only when a project has no turnover branch configured and there is none on origin. The paragraph is handed over only when the tree's parent really is a turnover branch git can point at, so a stale config name cannot send a worker to merge into a branch nobody has.

The assertions that carry the requirement

  • The cut, on a master checkout. A repo with master checked out and a dmr-7-turnover branch one commit ahead: the run body says cut from `dmr-7-turnover`, says this project's turnover branch (local only), says merging ... into `dmr-7-turnover` LOCALLY and do not push, and contains no push it and open a pull request and no gh pr create. The tree's HEAD equals the turnover tip, and the checkout is still on master.
  • The parent record. The in-memory card, jobs.parents.get(project, branch) and logs/branch-parents.json all hold parent: "dmr-7-turnover", parentSource: "cut", and the turnover tip as parentSha.
  • Remote-backed or not. The paragraph is the same instruction with turnoverOnRemote: true or without it; the only difference is the parenthetical that names which it is.
  • The conditional permission. A main parent with no turnover branch still says push and carries the "only because" clause; a main parent with one says so do not push a new remote branch and contains no push command.
  • The setting, end to end. A real panel: a save lands in config.json, the row keeps its path, a discovered project gains a row with no path, a clear removes the key, a landing branch is refused with the file untouched, and the value rides /api/state so the chip draws it.
  • The lookup. Registry first, config row second, empty otherwise; mutating the registry record changes what the same lookup answers, which is the no-restart guarantee.
