Waves of work: the model, the records, the gates, and the first slice

agent-worktree-gui 1.148.0 at 1aad736b (2026-11-21), on wtgui/write-the-design-document-for-waves-of-fb3b0f. A design note written BEFORE any wave code exists. Every claim below names the file and symbol it was read from; every count in this header was measured with grep on this commit, not recalled.

Three containers already exist, and a wave is the fourth. An initiative says what the work is for and which trees are behind it. A task row says who is carrying one piece of it, on which tree, in which state. A pipeline says how a tree may move (the rung ladder) or which stages one row walks (the studio bundle). None of them is an ordered, gated group of tasks: the initiative has no order, a task joins it only through its worktree, and the 14 exit checks are a validated vocabulary that nothing evaluates yet. The word wave appears exactly once in lib/, routes/ and server.js, in a comment about memo expiry (lib/remote-backoff.js:8). waveId, waves and waves.json appear zero times in code, tools and tests. The proposal is deliberately small: one store beside initiatives.json, one field on a task, one state derived on read, and gates named with vocabulary the panel already ships.

5things missing: order, membership, gate, current, record

1. The layers as they exist

Four records are in force today. The two meanings of "pipeline" are kept apart on purpose, because the code already keeps them apart on two different keys: a job's pipeline is the tree's rung (lib/jobs.js:1607-1610), while a task's pipelineRun is a bundle assignment (lib/task-pipeline.js:30). A wave sits above both and must not collapse them.

2. The gap, stated plainly

Five things the reader asked for do not exist. Each is named with the place it would have to live and what stands there instead.

No ordered containers

An initiative has no position field. Its trees are grouped by project name and sorted alphabetically (routes/initiatives.js:120-128), and the group list is sorted by name too. The only order the code stores is a task's order, which is the reader's drag tiebreak INSIDE a state bucket (lib/assistant/queue.js:24-27), and a bundle stage's 1-based position (lib/pipeline-bundle.js:319). Neither belongs to an initiative, and neither can order a group of tasks.

No membership for a task

Membership in an initiative is a TREE record keyed by path (lib/initiatives.js:7-12). The view links a task to an initiative only by t.worktree && treeKeys.has(normTreePath(t.worktree)) (routes/initiatives.js:132), and its own comment says nothing there reads a branch name, because a branch that looks like a tree is not a link (routes/initiatives.js:43-46). Consequences: a task with no worktree cannot be a member of anything; two tasks on one tree are one link; and a group cannot select a subset of the work on a tree.

No gate

The initiative history vocabulary is closed at four actions (lib/initiatives.js:75). The 14 exit checks are validated at load and save, but nothing evaluates one: the source says so (lib/pipelines.js:40-41). The only gate object in the system is a bundle gate anchored after a stage by after and to an artifact it decides on (lib/pipeline-bundle.js:331-369), which is a boundary INSIDE one row's pipeline, not between groups of rows.

No notion of which wave is current

The initiative document returns projects, tree rows, assistants, counts and history (routes/initiatives.js:166-183). Every ordering in it is a display sort, not an authored one. There is no field anywhere that says "this is the part being worked now"; the closest derived notion is a running row (taskRowOf's state, routes/initiatives.js:66), which describes one task, not a group.

No waves field, anywhere

Measured on this commit: grep -rnE "waveId|\bwaves\b|wavesFile|waves\.json" lib routes public server.js tools test --include=*.js --include=*.mjs returns 0. A plain grep -rni wave lib routes server.js returns 1, and it is a comment about a wave of memos (lib/remote-backoff.js:8). The interior word only survives in the console's "wave button", which is a per-session display switch (public/render-jobs.js:427, public/turns.js:474). The docs use "waves 0-9" for a batch of parallel route moves (docs/plan/split-for-concurrency.md:24, :42-43; docs/reviews/split-server.md:746-761), which is a different idea and is called out in section 8.

3. The proposed record

One record, one field, one derived state. The record lives in its own state file, keyed by initiative id, so an initiative write never rewrites a wave and a wave write never rewrites the initiative store. The shape is exactly the one the brief asked for:

// state/waves.json, beside state/initiatives.json
{
  "version": 1,
  "byInitiative": {
    "init_m3k2p1_a7f2c9": [
      {
        "id": "wave_01",
        "initiativeId": "init_m3k2p1_a7f2c9",
        "position": 1,
        "title": "The read path",
        "entryGate": { "check": "clean" },
        "exitGate": { "check": "pr-merged" },
        "template": "poc-to-uat",
        "auto": false
      }
    ]
  }
}

The file, and why it is a second file

lib/paths.js:259 gives the initiative store its path with config.initiativesFile || file("initiatives.json"). The wave store is its sibling, config.wavesFile || file("waves.json"), stamped WAVES_VERSION = 1 the way INITIATIVES_VERSION is (lib/initiatives.js:31). It earns a second file for the same reason the initiative store is a side store at all: the board's rows are rebuilt from git on every scan and a fact written onto a row does not survive (lib/initiatives.js:7-12). A wave is authored data, and authored data lives in a document a reader can open. The write rule is copied whole: an unreadable file is refused with its sentence and its path, every write answers 409, and the bytes are left alone so the reader can salvage them (lib/initiatives.js:20-28, routes/initiatives.js:237-245).

The field on a task

waveId joins the task record in pickTask (lib/assistant/queue.js:676-745) and is carried VERBATIM, the way pipelineRun already is: this module is not the wave store's reader, and a record naming a wave the store no longer holds must reach the window as unresolved rather than be normalised to null (lib/assistant/queue.js:739-745; the contract is stated at lib/task-pipeline.js:19-24). Absent means no wave. It does not mean the first wave, and it does not get a default: the driver's own first rule is that absence and breakage are different answers.

The state, derived on every read

A wave has no state field. Its state is a fold over its members plus one live read of its gates, computed on every read, exactly as an initiative's projects are grouped from trees on every read (routes/initiatives.js:120-128) and as stale and conflict are derived from the job store and never written (lib/assistant/queue.js:16-19).

waveState(wave, members, read):
  if members is empty                  -> "empty"
  exit = read(wave.exitGate)
  if exit.met                          -> "done"
  if any member.state == "parked"      -> "blocked"
  if any member.state == "running"     -> "running"
  entry = read(wave.entryGate)
  if entry.met                         -> "ready"
  if entry.cannotTell                  -> "unknown"
                                       -> "unentered"
Derived stateWhat makes it trueWhat it is not
emptyNo task names this wave id.Not "ready": a wave with no members has not opened, it has nothing to open.
unenteredThe entry gate read says not met.Not a failure. Several waves are unentered at once by design; only one is current.
unknownThe entry gate could not be read: no PR, no host answer, a check with no evaluator.Not "unentered". The two need different words, because one is a fact about the work and one is a fact about the reader.
readyThe entry gate is met and no member has started.Not a stored flag, and not a lock: a second wave can also be ready.
runningAt least one member is running.Not "the wave's run": members have their own threads and runs (lib/assistant/queue.js:139-166).
blockedAt least one member is parked and none is running.Not a wave-level park. The hold is the member's (TASK_HOLD_KINDS, :68).
doneThe exit gate read says met.Not "every member is done": a wave can exit on a merged PR while one member is still queued for a follow-up.

Which wave is current is also derived, not stored: the lowest-position wave whose state is running, else the lowest-position ready wave, else the lowest-position unentered one. That is a display rule with a stated order, not a field anybody can forget to update. It can be wrong in a way a reader can see and argue with, which is better than a stored current: true that can be wrong invisibly.

4. The rules that make it stable

Five rules. Each one forbids a shape that would work for a week and then disagree with itself, and each one copies a rule the code already keeps somewhere.

1. A wave never owns a tree. A task does.

Membership in a wave is membership of TASKS; the task already carries worktree and project (lib/assistant/queue.js:723-725), and the initiative already owns tree membership keyed by path (lib/initiatives.js:7-12). A wave-level tree list would be a third map of the same fact, and the first scan that moves a tree would leave it stale. It also breaks the per-stage case for free: a bundle pipeline with per-stage isolation cuts one tree per stage (lib/pipeline-bundle.js:416-424), so "one task, one tree" is already false inside a fan-out. Counting members as tasks is the only count that stays right.

Forbids: wave.trees[], a wave branch, a wave owner, a wave-level worktree. Precedent: the initiative store exists precisely because a fact on a row does not survive a scan.

2. A wave never holds a second copy of a task's state.

The task's state is on the queue row (TASK_STATES, lib/assistant/queue.js:52), and the fields around it are either the row's own or derived at read time (:16-19). The driver's second rule makes the same point about a stage: a stage is settled by its RUN, not by a sentence (lib/task-pipeline-drive.js:16-23). A wave.state or wave.doneAt would be a snapshot of the queue, and the next read would believe it after the row moved.

Forbids: state, done, doneAt, percent, blockedBy on the wave record. Precedent: stale and conflict are derived and never written; a running task whose thread stopped stays "running" on disk until a reader decides.

3. Membership is explicit, so one wave can span projects.

A task is in a wave because it names the wave id, not because its path starts with a prefix, its branch carries a tag, or its lane matches. An initiative may already span several projects (lib/initiatives.js:14-17), and the task row already carries a project name next to its tree (lib/assistant/queue.js:723-725), so an explicit membership costs nothing and keeps the cross-project case honest. It also keeps a task's row able to appear under two initiatives without appearing in two waves: each initiative's document is built from its own tree keys, and a queue row is one entry in each, never two within one (routes/initiatives.js:155-157). The same rule for waves is one wave per task, enforced at write.

Forbids: path prefixes, branch-name conventions, lane as membership. Precedent: "Nothing here reads a branch name: a task with no worktree is not on any initiative's trees, and a branch that LOOKS like a tree is not a link" (routes/initiatives.js:43-46).

4. Gates reuse the closed exit-check and bundle-gate vocabulary. No third dialect.

An entry or exit gate is {check, ...params} where check is one of the 14 names the panel already validates (lib/pipelines.js:43-61) and the parameters are the ones EXIT_PARAM_SPEC already describes (:64-79). The bundle's gate adds only two ideas a wave borrows: a gate names the check that closes it (verifiedBy, lib/pipeline-bundle.js:364; read by reviewGateFor, lib/pipelines.js:721-737), and a gate may map an outcome to an edge (routes, lib/pipeline-bundle.js:179-190) - a wave does not need the second one, because a wave boundary has one exit, not two edges. What a wave must NOT invent is a sentence like blockedBy: "waiting on review": a status word cannot be read back, and the whole point of the vocabulary is that every check names a fact somebody can go and look at.

Forbids: waveGate, doneWhen, free-text gate prose, a new set of check names. Precedent: a check outside the list is refused at load and save time, not rendered empty at run time.

5. A wave opens only on a live read-back, never on a status word.

The read that answers a gate must be the same kind of read the panel already trusts: the PR's state from the row's verdict (settleTasks reads row.verdict and requires MERGED before closing a row, lib/assistant/queue.js:1585-1591), the reviewer's three checks through readReviewExit, which answers cannotTell rather than guessing when the host answer is missing (lib/pipelines.js:783-800), and the driver's refusal to advance on a PR that reads DECLINED (lib/task-pipeline-drive.js:77-79). "Cannot tell" is a first-class answer, and it blocks the gate. A stored status: "done" on a wave is exactly the word this rule removes: it is written once and read after the PR was reverted.

Forbids: a wave status word, a completed boolean, a gate that passes because a member said so. Precedent: fail-closed is already the panel's habit; an unevaluable exit does not exit.

What a wave borrows

  • A 1-based position and an array order. "Wave 2 of 5" is what a reader says; an index of 1 is what they have to convert (lib/pipeline-bundle.js:449-452).
  • A template as an exact id. pipelineById refuses a near-match on purpose: a pipeline id is a config key and a record's value, and a typo the panel hides is a row on the wrong pipeline (lib/pipeline-bundle.js:537-543).
  • Gates named by the check that closes them. verifiedBy is the precedent: a gate carries the name of a fact, not a sentence about one (lib/pipeline-bundle.js:364; lib/pipelines.js:721-737).

What a wave must not become

  • A pipeline. A wave with stages would be one bundle pipeline that N rows must share, and the bundle has no membership concept at all. The driver would then need to know which row is at which stage of a shared graph, which is the wave record again, plus a graph nobody authored.
  • A second writer. The driver's eighth rule is that it writes nothing; the queue file, the journal and the repaint belong to sweepQueues, which hands the returned rows to ONE writeQueueFile (lib/task-pipeline-drive.js:74-76). A wave must not write task state either: it reads rows, and a person or the driver moves them.
  • A rung. The ladder only climbs and refuses a downgrade with a sentence (lib/pipelines.js:521-538). A wave that was a rung would inherit that refusal and would make "wave 2" a thing a tree cannot leave.

8. Drift, and what is not claimed

The drift note: "wave" already means a batch of route moves

Three documents in this repo use the word for something else: docs/plan/split-for-concurrency.md stages the server split in "waves 0-9" (lines 24, 42-43, 403, 742), and the two reviews it descends from do the same (docs/reviews/split-server.md:746-761, docs/reviews/split-for-concurrency.md:160-179). Those waves are batches of parallel file moves, not records; they have no id, no gate and no store. Recommendation: keep wave as the record's name because that is the word the reader used, do not rewrite the historical plan, and in new prose call the plan's batches "route batches" or "stages". If the collision is judged worse than the rename, the record can be renamed before the first line of code at no cost - which is exactly why this note is being written first.

Drift note: the gate vocabulary is validated, not evaluated

EXIT_CHECKS is described in the source as "the whole vocabulary", with the sentence that nothing there evaluates one yet and the evaluator is a later task (lib/pipelines.js:40-41). Only the three reviewer checks are actually read, through REVIEW_WAIT_CHECKS and readReviewExit (:586, :783-800). So a first slice that gates on pr-merged is readable today from the row's verdict (lib/assistant/queue.js:1587), while a gate on file-exists or command is not, and must report unknown rather than pass. That is the honest reading of "reuse the vocabulary": reuse the names and the parameters, and do not claim an evaluator that does not exist.

Drift note: the numbers are pinned to a commit

This page was written against 1aad736b, where package.json reads 1.148.0. The branch carries the next number; the changelog is rendered at landing. If main moves before this lands, the line numbers in the appendix are the only thing that drifts: every claim also names a symbol, so the greps still find it. No count in this page was copied from an older report.

What is not claimed

  • No wave code exists. This is a design note; section 6 is a plan, not a description of a landed slice.
  • No gate is evaluated. The design says what a gate would be and which checks are readable today; nothing here runs a check.
  • No panel screenshot is offered as evidence of a feature. The only capture is this page's own first screen, used to prove the page opens with no network (below).
  • No migration is proposed. A task with no waveId is in no wave. There is no backfill and no default wave, because a default would invent a membership nobody authored.
  • No throughput claim. The design is about what can be READ and argued with. Whether waves make work faster is a question for measurements after the slice.

9. Recommendations and open questions

Everything in this section is a recommendation, not a claim about the code. The five recommendations are ordered by what they unblock.

Recommendations

  1. Build the read-only store and fold first. It proves the record, explicit membership and derived state without writing a status field, and it can be reviewed against section 3 line by line.
  2. Restrict slice-one gates to the checks the panel can read today. On the board row: clean from the dirty count (lib/scan.js:97), commits from ahead, pr-open and pr-merged from the PR and verdict (lib/assistant/queue.js:1587-1591). Through the review read: pr-approved, pr-comments, reviewers-exact (lib/pipelines.js:586). Everything else renders unknown.
  3. Keep auto false, and subordinate to the Assistant's spawn setting. Unattended starts are the reader's switch, passed in as an argument; a wave may not start what the assistant was told to ask about (lib/task-pipeline-drive.js:70-72).
  4. Do not reorder in slice one. Create appends at the end. Reordering is a write with a history and a question about a running wave, and it belongs to a later slice with its own tests.
  5. Bound the fold. Waves per initiative (50 is generous) and members read (200, the queue's own cap, lib/assistant/queue.js:54) so a wave read cannot become a second scan of every queue.

Open questions

  1. What happens to a member that is cancelled or moved out of the initiative's trees? The design keeps the row as a member with its own state and lets the fold show it, rather than deleting history. That is a choice, not a fact; it matters most for a wave that has already exited its gate.
  2. May a wave hold a task whose worktree belongs to another initiative? "Explicit membership, so one wave can span projects" does not answer this. The proposal is no: a wave is inside one initiative, and cross-initiative sharing stays the tree rule the initiative store already has.
  3. Is the exit gate re-read after it is met? Re-reading lets a wave reopen when a PR is reverted, and a wave that was "done" yesterday can read "running" today. Storing the moment it was first met loses that. The proposal is re-read, with the state word allowed to go backwards.
  4. What does a wave do when its template id disappears from the bundle? The proposal is to keep the id and read unresolved, mirroring pipelineRun (lib/task-pipeline.js:19-24), never silently null. A later bundle may bring the id back.
