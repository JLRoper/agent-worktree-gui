1. The delta saved as one patch, outside the source tree

The whole 21-path delta is one unified diff written to a scratch directory outside the repository (async-pipeline-driver-delta.patch, 2314 lines, sha256 6e9384fea3463e4ffe1e7a98ad29c990af61e3fc92ab1bf9b2b15e8e9e54b7c3). The 20 tracked files came from git diff in the source tree; the untracked test was added as a new file mode 100644 hunk with its own blob hash.

The patch no longer applies to main as one set: git apply --check against this worktree (which is level with origin/main) checks all 21 paths and fails 6 of them - lib/assistant.js, lib/task-pipeline-drive.js, test/task-pipeline-drive.test.js, test/task-pipeline-sweep.test.js, test/task-pipeline-verdict.test.js, test/task-pipeline-walk.test.js. Those are exactly the paths main rewrote in 38e7a6f8 (and the harnesses it touched with it). A clean apply is therefore not evidence of a live change: 15 paths apply because main never touched them, not because the change is still wanted.

3a. What the await buys, measured

Why an unawaited sweep is one pass behind. sweepQueues() is promise-returning by design: a pass that needs a git fact suspends instead of blocking - lib/assistant.js:1400 const result = run(); with :1397 return err.treeFactsPending.then(run);. Main's own suite pins what that means for a caller that ignores the promise: test/task-pipeline-sweep.test.js:153 const first = assistant.sweepQueues(); ... :160 assert.equal(rowOf(added.id).pipelineRun.stage, "S1", "no partial queue write while facts are pending"); - the row is still at the stage it started from while the pass is in flight, and only after :163 await Promise.all([first, second]); does :166 read "S2".

How long the gap is, on this host. One real tree reading through main's own method, timed in an export of origin/main:

Assistant.prototype.treeFactsOf(".../agent-worktree-gui")              384 ms
Assistant.prototype.treeFactsOf(".../.worktrees/salvage-...-0d4a42")     373 ms

Against what the harnesses sleep. Every one of them fires the sweep and then waits far less than one reading:

  • tools/pipeline-exec-round.mjs:239-240 const settle = async () => { for (let i = 0; i < 12; i += 1) await sleep(5); } - 60 ms, then it compares the row's thread before and after the step;
  • tools/pipeline-exec-poc-rounds.mjs:265 await sleep(70); - then reads the prompt count it expects the pass to have produced;
  • tools/verify-pipeline-assembly.mjs:171 await sleep(120); - then reads the row it expects the pass to have written;
  • tools/verify-pipeline-walk.mjs:252,262 and tools/bench-pipeline.mjs:262 - two or three bare await tick(), which is a macrotask, not a wait.

So the step boundary these tools assert on is ~300 ms earlier than the pass they just fired. The consequence is narrow but real: a step counts as "nothing moved" when the pass simply has not finished, one iteration of a bounded loop (60 or 900) is spent on every pass, and a loop that runs out of budget reports an unfinished row - which reads as a pipeline defect rather than a timeout. Awaiting the returned promise makes "one sweep" mean "one completed pass".

What it does not fix: no shipped path. Every call site inside the panel already awaits the promise or handles it: lib/assistant.js:1685 await this.sweepQueues();, and :1904 / :4157 const result = this.sweepQueues(); with a .catch(...) on the returned promise. The seven unawaited lines are exactly these five verification harnesses, so this is determinism in the tools, not a bug a reader of the board can see. That is why "retire with no salvage" is a real option rather than a cop-out.

4. What was run, and what it answered

  • node --check on all five tools: five of five OK.
  • npm run test:changed: one test file names the diff, test/pipeline-bench.test.js. Run alone: 6 tests, 6 pass, 0 fail (26.5 s).
  • tools/verify-pipeline-assembly.mjs: 79 checks, 0 failed, exit 0 - four stage trees, four commits, one assembly, the conflict round parked.
  • tools/verify-pipeline-walk.mjs: red on this host, and red on origin/main too. Base export of origin/main: -1 / 15 checks passed, 16 FAILED, all four scenarios stalled at their first stage. With the awaits: 6 / 15, the probe-fix and author/review scenarios fully green, then the same crash the base hits - TypeError: Cannot read properties of undefined (reading 'at') at leaveLeftover (:202, task.pipelineRun.stageRuns.at(-1) on a row with no stage run yet). Two pre-existing defects of the harness itself, unrelated to the sweep: the leftover fixture assumes a stage run exists by step 3, and the seat writes a stage artifact at stage.artifact.path without fillHoles, so ledger/ping-pong/draft-r{{round}}.md is written with a literal {{round}} and the driver never finds it. Fixing them is a separate change; the awaits are not the cause, which the base run proves.
  • npm test once, at the end, before the pull request. A fresh worktree has no config.json (gitignored), which fails gateway-permissions.test.js at import with an ENOENT; the primary checkout's copy is copied in first, as the landing notes require.

5. What retirement removes

Once the salvage lands and reads MERGED, from the main checkout only:

  • the worktree directory .worktrees/async-pipeline-driver-refactor - with it, the 20 uncommitted files (+431 / -276), the untracked test/tree-facts-cache.test.js (88 lines, preserved in the patch above and in section 6), and an untracked .kilo/ directory that is local tooling, not part of the delta and not in the 21 paths;
  • the local branch wtgui/async-pipeline-driver-refactor (git branch -D). It has no PR, no remote ref to keep, and its tip b7394d4c is already an ancestor of main, so nothing unique to the branch is lost;
  • its registration in git worktree list, which is what the panel's board reads.

Nothing on origin is deleted and no other worktree is touched. The source tree stays in place until the pull request reads MERGED and /api/jobs shows no live run at that path.
