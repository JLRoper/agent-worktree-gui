1. What the brief said, and what the panel showed

The brief named the start (140px), the shape (a non-scrolling slack turn) and a cause to prove: the drag freezes the top edge by writing the transcript's scroll offset, and a body with no scroll room cannot honour that write. The first half of that is exactly what the gesture does - it freezes the top edge at the press and writes the height from it (public/app.js:10821 reads the room once, public/app.js:10915 holds every move to it). The second half is real but not the writer of the failing numbers: the transcript at the 140px start really has no scroll room, and every scroll write the drag made was scrollTop = 0 from 0 - and the top edge did not move for the whole drag.

What moved was the handle. The grip is bottom: 0; right: 0 inside .out-box, and in the slack turn that wrapper is display: flex; flex-direction: column; flex: 1 1 auto (public/style.css:7061), so it stretches to the pane's spare room while the console inside it, given an explicit height, is flex: 0 0 auto (public/style.css:7070). The grip therefore sits at the bottom of a box 145.41px taller than the console it belongs to. The hand presses that grip, the console grows, and the handle does not move: the console grows inside the wrapper's blank space until the blank is used up.

3. The scroll room, measured

The transcript at the 140px start is slack: its content is exactly the pane's height, so scrollHeight - clientHeight is 0 and a scrollTop write cannot move it. The gate instruments every write to the transcript's offset and the pre-fix trace shows what the gesture's own paths asked for during the drag: eight writes, every one of them 0 to 0, from setScroll at public/board/console.js:3687 through public/app.js:10929. A body with no room cannot honour a write to a non-zero offset either, but it was never asked to: the frozen top edge was 566.78 at the press and 566.78 at every step.

So the brief's mechanism is half of the story. The room matters at the release, not during the drag: once the wrapper is the console's own box the transcript gains room as the console grows (32px at 820 in the third row above), and a pin or a rebuild that lands at the release can spend that room by scrolling the transcript to its foot, taking the top edge - and the corner - with it. Two separate bands let it happen, and both are closed here:

  • noteCardBodyScroll(body) used an 8px band to call a transcript "still following" (public/board/console.js:3769). A drag's own last few px are inside that band, so the next pin scrolled them away. The release now records the truth with noteCardBodyScroll(d.body, 0) (public/app.js:11017), and the chat pane's own placement does the same (public/assistant.js:2408).
  • renderConversation measured only the DOM, with a 32px band (public/render-jobs.js:1165 before this change). A rebuild at the release read a drag's gap as "on the foot" and scrolled it away. The body's own record now wins when it says not following, and the fresh node is noted with the 0 band (public/render-jobs.js:1209).

4. The fix: the handle moves with the console

One rule, at public/style.css:7082:

.as-subpane[data-subpane="chat"] > .job > .job-body > .turn.is-slack > .out-wrap > .out-box:has(> .job-out[style*="--out-h"]) {
  flex: 0 0 auto;
}

The rule above it already draws a console with an explicit height at that height (public/style.css:7070); this one does the same for the box the grip is drawn in, and only when the console inside it has a height. The wrapper is then the console's own box: boxH === console height, corner gap 0, and the drag's growth moves the grip the hand is on. A console nobody has resized keeps the flex and the pane's spare room still lands in it.

The rest of the patch is the release side. The assistant's head is a row above the console (a status chip in the as-bar strip, a new session tab), so a paint that lands under the hand moves the frozen top edge: the head's paint is now deferred to the release (public/assistant.js:166 to 176, asked from syncSessionTabs at public/assistant.js:184 and renderAssistant at public/assistant.js:2172), and outGripDefer keeps every distinct deferred paint rather than only the last (public/app.js:11022).

8. The residual, plainly

One row in 48 does not end with the corner on the hand: interrupt-poll@1600/140, final 24.3px, tagged pane reflow 24.29px in the pass line. The deferred head paint runs at the release, the status chip strip gains a row (as-bar 36.94px to 61.23px), the card and the console move down by the same 24.29px, and the grip goes with them. The transcript's own offset did not move - the body has no room, so no scroll could undo the drag - and the gate tells the two apart by that evidence and by the card's top moving with the box's (tools/verify-console-corner-drag.mjs:900 to 915).

That is a paint that has to happen, moved from under the hand to the release; it is not the drag's travel being given back. It is printed in the pass line rather than swallowed, and it is named here as a separate, smaller defect: a head that grows above the console when a chip arrives moves the corner by the row's height. Fixing it means reserving the chip row's height for the length of the gesture, which is a layout change to the float's head and not this row's brief.
