Why the Director's QUEUE line files itself again

Read-only research. The path from a Director reply's QUEUE line to its queue row, the one key that is supposed to stop a second filing, and why five texts were filed eighteen extra times. No product code was changed.

Answer: a Director reply's QUEUE line has no idempotency key anywhere on its path. The only thing that stops the same reply filing a second row is the turn id being present in Assistant.harvested, a Set of at most 50 job ids in assistant.json (lib/assistant.js:4838). A turn that has fallen out of that set is re-harvested by the next re-read, and every QUEUE line in it is carried out again as a brand new row; addTask (lib/assistant/queue.js:541) has no duplicate check and the row carries no reference to the turn or the line.

Measured on the live store: 5 texts, 18 extra rows. #268, #269 and #270 (filed 14:00, 14:41 and 15:01) were re-filed at 16:45, 16:48, 17:11, 17:54, 18:02 and 19:05 (rows #271 to #285 and #292 to #294). #281 and #282 joined the set at 19:05 (#291 and #290). #286 and #287 still exist once each. The difference is not the text: it is whether the turn that wrote it was still inside the 50-id mark when the next re-read ran.

The key, stated exactly. The reply is stored under the turn id: the job record's id in jobs.json, mirrored into harvested. The queue row is stored under its own integer id in queue.json. There is no key shared between them. createdBy names the Director and createdAt names the moment, and that is all the row knows about where it came from.

2. Why the same text is carried again

The guard is a window over harvest events, not over turn age. A Set keeps insertion order, and slice(-50) drops whatever was inserted first, so the mark retains the last 50 turns the panel harvested - in whatever order that happened. Two consequences follow.

  1. A turn outside the mark is carried again. Any re-read of a stored turn that is no longer in the set runs its actions from scratch. The code already names this failure for SPAWN, in the comment that introduces the SPAWN debt's own guard: "which is what a boot does when it re-reads one of the assistant's old turns (the harvested mark is capped at 50 turn ids, so the oldest fall out and read as never harvested)" (lib/assistant.js:5233-5236).
  2. The window moves in both directions. A re-read that inserts forty old ids evicts the newest ids first. That is how #281 and #282 became re-carryable at 19:05 while a 15:01 turn was still protected: the mark's contents are a harvest log, not a recency stack.

4. Why those three, and not #281, #282, #286, #287

At the time the brief was written, #268, #269 and #270 were the only texts whose turns had left the mark. Their turns were written at 14:00, 14:41 and 15:01; by 16:45 enough harvests had happened to push them out, and every later re-read re-filed them. #281 (17:55), #282 (17:59), #286 (18:06) and #287 (18:28) were still inside the window.

Six hours later the boundary had moved the other way. At 19:05 #281 and #282 had left the mark and were re-filed (#291, #290), while #286 and #287 had not. Nothing about the texts changed between 18:28 and 19:05 - only their position in a 50-entry Set.

Limit of the reconstruction. The mark's exact membership at 18:28 cannot be recovered: it is a Set in assistant.json that every harvest overwrites, and the journal keeps 300 entries. What the store does prove is the guard itself (50 ids, :4838), its own comment naming the re-read (:5217-5220), the per-kind asymmetry (SPAWN refused, QUEUE filed, in the same pass), and the order of the 19:05 re-read. The 18:28 boundary is inferred from those, not replayed.

5. Candidate fixes

A. Key the carry, and give the row a source (recommended)

Thread the turn id and the line index through the carry and write them into the row. The index already exists in the audit ledger (scanCommands gives every prefix line an index, lib/assistant/audit.js:71-81); the queue branch would pass { key: `${who}|${job.id}|${index}`, source: { assistant: who, turn: job.id, index } } to queueMutate("add"), and addTask would return the existing row instead of pushing a second when the key is already present. The same key applies to MESSAGE, which today can start a turn twice.

  • Exact: survives a boot, a store restored from an older copy, a job re-adopted under a new id, and an enforce replay, because the decision does not depend on in-memory state.
  • Turn-based, not text-based: a reader editing the row's title cannot defeat it.
  • Cost: a new optional field on the row (pickTask default null, plus the "a missing key reads as absent, never as a match" rule any persisted shape needs), the turn id and index in queueMutate's payload (a second argument, not a route field the page could forge), and tests at each door.
  • Rows filed before the fix carry no key; a first re-read after the upgrade would file one more duplicate each unless the ledger is also seeded from the existing rows' titles once.

B. Make the mark age-bounded and per assistant

Replace the 50-entry FIFO with a persisted map of turnId -> harvestedAt, pruned by age (for example, never evict a turn younger than the job store's own 80-job retention) and kept per assistant, so a busy #2 cannot evict the Director's turns.

  • Cheapest: one function and one store shape, no queue schema change, and it fixes every kind at once - NOTEs stop duplicating, CHARTERs stop repeating, MESSAGEs stop starting turns.
  • Treats the trigger, not the duplicate: a store restored from a copy, a job re-adopted under a new id, or commandAudit: enforce replaying an unaccounted line still files a second row.
  • The state grows with turn count (bounded by the age rule), and the correctness argument stays "this process remembers", which is what failed here.

C. Refuse a duplicate at file time

In addTask, return the existing row when the same by already has a row with the same title and that row is not done.

  • No schema change, one place, and it also catches the two identical QUEUE lines in one reply (measured: the 18:27 reply repeats its line twice).
  • Heuristic: a legitimate later re-file of the same sentence is swallowed; titles clip at 200 characters, so two long texts that differ past the clip collide; and a duplicate that should never have been read is hidden rather than prevented, because the journal still records the carry.
  • Reasonable as a one-line stopgap while A is built; not the shape to keep.

Recommendation: A now, B as the follow-up. A is the only one of the three that makes the decision from what is stored rather than from what this process remembers, and it is also the fix MESSAGE needs. B is worth taking in the same landing if the reader wants the duplicate NOTEs and re-sent messages to stop as well, because A alone leaves the other kinds re-applying on a re-read even when the queue row is protected.

6. What was not done

  • No product code changed. lib/assistant.js and public/assistant.js were not edited; #286 is live in them.
  • #287 stays parked until the reader picks a fix, as asked.
  • The live store was read only. Both reproductions ran against a temp directory and a copy; nothing under ~/.wag was written.
