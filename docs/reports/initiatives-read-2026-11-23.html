agent-worktree-gui - read queue row 267

The Initiatives tab's two reads: where the 64 seconds and the 26 went, and the seam that was cut

GET /api/initiatives answered in 63.4 s on the live panel and GET /api/waves in 26.1 s, so the pane gave up at its 12 s client deadline and drew "the panel server did not answer within 12s". The store was never the problem: 10 initiatives, 12 waves, 601 queue rows. The cost was one seam - the wave gate's live evidence read - built for 19 members when one gate on one wave needed two of them, and reading three halves of every member's evidence when that gate reads one. Scoped to the gates that read it, a cold /api/initiatives now answers in 0.536 s and a cold /api/waves in 0.014 s, on the same state, with the payload the tab draws unchanged.

1 What the reader saw, and what the panel's own log says

The pane's sentence is the client's, not the server's: public/core/transport.js:82 turns an aborted request into "the panel server did not answer within Ns". The server's own log has the numbers behind it, in the same minutes, on the live panel at 1.162.1 - not on a fixture: 

17:35:04 warn slow request: GET /api/initiatives took 63374ms
17:35:30 warn slow request: GET /api/waves took 26059ms
17:37:15 warn slow request: GET /api/initiatives took 34709ms
18:04:03 warn slow request: GET /api/initiatives took 49498ms

18:32:37 warn slow request: GET /api/state took 5960ms

The stalls matter: this panel's event loop is shared with four assistants' turns, the fleet scanner and the snapshot builder, so a read that spends its time waiting on git children and a host's API pays several times what the same read pays on a quiet copy. That is why the numbers below are quoted as a pair on one copy of the state, and the live seconds are quoted only as what the reader saw.

The other suspects, each measured and each ruled out

The queueView fold (read the queue file, decorate every row against the board): 9.1 ms once for the evidence set and 11.7 ms again inside the fold - 21 ms of a 6354 ms read. It is called twice per assistant because the route and the fold each read what they need; at 0.3% of the total it is not worth a shared-view refactor here, and the comment at routes/initiatives.js:95 already records that the route may hand the same objects in.

The waveLane template parse: the bundle is 175 KB and waveTemplateLookup re-parses it only when the file's mtime or size changes (routes/waves.js:66-85). No wave in this state names a template, so the seam measured 0 ms. A wave that names one pays a stat per read and a parse on a changed stamp; that is already a deliberate cache and it was left alone.

The board-row decoration: rowFor walks store.rowsFor(project) per tree and per member. Over ten initiatives and 404 rows the whole tree fold is 8.2 ms. The 185-project board is the snapshot builder's cost (the same read measures GET /api/state at 250-450 ms), not this document's.

The lane fold and the gates: wave.state 1.0 ms, wave.lanes 1.3 ms, fold.lanes 12.9 ms for all ten initiatives. The gates themselves are cheap because readWaveGate only consults evidence for four checks, and for twelve waves it was called 24 times.

4 The cause, in the code

Both routes built the evidence map for every task that names a wave, before they knew whether any wave in the answer has a gate - and readMemberEvidence then read all three halves for every one of them: 

routes/initiatives.js:309   const map = await waveEvidence({ tasks, rowFor, paths });
routes/initiatives.js:320   const tasks = waveTasks();                     // every task in every assistant's queue
routes/waves.js:155         const tasks = queueRows(assistant);            // all 19, for ONE lane
routes/waves.js:165         const map = await waveEvidence({ tasks, rowFor, paths });
lib/wave-evidence.js:398    const read = await readLanding({ git, cwd, sha, mainRef, timeout });
lib/wave-evidence.js:403    for (const rel of artefactPaths(paths)) files[rel] = await readMemberPath(...);

Line numbers are the base tree (0b570710). Two facts follow from it, and both are visible in the tables above:

  1. The member set was every wave member in the panel, not the members of the lanes being answered. GET /api/waves for one initiative paid for all nineteen; GET /api/initiatives paid for all nineteen once. That is why the two endpoints took 64 s and 26 s for what looks like different amounts of work: they were doing the same work, and the difference between the numbers is what else the box was doing.
  2. Each member paid for all three halves of the evidence, whatever its wave's gate reads. The one gate in the state is file-exists: it reads evidence.files[path] and nothing else. The landing read (six git spawns) and the pull-request read (a host list) were made for members no gate can ask about, and for a gate that cannot read them.

5 The cut

Five changes, each one removing work no gate in the answer can consume. Nothing about the fold, the queue read or the document's shape was touched.

  1. A closed table of what each check reads - lib/waves.js:880 WAVE_EVIDENCE_READS: pr-open reads the pull request, pr-merged the pull request and the landing, main-moved the landing, file-exists the artefact. A check that is not in the table never calls evidenceFor in readWaveGate, so it owes no read - clean and commits judge the board row, and the gate's default case answers cannot tell without reading anything.
  2. A scope instead of a list of tasks - lib/waves.js:895 waveEvidenceNeeds(records) answers the checks, the wave ids whose gates read anything, and the three halves to read. routes/initiatives.js:332-339 and routes/waves.js:162-167 hand the reader only the tasks that name one of those waves. The fold still receives every task, so membership, states and the lane are unchanged.
  3. Only the halves a gate in this answer consumes - lib/wave-evidence.js:391 evidenceReadsFor(checks); :425 resolves no sha, :434 skips the landing read, and :439 skips the artefact read when no gate names a path. landing comes back null when nothing reads it, and a narrow answer is never handed to a wider gate: the checks set is part of the memo key (server.js:2054).
  4. A bounded pool instead of a sequential loop - server.js:2039 and server.js:2102-2144: four members in flight, not one at a time. The old loop paid the SUM of every member's wait; the comment it replaces said "sequential on purpose", and the reason given was to avoid a hundred git children at once. Four is that concern kept in proportion.
  5. One artefact read per (tree, clone, ref, path) per request - lib/wave-evidence.js:444 and the cache the reader creates at server.js:2100: every member of a gated wave asks about the same artefact, and the promise in the cache is what makes two members reading at once share the spawns instead of racing them.

6 After: the same endpoints, the same state

The tables in section 3 carry both columns. The short version, from one run of the harness against both trees, back to back, on one copy of the state:

The two reads now

GET /api/initiatives, cold: 4784 ms -> 536 ms (8.9x). GET /api/waves, cold: 4703 ms -> 14 ms (336x) on the gated lane, and 2154-2359 ms -> 12-24 ms on the gate-less ones. The evidence read went from 19 members, 35 git spawns and 3 host reads to 2 members, 4 git spawns and no host read.

The residual 411-826 ms is one member's artefact read with its tree gone: four git spawns on n8n-jlr, whose origin/main does not resolve, so the read tries the remote-tracking ref, falls back to the local branch, then asks for the newest commit that touched the path and its tree entry. Measured standalone on this host that read is 573 ms; inside the loaded panel it is 411 ms to 1.1 s across runs. It is the floor of a file-exists gate on a cleaned up tree, and it is paid once per thirty seconds, not once per repaint.

8 The network seam, named

Before the change the evidence read reached sefl-bitbucket three times per cold read (one prIndex per member that records a pull request number), each a REST list of the project's pull requests with its own 60 s TTL inside lib/project.js:350. The profile named the host on the read (facts.pr.hosts) because a seam that reaches the network must say which host and how often, not just how long it took. After the change that number is zero: the only wave with a gate reads an artefact, so no gate in this answer consumes a pull request.

The caches are now explicit in one place each: the evidence memo (30 s per member, keyed by the PR number, the recorded sha, the project, the tree, the artefact paths and the checks set - server.js:2031-2055), the PR list's own 60 s TTL, and the per-request artefact cache. None of them is incidental: each has a key that names what it answers for, and the checks set in the evidence key is there precisely so a narrow answer cannot be handed to a wider gate.

Limits, stated rather than smoothed over

The live panel's 64 s is not reproduced on the copy, and the report does not claim it is. The same read on the copy is 4.8 s cold. The copy is quiet; the live box is not (the same log lines that carry the 63 s read carry 2.4 s event-loop stalls and a 5.9 s GET /api/state). What transfers is the share - 99.1% of the read in one seam - and the mechanism, which is the same 19 members.

The residual cold read can exceed one second on this box. It is four git spawns for one member whose tree is gone; standalone that read is 573 ms, inside the loaded panel 0.54-1.27 s across runs. It is under a second when the box is quiet and above it when four agents are running; the table quotes the run it measured (536 ms) rather than the best one.

The pool is a judgement, not a measurement. Four members in flight is a bound chosen to keep the panel from becoming the busiest thing on the box, not a measured optimum; the read that needed it most in this state has two members.
