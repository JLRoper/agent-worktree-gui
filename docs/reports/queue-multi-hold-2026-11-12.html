agent-worktree-gui - the Queue reply block - one PR

The closed card belongs to the press, not to the held reply

205d7098 shut the duplicate-press hole by closing the whole card while a reply was held. The hole was real, but the shutdown lasted as long as the hold: the button was drawn off and the box was read-only with "queued, waiting" where its sentence was, for the rest of the turn. This landing splits the question. The closed face now answers one thing - is a press still in flight - and ends the moment that press settles, whatever the outcome, so the box comes back empty and the next, different message can be typed and held beside the first.

Base

The branch is cut from main at c0188ebb7b0fbb83d87c68e911edf8f38803c0b4 (docs: the 152.2 s terminal call was a sleep-poll on a running Jenkins build), read with git log -1 origin/main on this branch's first command. public/app.js has moved twice today, so the base report quotes the predicate by name and by line rather than by a number carried forward.

What the base build did

A card holding one reply read queued, waiting - your reply goes out when this turn finishes in the reply box, with the Queue reply button drawn off and the note queued, waiting beside it. Typing a second, different message put nothing in the box, because the box was contenteditable="false". The capture at the top of the evidence below is that state, taken from a git archive of the base with the probe typing into the box.

The cause is one answer used for three decisions. queueWaitingOn(thread) asks "is anything held for this thread", and 205d7098 asked it in the press, in the keydown handler and in the card's render. At the base:

public/app.js:3904   function queueWaitingOn(thread) {
public/app.js:3905     return replyQueued(thread).length > 0;
public/render-jobs.js:263   const queueHeld = queueWaitingOn(thread);

A hold lasts until the drain sends the entry, which is the turn and, when the thread delegated, its subagents. So the closed face lasted exactly that long, and the reader had no way to hold the second thing they had to say.

The split

Two questions, and each one has one job.

  • queuePressInFlight(thread) (public/app.js:3922) answers "is a press still in flight on this thread". It is the only thing that closes the card: return Boolean(thread && state.replyPress.get(thread));
  • queueWaitingOn(thread) (public/app.js:3928) keeps its own meaning - "does anything wait" - and now only feeds the count (1 queued, 2 queued) and the drain. Nothing closes on it.

The press claims the flight before it touches the box, paints the closed face, commits the entry, waits one task and releases the flight in a finally that repaints either way:

public/app.js:3881   if (queuePressInFlight(thread)) {
                       // already in flight: this press is the same press
                       paintQueueWait(thread);
                       return false;
                     }
                     ...
                     state.replyPress.set(thread, true);
                     paintQueueWait(thread);
                     try {
                       ... clear the box, queueReply(thread, text, files) ...
                       await pressSettled();
                       return true;
                     } finally {
                       state.replyPress.delete(thread);
                       paintQueueWait(thread);   // the box is back, empty, with the count beside it
                     }

The render draws the closed face from the flight (public/render-jobs.js:266, const queueInFlight = queuePressInFlight(thread);) and the count from the queue (public/render-jobs.js:263). The placeholder is the renderer's, written on data-ph and kept beside it on data-ph-idle, so the painter puts the box's own sentence back the moment the flight ends instead of leaving the press's sentence on an open box.

Enter asks the same question and calls the same function. The keydown handler's guard is now public/app.js:11352 if (queuePressInFlight(box.dataset.reply)) return;, and the Enter branch and the button both go through queueReplyFromBox, so a keystroke cannot reach a state the button refuses.

The four tests

test/queue-single-press.test.js drives the page's own functions over a small DOM model, and each of the four named claims is its own test:

claimwhat it asserts
(a) the box takes text againafter one press: contenteditable="true", no aria-readonly, button live, box empty, note 1 queued, and a second message can be written.
(b) two different messages both holdpress, type, press: two entries, in order, each with its own at, note 2 queued.
(c) a press inside the flight holds nothingthe press is not awaited; the mid-flight face is asserted (closed, button off, queued, waiting, the press's placeholder); a second press with text in the box is refused and the queue still holds one entry; the face is gone once it settles.
(d) Enter obeys the same predicatethe keydown guard asks queuePressInFlight, the old queueWaitingOn guard is gone, both branches call queueReplyFromBox, and the guard answers yes mid-flight and no after it.

Three more in the same file: the face comes off when the commit throws, the drain sends two held replies in the order they were written and takes the count off the card, and a double press in one turn holds one entry. On the base build the file fails at load: the page carries no queuePressInFlight(), which is the point of the split.

The real card

tools/verify-queue-multi-hold.mjs boots the panel from a tree, fabricates a running turn in the page's own state.jobs, lets the page's own renderer draw the card, stubs the page's fetch so nothing reaches a gateway, and drives it with a real mouse and a real keyboard.

What changed

  • public/app.js - state.replyPress; queuePressInFlight, queueWaitPhrase, pressSettled; queueReplyFromBox is async and releases the flight in a finally; paintQueueWait paints the flight face and the count; queueWaitingOn is the count only; the keydown guard and both call sites follow it.
  • public/render-jobs.js - the closed face from queueInFlight, the count from queueHeld, the idle sentence kept on data-ph-idle.
  • test/queue-single-press.test.js - rewritten to the split: (a), (b), (c), (d), the failed-commit face, the drain order and the double press.
  • test/queued-reply-attachments.test.js - the press is awaited, and the harness carries replyPress.
  • tools/verify-queue-multi-hold.mjs (new, npm run verify:queue-multi-hold); tools/verify-queue-single-press.mjs removed - its contract, a held reply closing the card, was the defect, and it would pass only on the build this landing replaces.
  • package.json - the new verify script and the version.

What the fix does not change

Queueing is still the page's own: a press commits an entry to state.replyQueue and sends nothing. The flight the guard covers is therefore the press's commit plus the task the browser takes to draw it, not a network round trip - if the press is ever given a server write, that write belongs inside the same claim, and the closed face will cover it without another change. The same text typed twice on purpose is still two entries: that is the reader's business, and 205d7098 was about one press delivering one entry, which it still does.
