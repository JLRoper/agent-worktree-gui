1. The reproduction: one real wave, both ways

A real panel (tools/panel-testkit.mjs booting server.js) with a throwaway config, one initiative made through POST /api/initiatives, then one wave made through the only writer there is. The tab was read once before the wave so its memo existed, exactly as it would after a reader opens the tab and then asks for a wave. Both reads were taken back to back, with no write through the initiatives route in between.

POST /api/waves              200  {"ok":true,"wave":"the-wave-in-question"}
GET  /api/waves?initiative=<id>   200  {"found":true,"readable":true,
                                    "waves":[{"id":"the-wave-in-question","title":"The wave in question",
                                              "state":"empty","stateWord":"no members"}]}
GET  /api/initiatives        200  {"waveStatus":{"found":false,"readable":true,
                                                 "gateChoices":["clean","pr-open","pr-head","pr-approved","pr-merged"]},
                                    "initiatives":[{"id":"init_mx09cooo_aiuyjw","waves":[]}]}

Broken on disk, the same two callers also disagreed about whether the store could be read at all:

GET /api/waves?initiative=<id>   409  {"refused":"unreadable"}
GET /api/initiatives        200  {"waveStatus":{"found":false,"readable":true}, "card waves":[]}
Read the second line with the first: the route says the file cannot be read, and the tab says it can, with no waves. Neither answer is a parse error. They are two different reads of the same file.

2. The field and each route's arithmetic

RouteWhere it computes the answerWhat it says about the wave
GET /api/waves laneView() per request: waves.statusOf() for the store's status and waves.wavesFor(id) for the records (routes/waves.js:170-196), on a store whose load() re-stats the file (lib/waves.js:322 stampOf, lib/waves.js:422 statusOf). found: true, one wave, state: "empty". GET /api/initiatives cachedView(): the last built document, kept in memory and on disk beside the initiatives store and answered while younger than VIEW_STALE_MS = 2000 ms, and even when older returned while a rebuild ran behind the reader (routes/initiatives.js:599-616 before this change). The document was built when the initiative was created, before the wave existed. waveStatus.found: false, card waves: []. The file as it was when the document was built.

The differing field is waveStatus.found - false on the tab, true on the waves route - and it drags the card's waves array with it: empty versus one record. In the broken-file case the differing field is waveStatus.readable: true on the tab, and the route's 409 refused: "unreadable".

The two routes did not disagree about how to fold a lane; both call the same waveLane() over the same records and the same queue rows. They disagreed about when they read. The waves route read the store now. The tab answered a document it had read earlier and presented it as now, because its memo was keyed on nothing but the clock. The record had moved and the memo had no way to know.

3. The authority chosen, and why

The store is the authority: waves.json, through the one shared Waves instance.

The derived read is not a second source of truth and must not be promoted to one. Three reasons:

  • The store is the only authored document. A lane is a projection of it plus the queues and the evidence; if the projection is allowed to outvote the record, a wave a reader just wrote can be denied by a document nobody wrote.
  • The waves route cannot cache without lying about a file a reader may have just edited by hand - a hand edit is a first-class way to author this store, and the store's own loader was built to notice it on the next read (lib/waves.js:322-343).
  • The tab's memo exists for a cost reason (the gate-evidence join measured 25-52 s on a loaded box, longer than the client's 12 s timeout), not to define correctness. Its key was the clock; the key must be the input.

So the tab's memo is now served only while it was built against the wave store's current file, status and mtimeMs:size stamp, and while the member rows that can open or close a wave are unchanged. When any of those has moved, the read waits for a fresh fold instead of answering a lane the waves route would contradict.

7. What this guarantees, and what it does not

Guaranteed: the tab's read never answers a wave record, a wave's existence or the store's readability from a document built against another store state. The member rows that decide whether a wave is open or closed are part of that key, so a queue write that changes a member's state, worktree or named abandonment also forces the tab to fold again before it answers.

Not claimed: the memo's two-second window still applies to facts read from the world rather than from the store - the board rows behind a gate's evidence, and queues of tasks that name no wave. Two calls a moment apart can differ if a pull request merged or a board row changed between them. That is two different times, not two different computations, and both routes read those facts through the same evidence reader (lib/wave-evidence.js) when they fold.
