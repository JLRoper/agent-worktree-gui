1. What the reader measured, and why the code agreed with it

With the Initiatives pane at its top and its content exactly filling the box, the first card's expansion grows the pane past its box. The pane then has to decide where its reader is, and it decides before the repaint, in captureInitScroll. The old test was the standard one:

atBottom: scroller.scrollHeight - scroller.clientHeight - top < 2

For a pane at its top with no overflow that reads 0 - 0 < 2 - true. It is true for a reader parked on the last line of a long list too, and the two states are numerically identical: nothing in scrollTop, scrollHeight or clientHeight tells them apart, because when the content fits, the box's height is the content's height and scrollTop can only be 0. So the first branch of restoreInitScroll took the pane to scrollHeight, the browser clamped it to the new maximum, and the card the reader had just opened went off the top.

The missing number is not the position but the slack the pane had before the change. That is what the fix measures, and it is the one thing about the old state that the old test threw away.

2. The change

Two lines in the capture, one branch in the restore, and the comment that names the cause. Nothing else about the pane's scroll was touched: the card anchor, the top rule, the sub-pixel guard and the fallback to the old number are exactly as they were.

const slack = scroller.scrollHeight - scroller.clientHeight;
const overflows = slack > 1;
return {
  scroller,
  top,
  card: card ? { id: card.getAttribute("data-init-card"), dy: card.getBoundingClientRect().top - box.top } : null,
  fits: !overflows,                       // did not overflow before the change: pinned to its TOP
  atTop: top <= 0.5,
  atBottom: overflows && slack - top < 2, // a reader can only be at the bottom of a pane with slack
};

In restoreInitScroll the bottom branch keeps its place (it is the state that must survive growth below the reader) and fits is answered next, before the anchor: a pane that never overflowed is on its first line, so the growth lands below what the reader is looking at and the pane stays at 0. The anchor branch is then reached only by a reader who really did scroll, which is the case it was built for.

4. public/app.js: the same test, a different question

The row named public/app.js too, so its three at-bottom tests were read one by one. All three are about an output console, whose content only ever arrives at its foot, and none of them is this defect:

  • public/app.js:10015 and public/app.js:13016 - the record kept for a pre.job-out console across a card rebuild. A console that fits is one whose newest line is already on screen, so "fits means following the tail" is what the reader wants there, and render-jobs.js:1091 uses it to follow. Making a fitting console stop following would leave the next streamed line below the fold - a regression, not this fix.
  • public/app.js:12981 - state.subConsolePinned, written only inside readerInputHere(pre): a reader's own gesture, which a pane that fits cannot produce without a scroll.
  • The console's own fold rebuild - the console equivalent of this row - already carries an anchor: public/board/console.js:2805-2808 re-measures the row it held and corrects by that offset, so an opened tool group does not need the at-bottom test at all.

So public/app.js is unchanged. If the reader would rather the console's "fits" also stopped counting as "following", that is a different behaviour with a different cost, and it belongs in its own row.
