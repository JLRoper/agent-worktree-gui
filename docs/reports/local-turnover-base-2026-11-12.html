1. The pair this extends

The base the board compares every row against is one function: resolveBaseRef in lib/base-ref.js, which builds the project's remote plus main branch from config.json. The line that builds it, quoted from the file at :67:

const remoteRef = picked.remote && mainBranch ? `${picked.remote}/${mainBranch}` : mainBranch || null;

That pair answers "what is this project's main". A cut asks a different question: "which commit does this tree start from". Before this landing there were two answers, and both were named: the checkout's own branch (startRefOf in lib/jobs.js), or the branch the project names in its settings (turnoverBranch, wired into the cut by ae6888ca). The third kind names nothing. It is found at the cut, and when nothing is found the cut stops and asks, because the one outcome this option exists to prevent is a silent fallback to main.

2. Three conditions, held together

A local branch is a candidate only when all three are true. Each one alone is a different wrong answer, which is why each has its own test.

#ConditionThe mistake it refuses
1the name is the turnover shape YYYYMMDD_HHMM_<KEY>_<slug>a feature branch, pushed and unmerged, is not turnover work
2a remote carries a branch of that namean unpushed branch is invisible to everyone else, so a child of it can never be rolled back
3it is not an ancestor of main or mastera merged branch looks perfectly publishable and has nothing left to roll into

The name pattern is not copied. lib/turnover-base.js compiles the push gate's own string, BRANCH_NAME_GATE_PATTERN from lib/push-permissions.js, so the gate that decides what may be published and the resolver that decides what may be a parent cannot disagree about which branches are work. One deliberate relaxation, commented in place: the gate's slug class is lowercase because it decides what publishes without asking, while a real turnover slug carries the reader's words, so the resolver widens the case class and keeps the date, time and ticket half character for character. Ancestry is asked as data, git rev-list --count <base>..<candidate>, because a zero there is the answer and an exit status is not distinguishable from a failure through this panel's git helper.

3. The scratch repository

5. Tests, red first

The tests were written before the resolver and failed against it. What they cover, one rejection reason per test:

  • a merged turnover branch is rejected: it is an ancestor of main
  • an unpushed turnover branch is rejected: no remote carries it
  • a feature branch is rejected: its name is not a turnover name
  • with no qualifying branch the rule answers nothing, and says why for every local branch
  • two qualifying branches resolve the newer one, because the name is its own clock
  • the name test is the one pattern, not a second copy of it
  • a real repo with a merged, an unpushed and a valid branch resolves only the valid one
  • a cut on the option asks the reader when nothing qualifies, and cuts nothing
  • the brief for a run cut on the option carries the local-only turnover rule
  • a run cut on the option receives the rule in its brief
  • the three kinds are one list, and a project that names a branch reads as the named kind
  • the row stores the third kind with no branch name, and never stores a kind that absence already means
  • the wire shape carries the kinds and their labels, and each project's kind
