2. One helper, and why it parses the page

tools/style-sheets.mjs is the only place that reads the sheet list. Four functions:

styleSheetFiles({ root })        ["base.css", "chrome.css", ...]   in load order, all 22
styleSheetPaths({ root })        the same names as absolute paths
readStyleSheets({ root })        one string, every sheet in load order, LF newlines
readStyleSheets({ files })       the same for a caller's own subset
styleLinkTags({ root, prefix })  the <link> tags a fixture page serves, one per sheet

Load order is the reason the list is parsed and not written down. A rule's cascade position is half of what it means to a browser, so a concatenation in any other order is a different stylesheet, and a hand-written list goes stale the first time a surface gains a file. Two properties follow from parsing the page:

  • A sheet deleted from disk fails loudly. styleSheetFiles throws when the page links nothing or links a name public/ does not hold. That is the one way a "this rule is not in the stylesheet" assertion can lie: reading an empty string passes it.
  • A --root build keeps working. The four fixture tools take PANEL_ROOT (a git archive of a base commit, for the before picture). Their pages are built from THAT build's public/index.html, so a pre-split export still links its one file and the before/after pair stays honest.

The four private copies of the parse are gone with it: test/style-sheets.js now delegates (keeping its 19-sheet subset filter and the two names every test imports), verify-css-split.mjs and css-split-review.mjs call styleSheetFiles, and verify-queue-agents.mjs's sheetsFromIndex() is deleted.

One reference to the deleted file survives on purpose, in one place: verify-css-split.mjs reads the pre-split blob out of git to prove the split, so it must name the path. It is spelled as a constant (LEGACY_SHEET = ["public", "style.css"].join("/")) with a comment saying why, so the sweep can still answer nothing while the gate says what it proves. Nothing reads that path from disk anywhere.

4. The queue gate: a skip needs a live holder

The lane rule (queue row #293) skipped a queued row only when a LIVE job's row claims one of its files (liveRowHolders + laneRefusal, lib/spawn-check.js:170 and :241). verify-queue-cards.mjs seeded one running task with no live run at all, so after that rule landed the SKIPPED note the gate pins could never appear: 6 of the eight route checks passed (the eighth was the readFileSync throw).

The fixture now carries the fact the rule reads. A fifth task, #5 "Hold the lane on the split sheets", is a running row whose run id is in the sandbox job store: one record written to <sandbox>/logs/jobs.json before the panel boots, status running, thread seed-thread-holder. The sandbox's gateway is a dead port and the boot reconcile skips a restored run it cannot ask about ("a restored turn stays live and pending"), so the run reads live for the whole gate. Task 1 keeps no run id and stays STALE, which is the pair the gate needed: one stale running row that holds no lane, one live row that does.

PASS  …the first running task is stale (no live run behind its threads), so the row has a note to draw
PASS  …the second running task is LIVE, its run answered by the seeded store: (live)
PASS  …the queued task is skipped against the live holder, so the row has its reason:
      files in use by #5 (job seed-run-holder on thread seed-thread-holder, running) - #2 also claims
      public/assistant.js, so starting it would put two workers in that file. wait for job seed-run-holder
      to end and land #2, or record an explicit overlap first (queue action allow-overlap, which stores
      who allowed it and the file).
PASS  …and the stale row holds no lane: the skip names the live holder, never #1

The pane draws running rows first, so the cards are #1, #5, #2, #3, #4: the note assertions are indexed to that order, and the live holder's row is checked for the absence of a note. All twelve checks before the browser half pass.

5. What is still red, and why it is not this row

Three gates are red on this branch for reasons that predate it. Each was measured on the base with only the deleted-file read stubbed, so the numbers are comparable.

verify-queue-cards.mjs: seven browser assertions

47 checks, 7 failed, all seven after the browser opens: "a surface of its own" (the done card's background: var(--card) equals the group's), "the actions row is the card's last child", "sits at the card's bottom edge", "below the head", "one sub-row per agent, with its thread" (the agent line now leads with project:), "the meta line still names the tree and the files" and "truncates a long file list" (the meta line now reads project agent-worktree-gui; the tree and files moved). On the base, with the readFileSync stubbed so the browser half could run at all, the same seven fail in the same words. They pin the pre-#410 card, and re-pinning them is a card-layout job, not a stylesheet one.

verify-css-split.mjs --stream

The half-A comparison reads the last commit that holds the pre-split blob and compares the CURRENT sheets to it rule for rule: 3,061 old rules against 3,076 now, first divergence at rule 423. Any CSS change after the split makes that comparison red by construction, and CSS has changed several times since (1.191.0's cut dialog and board table, 1.194.0). The base answers exactly the same two numbers with the same first divergence, so this branch changes nothing about it. Repairing it needs a decision (compare against the split commit's own sheets, or pin a baseline file), which is why it is reported rather than guessed at.

verify-child-button.mjs: two JS-half assertions

23 of 25 pass. The two failures are "it sends the project, the row's path and the name" and "cancel cuts nothing": cutChildTree (public/app.js:7943) now opens a cut dialog (openCutDialog) instead of POSTing a fixed body, so the gate's regexes describe a handler that no longer exists. The two read public/app.js and never touched the stylesheet, so they fail identically on the base once the missing-file throw is out of the way.
