1. What was wrong

Two readers answered "may this row start?" and only one of them was asked at the cut. The digest's lane is derived at read time (laneInfo, lib/assistant/queue.js:1503): it groups open rows that claim the same file, names the lane after the file, and prints waiting on #N behind a live head. decorateTasks also set a conflict and a skipped sentence for a queued row whose files touched a running row's files (lib/assistant/queue.js, the block above :1431).

The cut did not consult either. Assistant#taskRowCheck (lib/assistant.js:2577) ran rowRefusal - a refusal only when the ROW already has a live worker - and jobs.create ran heldTreeRefusal - a refusal only when a TREE already holds a live run (lib/jobs.js:3845). A shared file is neither. So GET /api/assistant/spawn-check answered ok: true for a row the digest was printing SKIP: for, and on 2026-11-24 two workers reached public/style.css because of it.

There was a second half. The digest's conflict was computed against every running row, including a STALE one whose run had ended. The cut refuses only a live worker, so the same disagreement existed in the other direction: the digest said SKIP and the cut would have started the row.

2. The change: one predicate, two callers, one sentence

liveRowHolders (lib/spawn-check.js:155) finds the rows a LIVE job is working whose files this row also claims. It takes a liveness(row) callback because the queue reads liveness from its run record and the cut reads it from the job store; both hand the result to the predicate rather than judging the overlap themselves. A row is a candidate only while it reads running, and only while its liveness answers live: true - a stale row holds nothing, which is what lets the row start once the holder settles.

laneRefusal (lib/spawn-check.js:226) is the ONE decision and the ONE sentence. Its refusal is shaped like heldTreeRefusal: it names the holder row, the file and this row, and its remedy names the job to wait for. The wiring is the part that makes drift impossible:

readerhow it reaches the predicate
the pre-flight routeroutes/assistant-spawn-check.js:108 calls assistant.spawnCheck (lib/assistant.js:2661), which calls taskRowCheck, which calls taskLaneCheck (lib/assistant.js:2640)
the cutstartSpawn calls spawnTaskRefusal (lib/assistant.js:7844), which calls the same taskRowCheck and throws sentenceOf(check); the harvest pre-check at lib/assistant.js:6930 calls the same function before the line is carried out
the digestdecorateTasks (lib/assistant/queue.js:1431) calls liveRowHolders and laneRefusal itself and sets skipped = sentenceOf(lane) (lib/assistant/queue.js:1452), printed as SKIP: ${t.skipped} (lib/assistant/queue.js:1665)

Because the digest's skipped is built by the same function the cut throws, SKIP: followed by the cut's message is the digest's line, character for character. There is no second phrasing to drift.

4. The exception: one holder, one file, one person

An overlap is refused unless someone explicitly recorded an exception. POST /api/assistant/queue with action: "allow-overlap" (lib/assistant.js:2467) resolves the LIVE holder from the same taskLaneHolders the cut reads and writes one entry on the row:

[{"file":"public/style.css","holder":1,"by":"reader","at":"2026-11-24T12:24:50.308Z","reason":"both rows are one edit to the same rule"}]

The exception is a NOTE, never a refusal: the pre-flight answers ok: true with code: "lane_allowed", the row starts, and the cut journals the decision (spawn-overlap). The digest and the queue card say who lifted the rule and for which file:

ALLOWED PRE-FLIGHT reason: files in use by #1 (job run_holder on thread t-holder, running) - the overlap with #2 on public/style.css was allowed by reader at 2026-11-24T12:24:50.308Z: both rows are one edit to the same rule
ALLOWED DIGEST: - ○ #2 queued · the same rule, next · thread (none) · tree (none) · PR none · files public/style.css · LANE ALLOWED by reader on public/style.css (overlaps #1)

It is deliberately narrow: it names the holder it was decided about and the file. A second live holder on the same file is still refused (test "an exception covers ONE holder and ONE file"), and the action refuses to store an exception when no live run holds the file - a licence for a run that is not there would apply to a later row nobody decided about. clear: true removes the record and the lane is back.

The queue action is the door, not a mute: the row's own record carries the decision, so a later reader can say who lifted the rule. The digest, the pre-flight and the journal all read that one record.

5. What did not change

The per-tree guard is exactly as it was: heldTreeRefusal (lib/spawn-check.js:133) is still what lib/jobs.js:3845 refuses a second cut in a held tree with, and the lane check is a second check beside it. A SPAWN into a tree a live run holds is still tree_busy; the existing test/spawn-check.test.js case that compares that refusal with the cut byte for byte still passes.

One behaviour changed on purpose: a STALE running row no longer produces a SKIP on a queued row. Its run has ended, the cut would start the row, and the old SKIP was the same disagreement from the other side. The running row's own line still says STALE with the reason, so the fact is not lost; the test that pinned the old behaviour now pins the new one (test/assistant-queue.test.js, "a STALE running task no longer blocks a queued one").
