3. Gap 5.1: the review loop cannot answer a comment

This gap was named in section 5.1 of the 2026-11-09 report. It has no Jira request, no queue row and no test. This section files it and prices it.

3.1 The defect

The SEFL ladder's wait stage has two ways out: H-04 is a loop to address, and H-06 is a sequence to approve. The driver takes the rail first: edgeOutOf sorts the outgoing edges by EDGE_ORDER, which is sequence, return, loop (lib/task-pipeline-drive.js:185). So the walk is wait → approve, and address is never entered. No gate routes the other way: G4 carries no decision and no routes. A reviewer's comment can arrive, be read once at the wait turn, and never be answered; the ladder walks on to the approval stage and then to the merge. The design document says the loop is wait → address → wait → approve (docs/pipelines.md:319); the executable document does not draw that walk.

There is a second half the graph alone does not fix: the wait timer reads stage.exit.check (lib/pipelines.js:667, lib/jobs.js:2297), and a PDL stage declares an artifact, not an exit. So no wait is registered on a PDL wait stage in the first place. Even if one were seeded by hand, the timer's advance takes the next stage in the reading order, not the graph's handoff, and does not count a loop crossing (lib/jobs.js:2400). The comment cannot be answered because the panel never wakes the address stage, and if it did, the crossing would be uncounted. The test that covers the timer says so in its own comment: a PDL stage "names the artifact it writes, not the check that ends it, so the ladder timer has nothing to read for a PDL pipeline" (test/pipeline-wait.test.js:144).

Evidence: nextStageOf on the shipped bundle returns wait -> approve H-06 sequence; pipeline-bundle.seed.json H-04 at line 4679, H-06 at line 4696, G4 at line 4741; docs/pipelines.md:319; lib/task-pipeline-drive.js:185 and :901; lib/pipelines.js:586, :667; lib/jobs.js:2297, :2400.

4. Gap 5.2: the conversion dropped four checks

This gap was named in section 5.2 of the 2026-11-09 report. It has no Jira request, no queue row and no test. This section files it and prices it.

4.1 The defect

The design's exits are stronger than the PDL gates. Each dropped check is a fact a reviewer relied on. The four distinct checks are below; pr-head is dropped at two stages, but it is one check.

Gate numbers in this table are the SEFL ladder's. The GitHub ladder uses its own G1 to G6, has no address stage, and shares only pr-head and main-moved.

The GitHub walk shows the same pattern on the two checks it shares: pr-head and main-moved. The pr stage's prompt asks the worker to run gh pr view --json state,headRefOid,baseRefName and confirm the head; the main stage asks for git fetch and an ancestry check. Both are prose when they run, and the panel reads neither. A worker that skipped them would have produced the same green stage order.

4.4 Checked, not fixed here

  • The GitHub delivery is supposed to read the PR head and the main ancestry in its stage ledger. That is what makes the PR trustworthy; it is not what made the stage advance. The stage advanced on the artifact and the run.
  • The turnover ladder's last stage is also kind: "pr", so a correctly open PR reads running / STALE. That is the same settle rule as 5.2's last check but a different defect; it is not one of the two gaps here. It needs a landing outcome that can be OPEN by design.
  • The exact reviewer set is the check most likely to be wrong on SEFL in practice: PR 7 already carries code_review_java and an individual POORE entry, and Alex's review is recorded there. If the check runs after an individual reviewer is added, it will read two names. The PR stage's check must run at open, before the approval adds an entry, or the expected set must include the individual. The test plan below decides this before it runs.

  3. Set the branch permission. The worker's account gets read on the repository and write on the source branch, and no merge right on master. A repo owner has to set this; it is the only precondition the panel cannot create.
  4. File the row. On the panel, file a queue row onto sefl-review-loop at branch (or pr if the branch is already pushed), pointed at the PictureViewer worktree. The row is the test's record; it must name the PR and the reviewer.

5.3 The walk

  1. Let the ladder run branch → push → pr. At the pr stage, read the PR back: one PR, head equals the pushed commit, reviewers exactly the set decided in setup, four description sections.
  2. At wait, read the tree's pipelineWait. It must carry check: "pr-comments", every: 3600000, the thread and the branch, and no live run hold. Today it will not exist; that is the first expected failure.
  3. Have Alex approve the exact head. If the head moves after his approval, the approval is stale; the test needs both cases. The clean case is an approval at the final head. The negative case is a second commit after the approval, so lastReviewedCommit no longer equals the head.
  4. Arrive at merge with the clean approval. The worker POSTs the merge endpoint with the PR id and its current version. The account has no merge right, so the host answers 401 or 403 with a sentence. Record the status, the sentence, the PR id, the head, master's sha before and after, and the fact that no retry was made.
  5. Read master after: its sha is unchanged. Read the PR: still OPEN, approval at the head. Read the row: it is parked with a reason beginning merge-refused:, not running, not done, not STALE. The board still shows the PR URL.

5.5 Falsifiers and cost

Falsifiers. Any of these fails the test: a second PR for the same branch; a reviewer set that is not the set decided at open; a merge POST retried after the 403; pr-merged written without a MERGED read; the row marked done; master's sha moved; or a final message that claims the work landed.

Cost. The fixture half is 1-2 days: a stub host, a scripted seat, eight assertions, and a ledger that names the run, the stage and the verdict at each step. The live half is half a day once the branch permission exists; the permission needs a repo owner. The test will fail today by design; it should be filed as a red test and turned green by 5.1 Cut B and 5.2 Cut B, not by weakening its assertions.
