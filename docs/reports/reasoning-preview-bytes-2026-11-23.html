The reasoning preview now sends each word once

Written 2026-11-23 for branch wtgui/stop-the-reasoning-preview-re-sending-0eaf60, cut from b35bc604 (main, 1.162.6). Every number below comes from tools/measure-reasoning-preview-bytes.mjs run twice: once on the base build, once on this branch with the same scripted turn. Both JSON reports from the two runs are kept with the run's scratch files as reasoning-preview-before.json and reasoning-preview-after.json; nothing is quoted from memory.

1. The claim this instrument was built to test

A live reasoning.delta preview grows ONE thinking block under a stable at. The panel coalesced the gateway's tokens into a frame every 120 ms (TEXT_FLUSH_MS), and each of those frames carried the WHOLE block so far. Nothing in a repeat frame is new: the text is the same text the tab already had, bought again. The cost therefore grows with the square of the block's length, and a long think is exactly the case where it hurts. Row 256 measured this as the next 40% of stream cost; this is the frame-level proof and the fix.

The seam

  • lib/jobs.js:2155 flushReasoning(j): the one place a preview frame is built. It emitted { kind: "dim", think: j.reasoningLive, at, thinkOnly: true }.
  • public/board/console.js:3813 appendJobLine: the one place a preview frame is read. It took line.think as the block's whole text and replaced the cached block.
  • Nothing else in the tree sends or reads a thinkOnly frame. public/app.js only schedules the store poll (sweepThinking, public/app.js:3421) and never touches the frame, so the change did not need to go there; forcing an edit into it would have been a third seam with no work to do.

2. The harness

tools/measure-reasoning-preview-bytes.mjs boots a sandbox panel of its own (own config, own state, assistant off), points it at a stub Runs API that plays ONE console-heavy turn, and attaches one raw SSE reader to /api/stream?shape=delta. The scripted turn is a 48,000-character reasoning block streamed in 64-character deltas every 40 ms (about 1,600 chars/s) with six prose paragraphs and four tool calls interleaved, then run.completed. Every frame is counted by event name and by its exact bytes, and the preview frames are split by whether they carry a whole block (thinkFrom 0) or an append. 

# BEFORE: this tree at its cut point, b35bc604 (origin/main at 1.162.6), before any edit
node tools/measure-reasoning-preview-bytes.mjs --label before

# ...the fix, committed...
# AFTER: the same tree, the same scripted turn
node tools/measure-reasoning-preview-bytes.mjs --label after

--root <dir> boots a build that is not this checkout, for measuring a git archive export of a base instead of the tree the work is happening in. The harness refuses to report a win when no preview frame arrived at all (exit 2), so a build that silently stops relaying reasoning cannot measure as a beautiful zero.

The one number that does not depend on the turn's shape: 107.14x to 1.00x. The old frames carried the block 107 times over; the new ones carry it once. That multiplier is what the quadratic did, and it grows with the block, so a longer think paid worse than this one.

4. What the change is

flushReasoning now sends the tail after the last text it put on the stream, plus thinkFrom: the offset that tail starts at inside the block. The browser holds the block under the same at and appends when thinkFrom is where its copy ends, so the pacer keeps typing where it was and the block never re-keys. A frame with no thinkFrom (the finished reasoning.available line, or any sender from before this change) still replaces wholesale, exactly as it did. A tab that joined mid-block has nothing to append to, so it starts its copy at the offset the frame names and the store read at settle paints the complete thought; a gap in the offsets replaces rather than splicing out words the tab never received.

5. What the report proves, and what it admits

Proves

  • The bytes a tab receives for one console-heavy turn fall from 5.26 MB to 164 kB (-96.9%), with the same number of frames and the same console lines, so the saving is frame SIZE, not a frame that quietly stopped being sent.
  • The reasoning block's text crosses the wire once instead of 107 times (the exact invariant is also pinned at unit level in test/reasoning-delta.test.js: the chunks of one block concatenate to it, with thinkFrom always where the last chunk ended).
  • The browser half is pinned in test/reasoning-delta-pane.test.js: a contiguous chunk appends onto the block this tab holds; a mid-block attach starts at its offset; a gap replaces instead of corrupting.
  • The console's own lines measure the same on both builds (11.35 kB vs 11.35 kB), which is the control: the harness is not comparing two different turns.

Admits

  • The turn is scripted, not a real model. Its 48 kB at 1,600 chars/s is one plausible turn, and the absolute kB is that turn's; the 107.14x -> 1.00x multiplier is the shape independent part.
  • The sandbox board is empty, so "99% of the stream" is not the share a busy board would show. Rows, snapshots and job summaries would add bytes to both runs and lower the share on both; the preview's own byte drop is unaffected.
  • The two runs flushed a slightly different number of frames (249 vs 248 jobline frames) because the 120 ms flush is wall-clock. That is why the comparison is stated in bytes and in the per-character multiplier, not in frames.
  • Bytes are the SSE frame as the panel writes it (event: and data: lines included), not HTTP headers or transfer encoding, which this harness does not see.
  • Nothing here measures the page's render cost, only the wire. The pane's painting is covered by the two test files above, not by a browser run.
