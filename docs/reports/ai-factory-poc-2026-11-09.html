The answer in one paragraph

Both services work from an HTTP client on loopback and both leave a defensible record. Qdrant proves a filtered vector search over the panel's own reports end to end: create, upsert, query with a payload filter, read a point by id, delete. The vectors are a deterministic lexical stand-in because no embedding service exists on this box, so the plumbing is proven and retrieval quality is not. n8n proves a script can create, publish and call a flow, and read its execution back, through the public /api/v1 surface with an API key; the webhook is unauthenticated and the editor's /rest surface is not a contract. The design order that follows is: Qdrant over the panel's documents first, n8n stage events second, Qdrant over a worktree's code third, and a flow standing in for a stage only where the panel keeps ownership of the stage record, the gate decision and the handoff pin.

2. Qdrant: technical record

2.1 What it is and how it is reached

Qdrant is a vector search engine. It stores points, each a vector plus a JSON payload, and answers nearest-neighbour queries with optional payload filters. The instance on this box is the official container qdrant/qdrant:v1.12.4, published on 127.0.0.1:6333 (HTTP) and 6334 (gRPC), up two days at the time of the POC. There is no authentication on the HTTP port; loopback is the only boundary. The POC read the version from GET / and the container state from docker ps; both are recorded in the Qdrant report.

The panel is not a client today: it has no Qdrant module, no embedding client and no search route. The POC's client was the run's own script, and every request below is the exact path and body it sent.

2.2 The collection and the corpus

The POC created one collection, poc_panel_docs, and deleted it after the captures. The pre-existing engineering_standards collection was listed before and after and never written to. It holds 12 points at 512 dimensions, Cosine. The POC collection held 56 points at 64 dimensions, Cosine, HNSW m: 8, ef_construct: 64, two segments.

The five files were chunked with a 700-character window and a 600-character stride, at most 12 chunks per file. That is a bounded sample of each file, not the whole file. Every point carries the same four payload keys: source (repository-relative path), offset (character offset of the first character), length (characters in the chunk) and chunk (ordinal in the file). The chunk text itself is not stored; it is recoverable from the file at the offset. That is why a hit can be cited back to a file and a character position, and it is why the search response is small enough to quote in full.

{
  "source": "docs/reports/step-8-queue-prefix-2026-11-07.md",

  "length": 700,
  "chunk": 0
}

The embedding gap, stated plainly

The POC found no embedding service on this box. It probed http://127.0.0.1:11434/api/tags (Ollama) and http://127.0.0.1:1234/v1/models (LM Studio); both refused the connection. There was no OPENAI, DEEPINFRA or EMBED* variable in the environment, and a repository-wide search for embedding and qdrant returned nothing before the report existed.

The 64-component vectors are therefore a deterministic hashed bag of words, not a model's output: lowercase, tokenize, each token and adjacent bigram, FNV-1a 32-bit, index hash % 64, sign from bit 31, weight 1 + ln(count), L2 normalise, round to six decimals. Identical text produces identical bytes on any machine. It rewards shared vocabulary, not meaning. The filtered search below proves the request path, the filter and the payload round trip; it does not prove retrieval quality.

2.4 Latency and limits, measured

641.5 mscreate collection, the slowest call
71.6 msupsert 56 points, 35,454-byte body
60.4 msfiltered search, 3 hits
13.0 msread one point by id
88.9 msdelete the collection
2,449response bytes across 9 calls
  • The create call is not a query cost. Its 641.5 ms includes the segment and WAL setup the server does on first write; Qdrant's own time is 612.33 ms. A search over this collection is 60.4 ms client side and 39.09 ms server side.
  • The upsert is one batch. 56 points in a 35,454-byte body took 71.6 ms client side and 50.65 ms server side. The body size is a function of 64 dimensions and four payload keys; a 1024-dimension collection will not fit the same number of points in the same bytes.
  • No payload index was created. At 56 points the filter scans the sample; the collection's payload_schema is {}. That is fine here and wrong at a million points.
  • indexed_vectors_count is 0. The 56 points are stored and searchable, but below the indexing threshold (20,000), so the HNSW graph has not been built. The reported result is a scan, not an index lookup.
  • Persistence across restart, replication and throughput were not tested. The container stayed up; each call was made once; there is no p99.

3. n8n: technical record

3.1 What it is and how it is reached

n8n is a workflow automation service. A workflow is a graph of nodes; a Webhook node makes it callable over HTTP; the public API at /api/v1 manages workflows and reads executions. The instance on this box is the official container docker.n8n.io/n8nio/n8n:latest, published on 127.0.0.1:5678, up two days at the time of the POC. The running version is 2.46.6; the image id is sha256:8602f5dfacbe2c931eeafd010de0e68182310e9f309921e780ab69182e92b3ae, created 2026-11-04T13:04:10Z. The latest tag is not pinned; the digest is what identifies the build.

The instance was already set up with email and password authentication. The owner person record carries createdAt: 2026-11-06T20:49:35.556Z and role: global:owner, so the setup call read an existing account rather than claiming a fresh instance. Instance settings are public at GET /rest/settings: SSO is off for SAML, LDAP and OIDC, the auth cookie is not marked secure, community nodes are enabled and mail setup is absent.

The webhook call's client time is 848.3 ms and the execution's own start-to-stop time is 662 ms, so about 186 ms of the round trip is outside what n8n timed. The executions screen shows the same 662 ms and the same start time, Nov 9, 02:11:17; that agreement is why 662 ms is the number to quote, not 848.3 ms and not the 882 ms an earlier brief claimed. The API record and the screen are the two readings.

  • The webhook is unauthenticated. It took no credential and returned 200. It is protected only by the container's 127.0.0.1:5678 publish; anyone who can reach the port can call it. That is a property of the deployment, not of n8n.
  • No TLS. The endpoint is plain HTTP on loopback and authCookie.secure is false.
  • One execution, no concurrency, no queue mode. The container is a single process in the default execution mode. No restart, no queued execution, no worker was tested.
  • No credentials, no external service, no error path. The workflow calls nothing outside n8n and its code node coerces with Number() and String(), so a malformed body still returns 200. There is no failure branch.
  • The first-write numbers are not steady-state. Create (221.7 ms) and publish (656.9 ms) include whatever the server does on first write; one call each is not a benchmark.

5. Design: Qdrant, ranked by cost and payoff

The panel's documents are the obvious corpus: they are already versioned, they are already the record an agent is asked to cite, and they are small. The code a worktree carries is the second corpus: larger, more volatile, and the one an agent reads most often. 5.2 Option Q1: a semantic index over the panel's documents

Rank 1. Cost: medium-low. Payoff: high. This is the smallest corpus with the highest reuse: every agent and every reader is already told to cite these files. The POC's 56 points and nine calls are a working prototype of exactly this shape.

Scope. Start with the 28 top-level files in docs/reports and the 2 in docs/design: about 992,000 bytes, or roughly 1,650 chunks at the POC's 700-character window and 600-character stride (estimate). Extending to all 154 Markdown files under docs is 3,181,079 bytes, or roughly 5,300 chunks (estimate). Both are small enough that a single collection holds them and a full rebuild is cheap.

Ingestion. One script, run on demand and after a merge, that reads each file, chunks it, embeds each chunk, and upserts in batches. The POC's payload is the minimum: source, offset, length, chunk. Add three fields the POC did not need: kind (report, design, architecture, landing), line (computed from the offset at ingestion, so a citation reads path:line), and commit (the tree the text came from). Keep source and offset authoritative; the line is a convenience that must be recomputed when the file moves.

Collection. size equals the embedding model's dimension, not 64. Cosine distance. The POC's HNSW m: 8, ef_construct: 64 is a starting point at this size; no tuning was measured. At 1,650 to 5,300 points the collection is below Qdrant's 20,000 indexing threshold, so the same scan behavior the POC saw applies and a payload index is not needed yet. Revisit both at 20,000.

Embedding source. The blocker. The POC found no embedding service here. The realistic choices are a local Ollama model (bge-m3 at 1024 dimensions or nomic-embed-text at 768) beside Qdrant, or a hosted model such as text-embedding-3-small at 1536 dimensions if egress and a key are acceptable. Whatever is chosen, the collection's dimension and the ingestion script's model must be pinned together; a collection created at one dimension cannot accept another model's vectors.

Query route. A panel route, not a direct Qdrant call from the browser: POST /api/search/docs with {query, scope, limit}. The route embeds the query with the same model, calls POST /collections/<name>/points/query with a filter on kind or source, and returns {source, line, offset, score, snippet, commit}. The browser never talks to Qdrant, so the model name and the collection name stay in one place. The route does not exist today; this is a proposal.

Freshness and failure. The index names the commit it was built at. A query whose commit is not the current HEAD returns results labelled with the commit they came from, not as current. If Qdrant or the embedding service is down, the route answers 503 with the reason; it does not silently fall back to a lexical ranking that the caller would mistake for the semantic one. Rebuild is a full upsert of a small corpus, so a failed incremental pass is repaired by the full pass.

Payoff. An agent asked "what did we already decide about the queue prefix" can get the report and the offset instead of grepping 3 MB of Markdown. A reader can search the report archive from the panel. The POC's filter proves that a hit can be confined to one source, which is the property a citation needs.

What is estimated, not measured. The chunk counts, the embedding throughput, the cost of the model calls, and retrieval quality. None of those is in the POC. The transport, the payload filter, the point read and the delete are measured.

5.3 Option Q2: search over a worktree's code

Rank 2. Cost: medium-high. Payoff: high for agents, medium for readers. The corpus is more than four times the Markdown corpus by checkout bytes (13,503,711 for JavaScript and CSS against 3,181,079 for the documents) and changes on every commit. It is also the corpus where exact grep is already strong, so the semantic layer must earn its place on conceptual queries, not identifiers.

Scope. One worktree at one commit, not the whole clone. Index tracked .js, .mjs, .css and .html files, excluding .git, node_modules, .staging and tools/vendor. At 441 JavaScript files and 172,436 lines, with 40 to 50-line windows and 10-line overlap, the estimate is 4,600 to 6,200 chunks; adding 13,484 CSS lines moves it up, not down. The estimate is arithmetic, not a measured index.

Chunking. Use the repo's own region markers where they exist: public/app.js carries 132 // ---- name blocks, and a chunk that follows a named region is more useful than a blind window. public/style.css has comment blocks but no such markers, so it takes the fallback. Fall back to 40 to 50-line windows with 10-line overlap for files without markers. Payload: worktree, branch, commit, path, startLine, endLine, symbol, text_sha256. The query filters on worktree and commit; a result that names a different commit is stale by construction.

Lifecycle. Index on demand for the row being worked, and drop the collection or the worktree's points when the tree is released. A per-worktree collection is the simplest isolation; a shared collection with a worktree filter is cheaper to operate and easier to query across trees. Start shared, because the filter is the same mechanism the POC proved on source. Reindex incrementally from git diff --name-only <indexedCommit>..HEAD; a file that moved or was deleted must have its old points removed, or the index answers from a path that no longer exists.

Payoff. "Where is the worktree lock route", "what does the queue prefix move touch", "which module owns the pipeline fan-out" are conceptual queries that a path-and-line answer serves well. Exact identifiers should still go to grep: a semantic index that returns a plausible neighbour for an exact symbol is worse than the exact match. The design should say which tool to use for which question, not pretend one replaces the other.

Cost driver. Embedding 4,600 to 6,200 chunks per worktree, on every index, is the dominant cost, not Qdrant. A code-capable model is also a different choice from a prose model; the POC did not test one. The honest first step is one worktree, one model, one query set, and a measurement of whether the answers beat grep on the questions agents actually ask.

5.4 Option Q3: cross-tree decision memory

Rank 3. Cost: high. Payoff: medium and uncertain. Index every worktree's reports and every assistant's decisions, then answer "has this been tried before" across trees. The corpus is larger than Q1, the freshness problem is harder, and the duplicate-work question is already answered in part by the panel's own tree and PR records. Defer until Q1 and Q2 have a measured query set.

5.6 What not to do

  • Do not ship the hashed stand-in as the production embedding. It is a test fixture with a documented algorithm, not a model.
  • Do not create a collection at 64 dimensions because the POC did. The dimension is a property of the model.
  • Do not index chunk text without a hash and a commit; a citation to text the file no longer carries is worse than no citation.
  • Do not let a semantic hit stand in for an exact identifier lookup. Keep grep, and say which one answered.

6. Design: n8n, ranked by cost and payoff

The panel already has a pipeline model with stages, gates and handoffs, and it already records more about a stage than most orchestrators do. n8n is useful at the edges of that model, not at its centre. The design below is written to fit the model that exists, and the first rule is the one that decides every option: n8n may perform work and carry events, but the panel keeps the stage record, the gate decision and the handoff pin.

6.1 The model the proposal must fit

Three documents define it. docs/task-pipeline.md is the shipped model: a queue task carries pipelineRun {pipeline, stage, enteredAt}; each entry into a stage is a stage run with the id <pipeline>/<stage>#<visit>; the run carries a decision record and an inputs manifest. docs/pipeline-sources.md is the bundle shape: stages carry an artifact and an owner role, gates end stages, handoffs join them. docs/design/pipeline-stage-execution.md is the design behind the record: a handoff is a commit and a blob, never a branch, and an absent artifact parks the row.

6.2 Option N1: stage events fanned into a flow

Rank 1. Cost: low. Payoff: high. One outbox writer, one sender, one n8n workflow. No change to the stage, gate or handoff rules, and no change to the driver's authority.

What fires. The driver already writes a decision on every park and every move that has a stage fact, and a stage run already carries its status, artifact and inputs. The event is a projection of those facts, not a new source of truth: on start asked, on settle, on a gate park, on an artifact park, on an input refusal, on a cap. The event names the stage run and the decision it is reporting.

{
  "event": "stage.settled",
  "at": "2026-11-09T12:01:10.000Z",
  "project": "agent-worktree-gui",
  "worktree": "<repo>/.worktrees/<tree>",
  "branch": "wtgui/<slug>",
  "pipeline": "poc-to-uat",
  "stage": "S8",
  "visit": 2,
  "stageRunId": "poc-to-uat/S8#2",
  "status": "done",
  "decision": {"by": "panel", "trigger": "stage-settled", "code": null},
  "gate": {"id": "G-10", "outcome": null},
  "artifact": {"id": "finding", "path": "ledger/G58.json", "present": true,
                "sha256": "3d0e91...", "commit": "1c9f0aa4f3e2...", "blob": "42dbd25dd307..."},
  "handoff": {"id": "H-10", "from": "S9", "to": "S8", "kind": "loop", "visit": 2},
  "commit": "1c9f0aa4f3e2..."
}

Delivery. Write the event to an append-only outbox in the assistant's state directory, beside the queue, and let a separate sender post it to POST /webhook/panel-stage-event. The measured webhook round trip is 848.3 ms, and the driver is synchronous; a direct POST inside the driver would put n8n's start-up on the stage's critical path. The outbox makes the event durable, replayable and non-blocking: if n8n is down, the sender retries and the stage still settles. A drop counter is the only new failure number a reader needs.

The flow. Webhook -> Code (validate and normalise) -> Respond to Webhook (200 with {ok:true}) -> Switch on event and decision.code -> sinks. Sinks worth having on day one: a chat or mail notification for a park, a daily digest of settles and parks, and an append to a metrics table. The POC proved the Webhook -> Code -> Respond chain with responseMode: responseNode; it did not prove that n8n continues downstream after the Respond node, so that behavior is an assumption to probe before the flow is relied on. If it does not continue, split the acknowledgement into a second webhook, or let the sender retry idempotently and record each attempt; the outbox is what makes the retry safe.

What it does not change. The stage run, the gate decision, the handoff pin and the route fingerprint are untouched. n8n's execution status is not a gate outcome; a failed notification is not a failed stage. This is the whole reason the option is first: it adds a reader of the record, not a second writer.

Payoff. A reader can see a park as a notification instead of a panel tab refresh; a daily digest can name the stages that parked and the codes that parked them; a metrics table can answer "how often does pipeline-artifact fire" without a log scrape. None of that needs a change to the model.

Cost basis. One file writer and one sender in the panel, one workflow with five to eight nodes, and tests for the event projection and the drop path. The POC's 19 calls are the transport evidence; the workflow create and publish costs (221.7 ms and 656.9 ms) are first-write numbers, not a running cost.

6.3 Option N2: a flow standing in for a stage

Ranks 2 and 3, in two shapes. The agent-mediated shape costs little and changes no schema; the native-executor shape costs more and is the one that truly replaces the worker. Both keep the stage record, the gate and the handoff in the panel.

N2a, agent-mediated (rank 2). The stage stays a normal stage with a prompt. The prompt tells the worker to call the flow's webhook with the stage's inputs and to write the flow's returned artifact into the tree, then commit it. The worker is still the stage's owner, so the stage run, the settle, the pin and the gate all work as they do today. The flow does the deterministic part: a build, a deploy, a fetch, a transform, a notification chain. The cost is one prompt template and one flow per stage; the risk is that the worker can skip or misreport the call, which the artifact check catches only if the artifact is real.

N2b, native executor (rank 3). Add an optional executor to a stage: {"kind":"n8n","workflowId":"...","webhookPath":"panel-stage-run","timeoutSeconds":900}. The driver starts the flow instead of an agent, passes the same inputs manifest, and receives an artifact pointer and an outcome. The driver records the stage run, verifies the artifact exists and hashes it, and writes the decision record. This is the shape that genuinely stands in for a stage, and it is the one that needs schema, driver and writer work.

The hard part is the artifact, not the call. The POC used no worktree mount in the n8n container and called nothing outside n8n, so a flow that writes a file into a tree is untested. Three ways to close it, in increasing cost: the flow returns the artifact content and the panel writes it through one route; the flow returns a path and a worker commits it; or the worktree is mounted into the container, which is a security and lifecycle decision, not a convenience. The first keeps one writer and is the one to prototype.

The pin still has to exist. A stage that produces an artifact must end with a commit on the stage branch, or the handoff has no commit and blob to pin. The current record can say uncommitted: true and the next stage is told, but the design's rule is a commit and a blob. A flow stage that only returns "success" has nothing to hand off and should park pipeline-artifact; that is the model working, not failing. The honest v1 scope for N2b is a stage whose artifact is a small JSON decision record, written through the panel and committed on the stage branch before the settle, not a stage that edits source files.

Gate fit. The flow may return outcome, but the panel writes the decision record and only routes on it when the gate declares routes. A flow that wants to approve or reject is a seat, not a decider; the document's gate and its routes map are what turn the outcome into an edge. This is the same rule the design already states for a human seat.

Payoff. Deterministic stages stop paying for a model turn: a build, a deploy, a poll, a translate. The stage record, the gate and the pin stay readable. The cost is the executor path and the artifact contract, which is why it ranks behind N1 even though it is the more exciting option.

6.4 Option N3: the whole pipeline in n8n

Do not build. Moving the pipeline into n8n would replace the stage record, the gate decision record, the inputs manifest, the pin and the park vocabulary with an execution graph. The panel would become a client of n8n's execution state, and the first question a reader asks after a park ("which gate, which artifact, which commit") would have no answer in the record. The POC proves n8n can run a flow; it does not prove n8n can be the panel's pipeline authority, and the existing model is the thing worth keeping.

6.6 What the proposal must never do

  • Never let an n8n execution status be a gate outcome. The gate's decision record is the record.
  • Never let a webhook call block a stage settle. The outbox exists for that; the measured 848.3 ms is the reason.
  • Never hand off an n8n execution id as an artifact. A handoff is a commit, a blob and a sha256, or it is nothing.
  • Never let a flow write a gate decision. A flow may write the artifact the gate reads; the panel writes the decision.
  • Never call the event fan-out a pipeline-fanout; that name already means per-stage trees.

7. What to build first

  1. Q1, the documents index. Choose the embedding source first, because it sets the collection's dimension and the ingestion script's model. Build the ingestion script and the POST /api/search/docs route. Acceptance: a query returns a report path, a line and an offset, the filter confines it to the chosen scope, and the answer names the commit it was built at. This is the smallest build with the clearest payoff, and the POC already proves its transport.
  2. N1, the stage event outbox and flow. Project the existing decision records into the event envelope, write them to an outbox, and send them to one workflow that notifies on parks and digests settles. Acceptance: a park produces a notification with its code and stage run id; n8n being down does not change the stage's settle time; the drop counter is visible.
  3. Q2, one worktree's code index. Index one live worktree at one commit, with the region markers and the path-line payload. Measure it against a fixed query set and grep on the same questions. Acceptance: the report says which queries semantic search won, which grep won, and what the index cost in chunks and embedding calls.
  4. N2a, then N2b for one small artifact stage. Start with the agent-mediated shape, because it needs no schema change and proves the flow's output contract. Only then add the native executor for a stage whose artifact is a small JSON record, written through the panel and committed by the settle.

The order is cost and payoff, not ambition: Q1 and N1 each add a reader of a record that already exists, Q2 adds a corpus, and N2b changes the executor path. The first two can run in parallel because they touch different services and neither changes the pipeline's authority.

8. Limits of this page

  • No POC was re-run. The numbers are the two reports' own records: one run each, one call each, no warm-up and no repetition. They describe those runs, not a benchmark.
  • No semantic quality claim. The Qdrant vectors are a documented hashed stand-in; the search proves the filter and the payload, not meaning.
  • No production n8n claim. One execution, one process, no queue mode, no workers, no restart. The webhook is unauthenticated and the endpoint is plain HTTP on loopback.
  • No integration was written. The panel has no Qdrant client, no embedding client, no search route and no n8n emitter. Every design here is a proposal with its cost named.
  • The captures are a snapshot. The live frames are from 08:38Z on 2026-11-09. The Qdrant collection count and the n8n execution count can move after that; the POC collection cannot come back without a write the brief forbids.
  • The corpus counts move with the tree. 154 Markdown files, 441 JavaScript files and 185,920 JavaScript and CSS lines are a read at origin/main 69c1aba; a later landing changes them.
