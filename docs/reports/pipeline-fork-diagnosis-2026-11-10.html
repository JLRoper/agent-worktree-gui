The fork that was drawn and never walked

Why the four-stage POC drive ran S220, S221 and S223 with no S222, and why a stage that is refused its input now settles refused instead of done. Measured 2026-11-10 on real trees, one tree per stage, driven by the real driveTaskPipelines.

The report in five lines

  • The document is not at fault: its four handoffs, two lanes and one join are a block fanOutOf reads correctly, with or without an isolation field.
  • The isolation MODE is not the cause either: the row already ran one tree per stage, which is the only thing a block needs.
  • The cause is the driver's fan-out gate. fanOutStateOf answered null for every pipeline that was not isolation: "per-stage", so the walk treated a drawn fork as a CHAIN and took the first edge out of S220 for ever.
  • Second defect, same shape: the terminal stage was handed one of the two artifacts it declares and started anyway, so the row read done over work it was never given.
  • Both are fixed: the drawn block is walked by the graph, and an input no run settled is refused, with the stage run settling refused.

What the drive showed before the fix

The document, as the POC wrote it: S220 forks into S221 (data records) and S222 (access records); S223 joins them and declares both as inputs. No isolation field. One row, driven pass by pass, every pass against real worktrees cut with the panel's own Jobs.makeWorktree.

ledger   S220#1 done · S221#1 done · S223#1 done
trees    S220, S221, S223            (three, not four)
S222     no entry, no tree, no commit
S223     inputs: a221 by edge h221 · a222 declared, no writer, no pin
row      done

That is the reported failure exactly: the lane is missing, the join takes the data records without the access records, and the row closes. What it did NOT do is refuse: with no pin to check, the start had nothing to check against, so S223 ran on half its inputs and settled done.

The diagnosis, and what it rules out

The document's crossings: correct

fanOutOf on this document answers a block: fork S220, lanes [S221, S222], join S223, base derived from the fork's settled commit. Nothing about the graph needed changing, and no edge was mis-declared. The same answer comes back whether or not the document writes isolation: the flag was never part of the shape.

The isolation mode: correct for this row

The row carried a round, so every stage already had its own tree - the only workspace fact a block needs. A per-stage document on the same row produced four stages and a 3-parent aggregate before this change and after it. The mode was not selecting the wrong walk; it was being asked a question it does not own.

The driver's fan-out gate: the cause

fanOutStateOf(pipeline, run) returned null unless isolationOf(pipeline) === "per-stage". With null, the walk is a chain: nextStageOf takes the first non-loop edge out of the fork's settled stage, so the second lane is never entered, no tree is cut for it, and the join downstream is reached by one lane's edge only. The bug is one boolean in the driver's plan derivation, and the loss is silent because a chain has no way to say "this stage had two inbound edges".

The fix, first rule. The graph decides the walk, and the row's workspace model decides whether it can be walked: a row that runs one tree per stage (a round) walks the block its document draws, and isolation: "per-stage" remains the way a record with no round gets that model. A record written before rounds keeps its one tree, where the lanes would share a directory - there the block is not walked, and the second rule catches what was dropped.

The second defect: a stage handed half its inputs settled done

The input manifest already resolved every declared entry, and it already recorded a222 as absent with no pin. Nothing read that fact at the start: the pin check ran on the ONE edge the row arrived by (h221), which resolved, so the stage started. The manifest was written on the run and then ignored.

The fix, second rule. Every entry the document declares is resolved before the start. An artifact with a declared path, which no settled run of the pipeline has produced and which the stage's own tree does not hold, is refused pipeline-refuse-input, and that stage run settles refused. A writer's own record - including one from before pins existed, which says present: true and nothing else - is still a claim about the artifact and is not a refusal.

Proof 2: a refused terminal input reads refused, not done

The same document on a row that cannot walk the block (a record written before rounds, one tree). Nothing in the code was special-cased for this row: the block is not walked, the access records are absent, and the new rule refuses.

ledger   S220#1 done · S221#1 done · S223#1 refused
decision pipeline-refuse-input, fact kind input, artifact a222 (out/access-records.json)
row      parked
reason   "stage S223 cannot start: it is handed a222 (out/access-records.json). No run of this
          pipeline has settled it, and this stage's tree does not hold it, so the row refuses the
          input and settles refused, not done"
worker   never started

Before the change the same row read: S223#1 done, row done, worker started. The difference is one word in the ledger and the whole verdict of the row.
