1. What was measured, and what was deliberately not

The console's corner is resized by a page gesture, not by the browser's native resizer: .out-grip sits in the console's own bottom-right corner and public/app.js owns the number. The size has one source of truth and one writer, so the protocol reads the size from that source and never from a picture:

  • stored: state.outHeights[id], the panel's own store, plus the same number in localStorage;
  • the writer's variable: --out-h on the console element, the one writer's output;
  • rendered: the element's border-box rect and its clientHeight (which is the rect minus the sheet's 1px border on each side, so a constant 2px is the box, not a defect);
  • the witness: the grip's own getBoundingClientRect().bottom, against the pointer's clientY. A size can be written perfectly while the corner the hand is on does not move, and only this number sees it.

Every case is driven on the live transcript at its foot, which is where a reader watching a live turn sits. The pointer is moved with real pointermove events (Playwright's mouse), the press goes through the grip's own hit band (3px inside the 18px corner), and the release is a real pointerup. Between cases the starting size is set through setOutHeight and recorded with rememberOutHeight, which is exactly the state a reader's panel is in after their last resize.

Reproducibility and honesty: one run of the gate is one dataset, and the live panel keeps streaming and polling while it runs. A snapshot that lands mid-case can replace a node (it did, once, in the run quoted here, in slow@1600/460), so a case can move between PASS and FAIL by one when the board is busy. The numbers below are one run, kept whole; the trace beside the gate carries every step of it.

4. Reading it: the size tracks, the corner does not

In slow@1600/140 the pointer travelled 60px, the box grew exactly 60px (140 to 200), the store recorded exactly 200 and the drawn box is exactly 200 - and the grip moved 0px. The hand ended 60px below the corner it was holding. Same numbers at 460: 60px of travel, 60px of growth, a 60px gap. The flick is worse in one step: 120px of travel, 120px of growth, a 120px gap.

That is the shape of the reader's report, and it is why a screenshot or a size check would have called this healthy: nothing is wrong with the number the drag writes. Something moves the box's top edge by exactly the amount the drag moves its bottom, so top + height - the corner - is constant. Here is the slow drag, step by step:

5. Cause 1: the browser's scroll anchoring on the transcript, anchored to the composer

The same slow drag, twice, at the same shape, with one difference: the transcript's overflow-anchor. The gate's --cause-check run:

anchoring auto -> grip moved 0px of 38px, box top -38px, transcript scrollTop +38px, JS writes 0
anchoring none  -> grip moved 38px of 38px, box top 0px, transcript scrollTop +0px, JS writes 0

With overflow-anchor: none on the transcript, the corner tracks the hand to the pixel. With it on, the corner does not move at all. The element whose viewport rect never moves while this happens is the composer block below the console: .as-subpane[data-subpane="chat"] > .job > .job-body > .reply { position: sticky; bottom: 0 } (public/style.css:6447). The transcript is a flex column scroller (public/style.css:6424), the console grows, the sticky composer stays where it is, and Chromium keeps the anchor it picked (the composer) still by scrolling the transcript by the growth.

This is the third loop over one box, and it is not the one the gesture stands down. The page's own tail pin already asks consoleHeld/cardBodyHeld (public/board/console.js:3661 and :3671), and compensateAnchor stands down while is-out-gripping (public/app.js:9340), but that one compensates the PAGE's scroll (window.scrollBy), not the transcript's own scrollTop. The sheet's two existing overflow-anchor: none rules (html at public/style.css:83, .job at :1231) do not reach this scroller: setting the property on .job-body itself is what stops it, and it has to be important to survive a card rebuild.

The gesture's own comment (public/app.js:10536, its own header comment; the invariant sentence is at :10549) states the invariant it believes it holds: "the box's TOP edge is read ONCE, at the press ... the top is the one edge of this box no other loop may move while the pointer is down". The measurement says that edge is moved, every step, by exactly the height written. public/style.css:1559 also says the anchoring must stay on, with a measurement behind it (the "above" case: a row landing in the turn above moves the box's top 86.25px when anchoring is disabled). Both statements are true, which is why the fix cannot be a blanket overflow-anchor: none for the gesture.

What would fix it, in the gesture's terms

Keep the frozen top as the invariant but measure it instead of assuming it. After each height write, read the console's top and correct the transcript's scrollTop by newTop - frozenTop through the existing setScroll writer: the browser's anchor may then do whatever it likes to content that arrives from elsewhere (the "above" case keeps its 86.25px protection, because that correction is the same measurement), while the gesture's own growth can no longer move the corner. The alternative - freeze the transcript's scrollTop outright while the pointer is down - costs the "above" case its protection, which the existing slow-drag gate measures.

6. Cause 2: a repaint replaces the node the hand is on

In interrupt-repaint@1600/460 the pointer travels 36px, the box grows for the first six moves (463px to 478px), and then the console node is replaced under the hand. The gate records the node's identity at every step: same, same, same, same, same, same, NEW, NEW, NEW, NEW, NEW, NEW. The rebuild came back at the stored size - the box ends at 460px, the store at 460, --out-h at 460px, the size the case started from - and the remaining six moves wrote into a detached node. The drag is lost, not merely jittery.

The repaint came from the panel's own live path. updateJob hands the change to renderConversation (public/render-jobs.js:1071), which asks outGripHoldsCard(el) before it replaces anything (public/render-jobs.js:1093) and stands down. The assistant's own renderer is the one with no hold question: renderAssistantChat does host.innerHTML = conversationHtml(conv) at public/assistant.js:2318, and it is what a snapshot reaches through applyAssistant. The same gap is visible in slow@1600/460 in this run: the node was replaced while the pointer was down, the size delta is 60px and the store and the box agree, but the node the reader was holding is gone. Four of the four interrupt-repaint cases replaced the node.

The state poll itself is not the culprit: interrupt-poll passes on node identity in every shape. resync() reaches renderConversation (held) and takes the assistant path only when the card's signature has moved; the artifact change is what makes it move, and that is what a streamed turn's snapshot does between lines.

7. Cause 3: the slack turn draws a height that is not the drag's

The console being dragged is in the last open turn, and that turn carries .turn.is-slack: public/style.css:6471-6474 makes the turn, its wrapper, its box and the console itself flex: 1 1 auto, so the console fills whatever room the pane has left. Above that room the drag's number is authoritative; below it the flex wins. From past-min:

shapepointerstored afterdrawn--out-hwhat the three numbers say

So a reader who shrinks the console to a sliver gets a box that will not go below the pane's leftover space, a --out-h of 20px that nothing draws, and a store that still holds the previous size. The three records disagree, and the one that decides a rebuild is the store.

8. Cause 4: a floor drag stores nothing

rememberOutHeight refuses any number at or below zero (public/app.js:695-700), and the release clamps to the sheet's min-height (0 in the docked pane). So the release asks setOutHeight(0), which also refuses (public/board/console.js:3756), and nothing is stored: the console keeps whatever --out-h the last successful move wrote. On the next rebuild the stored size wins, and the console jumps back to the size the reader had before they dragged it to the floor. Measured: --out-h 20px, drawn 105.41px, store 140px, in the same frame.

9. What passes, and what that says

  • no-move passes in all four shapes: a press and a double-click on the corner leave --out-h, the store and the box exactly as they were. The press's own setOutHeight(r.height) and the restored inline values do what the comment says.
  • past-max@1600/140 passes: the release clamp lands on the room under the box's top edge (360px drawn against a 360.22px room) and the store agrees with the box. Its 680px snap is the designed behaviour of applying the clamp once, at release, and it is reported here rather than failed.
  • interrupt-poll passes on node identity: a state poll does not rebuild the transcript. The rebuild in cause 2 needs the signature to move, which a streamed turn's snapshot does.
  • slow@820/140 passes, and it is the useful exception: at that width and start size the anchor the browser picks is no longer the composer, so the top edge stays. The defect needs the box's foot inside the scroller's view with the composer below it - the ordinary state of the docked pane at its foot.

10. Settle time and repaints: this is geometry, not timing

Every case settles in 0 ms: the release's clamp is written synchronously in the pointerup handler, and the box is at its final height on the next frame. Content repaints inside the console while the pointer is down are 0 in every settled case; the only rebuilds are the five replaced nodes (cause 2). There is no coalescing defect to chase either: the flick's height reaches the pointer's 120px in the same event, its failure is the same corner cancellation as the slow drag. What is left is a geometry loop, and it is visible only at the corner.

11. The gate

npm run verify:console-corner-drag
# or, against any panel:
node tools/verify-console-corner-drag.mjs --url http://127.0.0.1:7331
node tools/verify-console-corner-drag.mjs --json --trace trace.json      # one JSON object / every step
node tools/verify-console-corner-drag.mjs --cause-check                  # the anchoring A/B above
node tools/verify-console-corner-drag.mjs --widths 1600,820 --sizes 140,460

It starts no server and restarts nothing: it opens the panel in its own isolated context, waits for a console with a grip in the live chat pane, and runs the 32-case matrix. Each case asserts the three numbers the brief asks for - pointer delta against size delta, the corner against the pointer, the store against the drawn box - and exits 1 with the failing case names on the summary line. It also fails a case that never engaged the gesture (a press that misses the band), so a vacuous run cannot pass. Exit 2 means Playwright is absent and the browser half did not run.

At the time of writing it answers 25 failing of 32, and the failures are the defects above, not flake: the same cases fail on repeated runs, and the two that moved between runs (a passed slow case, a past-max case) moved because a snapshot landed inside them. Once the row that holds public/ lands the three changes below, the same command should answer PASS, and it will fail loudly again if any of them is undone.

12. What the row holding public/ and lib/ should change

This row measured only; it did not touch public/ or lib/, which another row holds. The causes above name files and lines; the changes are that row's to make, and the gate is here to judge them.

  1. The gesture keeps the box's top edge by measurement. After each setOutHeight in the pointermove, read the console's top and correct the transcript's scrollTop by the difference from the press-frozen top, through setScroll. One correction per move, and the same measurement covers the browser's anchor and any layout that arrives while the hand is down. Do not blanket-disable overflow-anchor: public/style.css:1559 keeps it for the turn-above case, and the correction keeps that case too.
  2. The assistant's renderer asks the gesture first. renderAssistantChat (public/assistant.js:2318) should ask outGripHoldsCard(host) before host.innerHTML = conversationHtml(conv) and defer through outGripDefer, exactly as renderConversation does at public/render-jobs.js:1093. A node the reader's hand is on must not be replaced by a snapshot.
  3. The slack turn must not inflate a console the reader has resized. Either the console's basis becomes authoritative once --out-h is set (drop flex: 1 1 auto on the console under .turn.is-slack when the variable exists), or the release stores the floor it actually reached. A reader who drags to the floor should get the floor, one number in the store, and a rebuild that restores it.
