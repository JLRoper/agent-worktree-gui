Terminal call rules and per-call timing

Implemented 2026-11-11 on branch wtgui/implement-the-row-in-this-tree-only-and-02f181, cut from main. The source report is docs/reports/terminal-call-latency-2026-11-11.html; this page records what changed and the numbers the tests returned.

Result: the worker brief and the project runbook now forbid sleep-polling a build inside one terminal call, forbid bash -lc where a direct binary will do, bound kubectl and curl timeouts at 8 to 10 s, leave the pre-execution guard alone, and name the current DNS failures. The run record now carries each completed tool call's duration and command preview. A test captured a real child process exactly: 447 ms for a measured 446.9 ms, and 656 ms for 656.0 ms in a later run.

2. Where the brief text comes from

TERMINAL_BRIEF is exported beside TESTING_BRIEF and DELIVER_BRIEF in lib/jobs.js, and is appended to every run that has a tree (anchorCwd !== false). The assistant's own turn has no tree and is not given it. The paragraph is unconditional for a tree run: every worker runs commands, not only the ones that run tests.

The runbook copy lives in docs/runbooks/email-multi.md under ## Testing, and docs/runbooks/README.md now tells the next runbook author to carry the same rules. The brief and the runbook quote the same numbers so a worker cannot be told two different costs.

3. The timing record

tool.started stores the call's one-line preview with the in-flight entry. tool.completed matches it, takes the gateway's duration (seconds) and records whole milliseconds, with the wall-clock delta as the fallback when no duration is sent. The entry is written into the job, persisted to jobs.json, and returned by summary() on /api/jobs.

An earlier run recorded 405 ms for a real 405.1 ms child process. The number follows the machine and the load, not a fixture constant.

5. Not done, and why

  • No live Jenkins or k3s round trip. Both hosts still fail DNS from this machine, so the report's failure cost (0.4 to 0.6 s) is what can be measured honestly; a successful live read was not invented.
  • No push and no pull request. The row said stop at the commit, and that line was treated as the push decision. Nothing was pushed.
  • terminal_tool.py was not edited. The guard is sub-millisecond in steady state and its 30 s is a fail-closed ceiling; the brief and runbook say so explicitly.
