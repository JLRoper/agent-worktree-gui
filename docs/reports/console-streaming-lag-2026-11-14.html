Console streaming lag: every cause, measured

agent-worktree-gui, branch wtgui/console-streaming-lag-measure-and-name-ad41c8 at 101cf6aa, against tag v1.99.1. Headless Chromium, 1440x900, one long streaming turn. No shipped file changed in this run.

Verdict. On this fixture the console does not miss a frame: zero long tasks, zero frame gaps over 50 ms, and a delta reaches paint in 7.4 ms at p50 and 13.3 ms at p90, on both builds. The main thread is busy 21.6% of a 24 s window and idle the rest.

The lag is not throughput, it is layout and repetition: 9.7% of that busy time is layout and style, the scroll anchor forces a layout of the whole 325-line console on every frame (661.06 ms of self time charged to a two-line callback), and a 1 Hz sweep redraws all 325 lines (12318 drawJobLine calls in 24 s) so every tool row, and the clock's own span, is destroyed and rebuilt on a page that is otherwise sitting still.

Against v1.99.1, at an identical 193-line window: script 17.6%, layout 19.2%, busy 21.8%. The badge behaves identically on both: it is old behaviour, not a regression.

1. What was measured, and how

A panel of its own from each tree (spare port, its own PANEL_CONFIG, HERMES_HOME and jobs file, no API_SERVER_KEY), a stub Runs API that plays a real SSE turn, and one card spawned through the panel's own POST /api/agents with existing: true. The one-stream console key (wtgui.stream.<thread>) is written before the spawn, so the card is built as a stream, not repainted into one.

Fixture
20 prose/call/result rounds (10-line results), 4 command lines, one 120-line markdown reply, then the measured windows: a 20-row tool history in a full 300-line console window, 1687 px of content in a 318 px box.
Stream
one text delta every 25 ms (the panel's own 120 ms coalescing turns that into about 26 frames a second), a tool call every 2 s with its result 1.4 s later, and one five-call parallel burst - all pushed by --control calls, so a window boundary is a fact rather than a guess about a timer's phase.
Windows
silence (3 s, wire quiet) -> metrics (24 s) -> badge (721 frames of one in-flight call, crossing 9 s to 10 s and the swap to its duration).
Instruments
CDP Performance.getMetrics and a Profiler CPU profile sized to the window; PerformanceObserver long tasks plus a requestAnimationFrame heartbeat; the page's own functions wrapped for calls and inclusive time; a MutationObserver on the console; and the app's own EventSource listeners timed from frame arrival to the next animation frame.

The page probe never reads geometry in the metrics window, so the browser's own LayoutCount is the page's, not the harness's. The badge window is separate because its per-frame getBoundingClientRect IS a forced layout.

3. Ranked causes

1The scroll anchor forces a layout of the whole console, every frame

Where
public/board/console.js:1967 (the rAF), :1974 (setScroll(out, out.scrollHeight)), public/board/console.js:3024 (setScroll), callers stickSoon at :1955
Measured
661.06 ms of self time for the callback at console.js:1967 - the largest page frame in the profile, 15.8% of every sampled busy millisecond. stickSoon was called 12757 times in 24 s; the callback runs at most once per frame.
Why
out.scrollHeight is read after the content changed, so the browser must lay out the 325-line box before it can answer; the write to scrollTop then invalidates paint. Two statements, one full layout, on the frame after every growth.
Fix
Keep the read, drop the cost: anchor on overflow-anchor plus a single ResizeObserver on the console's content, and stick with el.scrollTop = el.scrollHeight only when the content height actually changed (cache the last value per console). A console that grew by one 18 px line does not need the geometry of 1687 px recomputed 60 times a second. If the anchor must stay a rAF, read the height inside it once per frame per console (it already batches) and skip the read when the last write put the box at the bottom and nothing was added.

2The 1 Hz sweep rebuilds the whole window and redraws every line

Where
public/app.js:1783 region (sweepThinking) -> public/board/console.js:2325 (paintStreamConsole) -> loadThinking -> streamBodyHtml at :2015 -> drawJobLine at :3488
Measured
16 full window builds (one per sweep) and 12318 drawJobLine calls in 24 s - 769.9 per build - for an inclusive 1306.3 ms. 3660 nodes added and 2179 removed inside the console in the same window (243.3/s).
Why
Every sweep re-renders every piece into a detached holder and then replaces the pieces that are not isEqualNode to what is on screen. The growing line and the busy row are never equal, so the tail is replaced; the sweep also re-enters drawJobLine for lines that did not change at all.
Fix
Make the store's own append path the only painter while a turn streams: recordJobLine already draws the line it changed (:3446). The sweep exists for text the panel did not see arrive; gate it on a version counter the store bumps, and skip the whole rebuild when the counter did not move. When it does, diff by data-lid and patch the changed row instead of rebuilding the piece list.

3paintToBottom reads the geometry of two boxes on every paint

Where
public/board/console.js:1160, reads at :1169 and :1170, write at :1174
Measured
286 calls, 109.4 ms inclusive, and 98.16 ms of self time in the profile - scrollHeight and clientHeight on the console AND on the card body, twice each, then a classList write that invalidates style for the next frame.
Fix
Compute the answer from the scroll event the reader actually caused (scroll already tells you the offset, and the box's own height is cached until a resize), and only call it from a scroll or resize, not from the paint path that fires per line.

4Selector matching inside the per-line draw

Where
public/board/console.js:3488 (drawJobLine), its querySelector(":scope > [data-wait]") at :3524, and the helpers it calls
Measured
437.41 ms of self time in querySelector and 12318 calls - a selector evaluation per line per sweep. This is the browser's matcher, charged to the page, and it is the second largest single frame in the profile.
Fix
Hold the row's own children by reference at build time (the row is created here) instead of querying back into it, or query the parent once per build and index the rows by data-lid.

5The tool row's clock is a new node on every paint, in a slot that changes width

Where
public/board/console.js:822 (grouped rows) and :1045 (flat rows) build <span class="jl-live tgrp-state" data-live-from>; the finished branch swaps to <span class="tgrp-state">{secs}s at :824 and :1043; tickLiveClocks patches it between paints at public/app.js:1784; the job loop is public/app.js:12155-12186
Measured
24 clock ticks and 171 badge spans added and 171 removed in 24 s (span.jl-live in the mutation record) - one destroyed and rebuilt per tool-row paint, 171 mutations inside tool groups. Over a 12 s call the badge node was replaced 1 time(s) while its text was patched 12 times.
Why
Every sweep's row HTML carries the clock, so the row's identity, not its text, is what changes. Then the text is patched in place between sweeps. That is two mechanisms for one number, and the node is destroyed by one of them.
Fix
See section 4: one stable node per row, created with the row, never re-created, with the clock and the duration written into a fixed-width slot.

6The command-fold marker measures text with a Range binary search, from a page-wide observer

Where
public/board/console.js:2793 (paintCommandFoldMark), :2804-2805 (clientWidth, clientHeight), :2814 (getBoundingClientRect), :2747-2765 (cmdCutOffset, a binary search of Range.getBoundingClientRect), :2786 (body.innerHTML = html), :2847 (ResizeObserver), :2876-2885 (the observer that calls scheduleCommandFoldMark for every added element)
Measured
1.7 ms per mark (max 2.6 ms over 8 runs), 32 layout-forcing Range reads for 4 text nodes, and 358 schedules in 24 s of streaming. Absent from v1.99.1 entirely.
Why
Each mark is: restore the whole body's innerHTML, read three heights, walk every text node, and binary-search each one for the row where the text stops, then cut the tree and insert the dots. The restore is itself a DOM write, so the next mark's first read is a forced layout - and the observer that ordered the mark wakes on the nodes the restore added.
Fix
Mark once per card and never clear-and-remeasure in the same paint: cache the cut offset keyed by (card, width, text length), skip the binary search when none of the three moved, and drop the innerHTML round-trip in favour of storing the removed nodes. The ResizeObserver can then be one observer on the console, not one target per card.

7The type-stream keeps painting after the wire stops

Where
public/core/type-stream.js:234 (feed), public/board/console.js:2166 (paintTypedLines), timer registered at public/app.js:12039 (400 ms)
Measured
With the wire silent for 3 s: 67 paintTypedLines calls, 69 drawRowText calls, 67 layouts, 389 ms busy. The 400 ms timer alone cost 44.7 ms over 60 calls in the measured window.
Why
Paced reveal is deliberate, and it means the console carries a repaint queue of its own on top of the wire. Under a burst the two multiply: the wire keeps appending while the pacer is still revealing what arrived a second ago.
Fix
Cap the backlog: when the pacer is more than one frame behind the wire, jump to the newest text instead of pacing through it (the reader cannot read a second-old reveal anyway), and stop the 400 ms timer when the pacer's queue is empty.

8DOM churn: whole pieces replaced instead of patched

Where
public/board/console.js:2373 (syncStreamConsole, the replace loop)
Measured
3660 nodes added / 2179 removed per 24 s (243.3/s), by target: pre.job-out 3336 added, span.jl-live 171 added / 171 removed.
Fix
Falls out of cause 2: a diff by data-lid that patches text and class keeps node identity, which is also what makes the badge fix in section 4 possible.

So the brief's reading is right in substance and needs one correction in detail: the badge does not move on every streamed repaint - it is replaced on every repaint, its text is patched between them, and its width changes only where the digit count does (9 s to 10 s) and at the swap to the duration, where the row's target jumps by 50.59 px. Three separate mechanisms, one number.

The proposal: one stable node per row, patched in place, in a fixed-width slot

  1. Build the slot once. Every tool row carries <span class="tgrp-state" data-tgrp-clock></span> from its first paint, empty for a row that never ran and re-used for every state after that. No branch may emit a second span, and no rebuild may replace the row while it is live (cause 8's diff is what makes that possible).
  2. Write text, never HTML. One function owns the slot: clockEl.textContent = live ? liveSuffix(from) : secs.toFixed(2) + "s". The per-second tick and the completion swap call the same function on the same node, so the swap is a text write, not a node replacement.
  3. Fix the slot's geometry. .tgrp-state { min-width: 5.6ch; text-align: right; font-variant-numeric: tabular-nums; } - tabular-nums makes every digit the same width, and the min-width covers the widest text either state can produce (102.70s), so 1s, 10s and 42.70s all occupy the same box. Measured, the font is already tabular in the numbers it draws (82.2 px for every one-digit second), which is why the slot only needs the min-width and the alignment to be still.
  4. Keep the reader's row. The clock's data-live-from must survive a sweep: put it on the row, not the span, so tickLiveClocks finds the row and patches its slot after any repaint instead of the repaint re-creating the span.

With that, the row's geometry is constant for the life of the row: no width change at 9 s, none at the swap, and the target's truncation window does not move while the turn writes. The measured 50.59 px jump and the 1 node replacement per call are the numbers this removes.

5. What changed since v1.99.1

git log v1.99.1..HEAD over the five console files is one commit: 101cf6aa "console: mark a folded command card's last row, and make its spacing the reader's", 421 insertions and 24 deletions across public/app.js, public/board/console.js, public/core/assistant-command.js, public/index.html and public/style.css. Everything else on the delta path is older than the tag.

  • New: paintCommandFoldMark, clearCommandFoldMark, cmdCutOffset, scheduleCommandFoldMark, cmdFoldResize (console.js:2747-2885) - cause 6, and the only code that reads text geometry per card.
  • New: scheduleCommandFoldMark on every element the copy observer sees (console.js:2883) - 358 calls in 24 s of streaming, all doing a subtree querySelectorAll.
  • Changed: spacing ownership in style.css and the last-row marker, which is why the two builds draw a different number of lines from the same events.
  • Unchanged: the scroll anchor, the sweep, paintToBottom, and the badge. The controlled pair shows them cost the same as they did at the tag - the badge identically so.

So the regression since the tag is real but small (script 17.6% per identical window) and it is the fold marker, not the streaming path. The streaming path's cost is old, and it is causes 1 to 5.

6. Limits of this measurement

  • No command card reached the turn: the card path needs a frame this stub does not install, so cause 6 was measured on a card built to .code-box.is-cmd's own shape inside the console, not on one the app produced. It is a per-mark cost, not a per-turn frequency.
  • One card on the board. The board-side cost of a redraw (every card, every scan) is outside these windows and would only add to causes 2 and 3.
  • Headless Chromium at deviceScaleFactor 1 on a fast host: these are lower bounds for a laptop on a 4K display, and the ratios are what travel, not the absolute milliseconds.
  • No delta was ever delayed by more than 17.4 ms, in either build. Whatever a reader experiences as "lag" at this scale is not the primary thread failing to keep up with the wire; the profile says it is the console doing work between deltas that a still page would not do.
