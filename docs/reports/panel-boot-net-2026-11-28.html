1. What the brief counted, and what this audit counts

The brief's line is "46 of the 64 panel-booting test files call startPanel more often than they register a t.after stop hook". The file count reproduces exactly: 64 files in test/*.test.js start a panel. The 46 does not, and the reason is the counting rule rather than a disagreement about the defect. Counted as the literal one-line pattern t.after(() => panel.stop()), this tree has 48 files over their hook count; counted by each hook's body (which is what a hook does, and the only thing that matters to the runner), it is 27, because these files write hooks in several shapes:

t.after(async () => { await first.stop(); if (second) await second.stop(); });   // two panels, one hook
t.after(() => homey.stop());                                                    // not named "panel"
try { ... } finally { await panel.stop(); }                                     // a stop that is not a hook at all

tools/panel-boot-audit.mjs counts a boot as a startPanel( or kit boot( call site and a hook as any t.after(...) whose body calls .stop(, with comments and strings masked out first. Run with --root against a git archive, it is the "before" column of every table here. Two trees matter: this branch's own cut, and the turnover head it was merged against at the end.

Two notes on that count, because both change which files go first. A file with more hooks than boots (2 boots, 6 hooks) exists: a test that stops a panel twice writes the hook twice. And a file with as many hooks as boots is not safe: a hook at the foot of a test body is only reached if nothing throws before it, which is exactly the throw row 569 measured. That is why boot() is the cure and a hook count is only the ranking.

2. The net, in the kit

Two pieces, and the first is the one that cannot fail. boot() is startPanel() plus a per-file registry, plus an unref() of the child and its three pipes; the unref is what stops a panel from holding the worker's event loop open, so the file reaches its end whatever any hook does, and a stranded child sees its stdin close and shuts itself down (PANEL_PARENT_WATCH_STDIN). stopBootedPanels() is the graceful stop: it stops whatever is still registered, newest first, and a panel whose own stop() succeeded leaves the registry so the sweep never touches it twice. The file registers it once, at module scope, as after(stopBootedPanels).

// tools/panel-testkit.mjs:279
export async function boot(options = {}) {
  const panel = registered(await startPanel(options));
  bootedPanels.add(panel);
  // The belt under the net: a panel that outlives its sweep must still not be able to hold the worker open.
  panel.unref();
  return panel;
}

// tools/panel-testkit.mjs:210 - what unref() does
unref() {
  child.unref();
  for (const stream of [child.stdin, child.stdout, child.stderr]) stream?.unref?.();
}

// and the file's one line, at module scope:
after(stopBootedPanels);

startPanel() stays exported and stays ref'd: the tools/verify-*.mjs harnesses are one-shot programs that stop their own panel and exit, and tools/panel-boot-proof.mjs --before relies on a startPanel child holding the loop to show the stall.

3. Why the hook is the graceful path and not the guarantee

Three measurements on Node v26.3.0 decided the shape of this, and the first two are why the unref exists.

A hook registered inside a running test belongs to that test. A two-test probe whose first test boots a child and installs the hook, and whose second boots one and throws, printed the sweep after the first test with kids=1 and then hung until the cap:

test("one boots a child", () => { bootChild(); install(); });
test("two boots a child and throws", () => { bootChild(); throw new Error("boom"); });
HOOK at file end, kids=1        <- ran at the end of test ONE
node --test exit=124 (20 s cap)

A hook registered while a module is being loaded does not reliably belong to the file's root test either. test/waves-write.test.js boots its panel at module scope after a preamble of fixtures, then declares its tests. A hook registered while the kit was imported ran 2.3 s before that first boot, with the registry empty; the same call written in the file's own body ran at the same wrong moment. The debug trace that named it:

TESTKIT SWEEP pid=50016 argv1=...test/.panel-boot-proof-waves-write.test.js ctx=child-v8 t=...665692 panels=0
TESTKIT BOOT  pid=50016 ... t=...667955 child=44028
TESTKIT BOOT  pid=50016 ... t=...671314 child=35788
# the first sweep ran 2.3 s BEFORE the first boot - and swept nothing

A sweep on beforeExit is no better. It was tried as the always-fires path, and it fires wherever the loop drains: with an unref'd child, that can be between two awaits inside one test. It showed up as test/panel-testkit-boot.test.js failing its own assertion - a panel a test was still using had been swept - and was removed rather than tuned.

So the hook is the graceful stop and the unref is the cure. Both directions were then measured on the same bytes. A copy of test/waves-write.test.js - the file whose hook fires early - with its sweep line removed and a boot that throws appended still exits in 8 s:

$ grep -v '^after(stopBootedPanels);$' test/waves-write.test.js > test/.no-sweep-waves-write.test.js
$ timeout 60 node --test test/.no-sweep-waves-write.test.js; echo EXIT=$?
EXIT=1 in 8s: tests 23, pass 22, fail 1 (the injected throw)

And test/panel-testkit-boot.test.js pins what a test can see of the registry: a panel joins, a test's own stop() takes it out, one sweep stops the rest and the port goes quiet.

The 65th file is this branch's own test/panel-testkit-boot.test.js, which boots panels to prove the registry; the 36 are the tail.

Those 36 are the tail the brief ranked after the ones with a gap: each registers a t.after stop hook for every boot it makes, so the throw has to land in the two lines between the boot and its hook to strand anything, and most of them hook on the line after the boot. They are not converted here, and the report says so rather than implying the folder is done. The gate that keeps the measured set at zero is npm run verify:panel-boot (tools/panel-boot-audit.mjs --fail): it exits 1 and names the files while any panel-booting file is off boot() with more boots than hooks, and it stays green through a conversion because boot() is what it looks for.
