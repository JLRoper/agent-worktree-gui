1. What moved, and what stayed

The brief was one cut: take the view half out of lib/waves.js into lib/wave-views.js, a pure move, with lib/waves.js keeping the re-export of every name its importers read. Nothing schedules, advances or switches anything in either file; the cut is a file boundary, not a behaviour change.

What went to the new file, with the ballast it needs:

  • lib/wave-views.js:46 waveMemberKey, the key an evidence map finds a member by;
  • lib/wave-views.js:52 abandonedOf, the member's named abandonment as the lane draws it (module-private before and after the cut);
  • lib/wave-views.js:72 taskWithOwner, the assistant a queue row came from stamped onto the row;
  • lib/wave-views.js:84 waveMember, one task row as a member;
  • lib/wave-views.js:129 waveView, one wave with its members, its derived state, its two gate answers and its lanes;
  • lib/wave-views.js:180 currentWaveId, the lowest-position running, ready, else unentered wave;
  • lib/wave-views.js:201 waveLane, one initiative's whole lane, with the auto switch's answer riding on each view.

Two helpers travelled because the moved code asks them and the store asks them too: lib/wave-views.js:30 isObject and :35 noneGate. They were module-private in lib/waves.js, so they are exported by the new file and imported back at lib/waves.js:79; they are not re-exported and were not on the module's surface before the cut. This is the direction row 509 used for clip, namedAbandon and text.

What stayed: the record and its write door (pickWaveGate at lib/waves.js:171, pickWave at :235, waveIdFrom at :300), the store (Waves at :315), the gate read (readWaveGate at :948), the state fold (deriveWaveState at :1087) and the auto switch (waveAutoOpens at :1231). Those are the state and storage half, and the point of the cut is that a change to what a lane draws and a change to what the store keeps now land in different files.

4. The two modules import each other, and both orders were run

This cut cannot be one-way the way row 509's was. The views need the state fold, the gate read and the caps, which stay in lib/waves.js; the store needs the two helpers, which moved here. So lib/waves.js imports ./wave-views.js and lib/wave-views.js imports ./waves.js.

The cycle is inert because neither module reads the other's bindings while a module is being evaluated: the only cross-module reads are inside function bodies, after a caller has loaded both. That was run, not assumed. A probe folded the same two-wave lane through the public module twice, once with lib/waves.js imported first and once with lib/wave-views.js first:

$ node import-order-probe.mjs waves   # lib/waves.js first
$ node import-order-probe.mjs views   # lib/wave-views.js first
{"waves":[{"id":"w1","state":"done","autoOpen":false},{"id":"w2","state":"ready","autoOpen":true}],
 "currentId":"w2","memberKey":"1@c:/t/a","sameView":true}

Both orders answered the same lane, the same states, the same auto switch, the same current wave and the same member key. The only differences in the two runs were the probe's own first label and that module's export list.
