1. What a push meets, and what a lift is

A cut writes one record into the branch-parents book, keyed by the tree's six hex tag: { parent, branch, tree, at, kind, lifted?, preLiftedBy? }. One kind is local only by definition: research, cut from the project's main parent. treeKindRefusal (lib/push-permissions.js:88) answers with a refusal for a research record that is not lifted, and RemoteWrites.decision returns it first: before the policy, before the push controls, before the landing mark, before any grant (lib/remote-writes.js:145). A push from an unlifted research tree is therefore not asked about and not granted - it is refused, and the sentence names the tree and the kind.

The lift is one boolean on that record. POST /api/worktree/kind-lift calls jobs.liftKind (lib/jobs.js:3252), which rewrites the record with lifted: true and leaves the kind alone. Nothing else moves: the push guard's policy and controls are untouched, and the worker's landing paragraph is untouched. After a lift the push falls through to the ordinary decision - the project's policy, the two branch controls, the permission box - exactly as it would for a turnover child with no lift needed.

So the state a queue row wants at the cut is the state a person reaches by pressing Lift. This change reaches it at the cut instead of after the first refusal.

3. The change

One input decides it: the SPAWN line named a task id. assistantSpawnRun reads it once (lib/features/spawn.js:214) and, only on the branch that CUTS a new tree, adds two fields to the same jobs.create it always called (lib/features/spawn.js:379):

...(rowId ? { landing: true, preLiftedBy: `row ${rowId}` } : {}),

landing: true is the mechanism that already existed and had no caller on this path. At the cut, makeWorktree writes the record lifted (lib/jobs.js:3152, 3154) and made.localOnly false (lib/jobs.js:3156), which is precisely the pre-lifted research record the brief describes. preLiftedBy is the new fact: rememberParent writes it only on a lifted record (lib/jobs.js:3219), and loadParents reads it back beside rec.lifted (lib/jobs.js:3181), so a restart keeps the reason as well as the flag.

What the SPAWN does NOT get is the other half of landing: true. In this panel that flag also means "a run started to LAND": the merge flow's trees are marked that way, their guard allows a push outright (server.js:1343, lib/remote-writes.js:153), and their brief is the blanket WILL LAND paragraph (lib/jobs.js:4089). A row pre-lift is the record only:

  • the guard is installed with landing: false (lib/jobs.js:3971), so the push meets the project's policy and its two branch controls, the ordinary decision - the same thing a hand lift leaves behind;
  • the worker keeps the parent's own LANDING paragraph (lib/jobs.js:4089), which is the only one that knows whether the project has a turnover branch and what its push policy is. A blanket WILL LAND on a turnover project would tell a worker to push a new remote branch, which the turnover doctrine forbids.

That is the one judgement this branch makes beyond the brief, and it is the reason the code separates cutPreLiftedBy (the record) from landing (the run) in jobs.create. The cut is still made with landing: true; only its two run-level meanings are withheld because a pre-lift is not a merge run.

The boundary the vocabulary keeps

A row SPAWN cut from a turnover branch is a turnover child: not local only, so there is nothing to lift, and the record stays kind: "turnover" with no lifted and no preLiftedBy (pinned by the fourth test). No third kind was added; BRANCH_KINDS and KIND_LABELS are untouched, and the verdict cell that draws them is not edited.

What the record looks like

// a SPAWN that carried row 186, cut from main
{ "parent":"main", "branch":"wtgui/...", "tree":"/.worktrees/...", "at":"...",
  "kind":"research", "lifted":true, "preLiftedBy":"row 186" }

// the same tree lifted by a person (POST /api/worktree/kind-lift)
{ "parent":"main", ..., "kind":"research", "lifted":true }

// a tree cut by hand, or a SPAWN that named no row
{ "parent":"main", ..., "kind":"research" }

// a row SPAWN cut from a turnover branch
{ "parent":"20261121_1200_ROPER-186_demo", ..., "kind":"turnover" }

The row carries the same fact for a surface that has no book in hand: branchKindPreLiftedBy is stamped beside branchKindLifted by applyTreeKind (server.js:3862) and returned by the lift route (server.js:5514). It is null unless a row pre-lifted the record, so a page or a later agent can say "lifted, because row 186" instead of only "lifted".

4. Tests

test/spawn-row-prelift.test.js drives the real assistant spawn path (startSpawn), the real spawner (assistantSpawnRun), the real Jobs.create/makeWorktree and a real repository; a stub gateway only accepts the run and ends it. Four tests:

  • row cut: a SPAWN carrying a queue row writes kind research, lifted: true, preLiftedBy: "row N", reads it back through loadParents and the file, installs the guard with landing: false, and still hands the worker the parent's paragraph (not WILL LAND);
  • no-row cut: the same path with no task id writes research, unlifted, no preLiftedBy, guard landing: false;
  • hand cut: jobs.create with no landing flag stays unlifted, a person's liftKind adds lifted and no row, and makeWorktree with landing: true, preLiftedBy returns localOnly: false while a plain cut returns localOnly: true;
  • turnover parent: a row SPAWN cut from a turnover branch records a turnover child, never lifted, and its worker is told to roll up locally.

Focused run while working: the new file's 4 tests pass, and 47 tests pass across the seven files that already pin this machinery (branch-kind, spawn-stage-landing, spawn-from, spawn-queue-link, spawn-busy, human-kinds, spawn-cards), plus node tools/verify-branch-kind.mjs with 57 checks and 0 failed.

The full sweep is reported as it happened, because it did not reach its summary. npm test was run once and printed 1,485 passes and 8 failures, then stopped producing output for 14 minutes with six heavy files still in flight (a sibling tree was running its own suite at the same time); it was cancelled at the 20 minute limit this project's worker briefs set. The eight failing files were re-run on their own: three pass alone (assistant-carry-key, assistant-to-replay, child-tree), and the other five fail identically on a clean git archive main tree, so none is this change:

  • assistant-profile - "the whitelists are gone from the profile, the payloads, the page and the route";
  • assistant-search-scroll - "the keyboard step scrolls the popover, not the transcript";
  • child-route - "the child route cuts from the row's branch, records the cut, and hands the rollup a rollable child";
  • gateway-permissions - the file itself, because it starts server.js in a worktree that has no config.json (ENOENT on config.json, measured on both trees);
  • header-controls - "the moved control keeps its handler: one press closes the stream, the next reconnects".

5. What is not changed

  • SPAWN IN cuts nothing, so it writes no record and lifts nothing: an existing tree's kind is the one it was cut with.
  • A tree cut by hand, and a SPAWN that names no task, are untouched: research, local only, lifted only by a person.
  • A turnover child is untouched: it was never local only.
  • The two kinds, their labels and the verdict cell that draws them are untouched; another live run is rewriting that cell.
