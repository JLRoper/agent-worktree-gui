A failing initiatives read backs off to one request a minute

The pane's stale read is re-armed from its own render and from a four-second timer, and neither looked at whether the last read FAILED. A broken store was therefore asked again on every repaint, and each failure's own repaint started the next read: row 275's worker counted 114 GET /api/initiatives in one sample window. This page is the measurement of the fix: the same instrument, the same forced failure, the same 62 s window, and the same pane - 144 GETs on the base, 4 on the fix, with Refresh still answering at once and a recovered read back on the ordinary four-second gap.

1The loop, in three lines of code

The row named the mechanism: the stale read is re-armed after every render, and a failure never moves the clock it is measured against.

renderAssistantInitiatives re-armed the read on the base (public/assistant.js:4173, now public/assistant.js:4231): 

if (!initDoc && !initLoading && !initErr) void loadInitiatives();
else if (initDoc && !initLoading && Date.now() - initReadAt > INIT_READ_GAP_MS) void loadInitiatives();

initReadAt is written in exactly one place, the success branch of loadInitiatives. A FAILED read leaves it where it was, so Date.now() - initReadAt stays above the four-second gap for the rest of the failure, and the render's second branch is true on every repaint. The repaint is guaranteed: the read's own .finally() calls renderAssistantInitiatives() (public/assistant.js:3579). Read fails, repaint, read again - bounded only by the request's own round trip, not by the gap. That is how one pane issued 114 GETs in a window while the store answered 500.

A failing read is also the expensive case: row 267's cut made a good read cheap (536 ms cold, 62 ms for a lane), but the failing path never gets the fast answer, because there is no answer. The count is the whole cost.

2The wait, and the three places that check it

The healthy gap is untouched: INIT_READ_GAP_MS is still 4000 (public/assistant.js:3490). The backoff is a floor over it and only exists after a failure.

const INIT_READ_GAP_MS = 4000;
const INIT_BACKOFF_BASE_MS = 8000;   // the wait after the FIRST failure
const INIT_BACKOFF_CAP_MS = 60000;   // the ceiling: a broken store costs one request a minute
let initFailCount = 0;               // consecutive failed reads; 0 while the store answers
let initRetryAt = 0;                 // no automatic read before this instant (0 = not backing off)
let initRetryWaitMs = 0;             // the wait the last failure scheduled, drawn in the reason line

function initBackoffMs(n) {
  return Math.min(INIT_BACKOFF_CAP_MS, INIT_BACKOFF_BASE_MS * 2 ** Math.max(0, n - 1));
}
const initHeld = () => initRetryAt > Date.now();

public/assistant.js:3490-3515. The doubling is the shape lib/held-replies.js already uses, with this pane's own ceiling.

The wait is checked three times, because any one of the three alone is the loop again:

WhereWhat it doesLine
the read itselfAn automatic attempt inside the wait returns without a request. force skips only this check.3546
the render's stale readThe re-arm that caused the loop now also requires !initHeld(), so a repaint during the wait starts nothing.4231
the timerRe-arms at max(gap, initRetryAt - now), so a held pane is asked when its wait ends, not four seconds after it.4075

A failure sets all three fields together (public/assistant.js:3570-3572), and a read that answers clears them together (public/assistant.js:3559-3561) - so a recovery is back on the four-second gap on the very next read, not slow for the rest of the session. A write's own document is the store answering too, so adoptInitiatives clears them the same way (public/assistant.js:3599-3601).

What the reader sees

The meta line keeps its prefix, its class and its place - read failed: <reason> is the text the zero-shift gate asserts - and the failure now carries why the pane is waiting and which control does not wait: 

<span class="as-hint init-read">read failed: ${esc(initErr)}${esc(initRetryReason())}</span>

read failed: the store could not be read (forced by tools/verify-initiatives-read-backoff.mjs) - retrying in 8s; Refresh reads now

public/assistant.js:4297 and 3520-3523. A sentence about the schedule, not a countdown: it changes when the wait does, so the pane's markup stands still between attempts and a poll does not rebuild the list under the reader.

Refresh and Try again are the same control (data-init-refresh), and it now asks at once (public/assistant.js:4806-4815): the press clears the document and calls loadInitiatives({ force: true }). Every read that follows a write is forced for the same reason - the write just proved the server answers (public/assistant.js:4541, 4559, 4582, 4676, 4892).

What is proved

A broken store costs 4 requests in the first minute instead of 144, the first failure still speaks, the reason says what the wait is and that Refresh does not wait, the press answers in 31 ms while the pane is naming a 60 s wait, and a recovered read is back on 4.0 s gaps in the same 16 s window it measured before the failure. The healthy path is identical on both arms (4 GETs per 16 s).

4Why the base arm is 144 and not the row's 114

The count is the instrument's, and the instrument has a delay in it. Row 275 measured with an instant 500, which lets the page loop as fast as the browser can round-trip; this gate holds each 500 for 400 ms, the same delay tools/verify-init-read-zero-shift.mjs uses so its own samples are not taken inside a spinning page. The delay is identical in both arms, so the comparison is exact; the base's 144 in 62 s (about 2.3 a second) and the finding's 114 in its window are the same loop at two sampling rates. The number that matters for the row is the one a reader would suffer: 144 asks against a store that is already saying no.

6Found on the way, and changed with it

  • The base stops retrying when it has no document. Its press clears initDoc, a failing read then leaves initErr set with no document, and the base's two re-arm branches both go false - the pane sits in "could not read the initiatives" with a Try again button until the reader presses it. That is why the base arm is not judged on the Refresh check. The fix makes that state ride the same wait as a pane with a map on screen (public/assistant.js:4231), so the reason line's promise ("retrying in Ns") is true in both states.
  • The reason line is drawn only with a failure. The meta line's rule from row 275 stands: it may not draw anything while a read is in flight, so the reason rides inside the initErr guard and an empty carrier still costs nothing (public/style.css:5099). The zero-shift gate was re-run on this tree and passes 34 of 34 checks at 660 px and 340 px; its failure sample is now two and three line boxes tall instead of one and two, and its whole-line-box assertion still holds.
