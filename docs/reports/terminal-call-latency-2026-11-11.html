Terminal call latency on this host

Measured 2026-11-11 23:16Z to 23:25Z on C:/ProjectDevelopment/agent-worktree-gui, branch main, HEAD ce87716a. Every number below is a wall-clock reading taken inside the call it describes; nothing here is inferred from priors.

1. The question

A terminal call took 152.2 s and its output ends with Branch #20 SUCCESS in 216.9 s. Was that the shell, the kubectl/Jenkins commands themselves, the pre-execution guard, or waiting?

Verdict: waiting, and specifically a Jenkins poll loop that sleeps inside the call. On this host one command of each kind costs under two seconds and six of them chained cost 5.6 s. To reach 152.2 s a call has to spend roughly 146 s not executing anything - which only a sleep between poll requests does. The 216.9 s build time in the same output is the fingerprint of that loop: the build was already running when the call started, and the call sat on it.

3. What each number rules out

  • The shell is not it. A bare echo is 115 ms. Even if the 152.2 s call had opened forty shells it would not reach 152 s.
  • The six commands are not it. Chained they cost 5,622 ms, and 3,060 ms of that is the one bash -lc in the chain. Six chained commands are 27 times cheaper than the call being explained.
  • Network waits are not it, today. Both jenkins.prog.sefl.com and the k3s DEV API fail DNS on this host in 0.4 to 0.6 s, so no request can silently burn minutes on connect. That also means the live cluster and Jenkins round trips could not be measured honestly - see the unverified list.
  • The guard is not it. See section 5: the probe is sub-millisecond on the happy path; it has a 30 s fail-closed ceiling, not a 30 s cost.

4. What is left: the poll loop

Subtracting everything measured leaves about 146 s of the 152.2 s call with no command behind it. The only way a shell produces that is sleep. The output corroborates it directly: Branch #20 SUCCESS in 216.9 s is what a wait-for-build loop prints after it exits, and 216.9 s is longer than the call itself - so the build had started in an earlier call and this call spent its whole life in the sleep-poll cycle, then printed the build's own elapsed time.

Arithmetic on the run record: 1,126,053 ms for 38 terminal calls is a 29.6 s mean per call if terminal were 100 percent of the run (it is not - the model turn, tool results and prompt assembly are in there too). One 152.2 s call is 5.2 times that mean: an outlier single call, exactly the signature of one call that waited while the rest answered in seconds.

5. What the process-identity probe costs

terminal_tool.py:1559 is the rejection path for a guard that did not answer in time. The guard itself is _pre_exec_block (line 1416), run on a deadline worker with guard_timeout = max(plan.effective_timeout, _PRE_EXEC_GUARD_MIN_TIMEOUT_S), and _PRE_EXEC_GUARD_MIN_TIMEOUT_S = 30 (line 1413). Inside it, gateway_lifecycle_block calls _is_supervised_gateway_process() (tools/process_registry.py:311), which early-returns False unless _HERMES_GATEWAY=1, and otherwise verifies is_supervised_gateway_launch() plus get_running_pid(cleanup_stale=False) == os.getpid(). That PID verification ends in a kernel process query - the psutil create_time the comment at line 1532-1539 names.

Measured: one create_time() is 0.1 ms, a full process_iter over 760 processes is 84.2 ms. So the probe's steady-state cost is well under a millisecond per terminal call - it is not a latency contributor. What the code buys with that cheapness is a 30 s fail-closed ceiling per call: if psutil wedges (the macOS case in the comment, #111922), the call is refused after 30 s instead of hanging for an hour. That is the right trade, and it is not the 152.2 s.

Side finding worth a fix of its own. bash -lc true costs 1,616 ms on this host, and 3,060 ms when run inside an already-running MSYS shell. Any command that wraps itself in bash -lc pays that every time. Chained commands should call the binary directly.

8. Unverified, and why

  • Live kubectl and Jenkins round trips. Both hosts fail DNS from this machine right now (no such host), so the honest figure for a real kubectl get pods against DEV and a real Jenkins read is not measured here - only the failure cost. The 152.2 s conclusion does not depend on them: even a 30 s cluster call is well short of 152 s, and the build output in the call proves a successful poll happened when DNS was up.
  • The exact original call. Its text is not in the panel's job lines or in the gateway log; only the reader's quotation of it survives. The six-command chain above is a reconstruction of that shape, not a replay.
  • Per-call tool timings. Nothing on this host records them (section 6), so every number in section 2 is an in-call stamp, which is the narrowest honest measurement available.
