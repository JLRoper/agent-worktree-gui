The initiatives meta line does not move while a read is in flight

Expanding an initiative re-reads the store. That read used to draw a hint (reading…) inside the in-flow meta line, which cost one line box plus the column's gap and pushed every card below it down until the read landed. This page is the measurement: the first card's top is identical before the read, while it is parked in flight and after it settles, at a 660 px and a 340 px dock, and the string never enters the DOM at all.

1The mechanism, in two lines of code

The row named the line and the mechanism: public/assistant.js:4212 on the base, a span inside .init-meta.

.init-meta is a flex column with a gap (public/style.css:5072), so a node inside it is a flex item: it is charged its own line box and the 8 px gap whether or not it holds a word. The base painted that item unconditionally, and chose its text from the read's state: 

<span class="as-hint init-read">${initLoading ? "reading…" : initErr ? `read failed: ${esc(initErr)}` : ""}</span>

The render that draws the meta line also starts the read when the document is stale (public/assistant.js:4154), and loadInitiatives() sets initLoading = true before its first await - so the very same paint that begins a read is the paint that writes reading… into the meta line. Every press that repaints the pane while a read is in flight does the same. When the read settles the next paint removes the text and the cards snap back.

2The change

The span is written only when there is something a reader must see. A read in flight leaves the markup identical to what is already on screen, which is also what the markup !== initMarkup short-circuit wants: 

${initErr ? `<span class="as-hint init-read">read failed: ${esc(initErr)}</span>` : ""}

read failed: … keeps its text, its class and its place in the meta line. The stylesheet keeps a second lock (public/style.css:5092) because an empty carrier would still be a flex item and still cost the gap: 

#as-initiatives .init-read:empty { display: none; }

Side effect worth naming

Even when idle, the base rendered that empty span and paid the gap: the meta line measured 103.75 px at a 660 px dock on the base and 95.75 px on the fix (8.00 px, exactly the column's gap), 121 px against 113 px at 340 px. The fix is 8 px shorter at rest, not only steady while reading.

A MutationObserver over #as-initiatives (childList + characterData, subtree) reads the pane's text on every callback. Proven able to see the event before it reports a zero: the gate plants a span holding reading… in the pane, requires the observer to record it, removes it and resets the counters.

The Refresh button is read at the same three instants as the card: rect top, rect height and disabled. All three are identical (top 207.06 px and 292.11 px, height 30 px, disabled false) - a read changes neither its place nor its state, so there is nothing there that moves the meta line either.

The base had a second defect here, and the fix removes it

On the base, a failing read could not show its error at all. loadInitiatives() leaves initReadAt alone on failure, so the render that follows a failed read finds the document stale, starts the next read (initLoading = true) and then prefers the loading branch over initErr: reading… was painted where the error belonged. The base arm of this gate shows exactly that - the forced failure's .init-read text reads reading…, never read failed:. With no loading branch left, the error is what a failed read shows (section 5 above, measured on the fix).

7Found on the way, not changed here

  • A pane that exactly fits its box is treated as "at the bottom". captureInitScroll computes atBottom = scrollHeight - clientHeight - top < 2 (public/assistant.js:4118), which is true for a box with no scrollback; restoreInitScroll then writes scrollTop = scrollHeight (public/assistant.js:4125) on the next paint. Measured while building this proof at a 660 x 1000 dock: before the press the pane measured scrollHeight === clientHeight (845 / 845), the fold took it to 1504 / 845, and the pane landed at scrollTop 659 - the opened card's top left the view. It is the same family (a repaint moving the reader) but a different writer, and the meta line is not in it.
  • A persistently failing read retries with no backoff. While the route answered 500 immediately, the pane issued 114 GET /api/initiatives inside one sample window (counted in the route handler): the .finally() repaint starts the next read because initReadAt never moves on failure. The gate slows that to one read per 400 ms so its own measurement stays stable; the retry cadence itself is untouched by this change.
