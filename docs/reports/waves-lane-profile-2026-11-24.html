1. What was measured, and on what

The reader's numbers came from the live panel: GET /api/waves?initiative=... answered 9.4 KB in 0.63 s, 2.80 s and 5.12 s on three consecutive warm calls, while GET /api/initiatives answered 212 KB in 0.42 s. That shape - a tiny answer with wildly variable latency - is a fan-out, not a payload. This report replaces the stopwatch with three instruments:

  • the panel's own phase clock: ?profile=1 on the waves route (routes/waves.js:276) wraps the read in lib/read-profile.js and answers profile.phases, profile.operations and the facts it read;
  • node --cpu-prof --cpu-prof-dir=... on the sandbox panel, so the flame view covers the route and not just the test;
  • GIT_TRACE2_EVENT on the panel's environment. Every git process writes an "event":"start" line, so the number of git subprocesses is counted from outside the code as well as by its own counter.

The panel was booted from a sandbox state directory (a copy of the live stores, its own port, its own dataDir, matrix.autoStart off, fetch and refresh long) so nothing read or wrote the reader's board. The wave that was measured is a fixture: 8 task rows, each pointed at a different real worktree of this repository, folded under one wave whose exit gate is main-moved. That gate is the one check that makes every member's content be read against origin/main, so the fan-out is exercised on every call instead of being skipped as "no gate needs it".

A tidier fixture would hide the defect: the six real initiatives on the live board currently have almost no evidence gates, which is why a warm read of them is fast today. The cost this row is about appears the moment a wave names a gate that reads content, and the fixture holds that condition still.

2. The flame view: no hot frame, and that is the finding

The CPU profile of the whole sandbox process, over a cold 9.8 s read, holds 97 samples. 54 of them are (idle). The largest frame in the panel's own code is pickTask at lib/assistant/queue.js:756 with 3 samples; everything else that recurs is Node's module loader at boot. There is no hot JavaScript function because the time is not spent computing: it is spent waiting on child processes.

So the instrument that decides this row is the number of git subprocesses, and the second is the wait. A cache cannot make a spawn cheap; only not spawning can. That is why the change below is a key, a bound and a faster ref read, and not a data-structure optimisation.

Measurement conditions, stated plainly: the last sandbox run happened while this host's C: drive was 100 percent full (472 GB used, 326 MB free), which inflated wall-clock times (one /api/state read took 16 s). The route's own phase totals and the spawn counts are quoted as measured; the wall times in the table are what the socket answered, and they are noisy for that reason.

Its second read is a hit.

4. The cache: what each answer is keyed on, and when an entry dies

Two caches live in lib/wave-evidence.js, next to the reads that fill them, so every caller gets them: the waves route, the initiatives document, the wave driver and the tests. The invalidation rule is written at lib/wave-evidence.js:169 and repeated here because it is the load-bearing decision of this row.

readkeyvalidated againstwhy that is the deciding fact
readLanding (a member's content on main)clone + recorded sha + main refthe main ref's tip sha, recorded on the entry as mainShathe sha is immutable content; the ref is whatever it names now. Nothing else can change the answer.
readMemberPath, the tree halftree + relative paththe stat's stamp: mtimeMs:size:kinda write, a touch, a delete or a replace changes the stamp and the answer is read again
readMemberPath, the landing half (the tree is gone)clone + resolved ref + relative paththe ref's tip shathat read is rev-parse + log -1 + ls-tree; its answer is decided by the tip exactly as a landing is

An entry dies when

  • the ref's tip is no longer the sha the entry compared against. This is the correctness device. A merge, a fetch or a local commit on main moves the tip, and the next read measures again instead of answering from the past.
  • the key changes. A member whose recorded sha or whose pull request's head moved is a different key; the old entry is never consulted for the new content.
  • it is older than 10 minutes (WAVE_EVIDENCE_ENTRY_TTL_MS, lib/wave-evidence.js:196). This is a memory bound and the pull request word's freshness window, never the landing rule. The PR state rides on a member's evidence and its own index has a 60 s TTL; an entry that outlived both would keep an OPEN pull request reading OPEN after it merged.
  • the cache is full (600 entries): the oldest quarter is evicted, so one huge wave cannot throw away the whole board's answers.

An unknown answer is never stored. Blindness is re-read on every call, so a git that comes back is noticed at once; a test proves it (section 7, test 5). A cached answer about a sha the clone has since pruned is still a true statement about main's content - the answer names the main sha it compared - and a fresh read of it would only add "and the sha is gone".

The tip is read out of the ref files, with git as the fallback

Every warm read has to know the tip, and git rev-parse costs a process: measured at 94 to 128 ms per call on this repository, and 28 to 42 of them was exactly the problem. A ref's value is also a file. refTipOnDisk (lib/wave-evidence.js:144) resolves the short name in git's own documented order - <name>, refs/<name>, refs/tags/<name>, refs/heads/<name>, refs/remotes/<name>, refs/remotes/<name>/HEAD - takes the first that exists, follows a symbolic ref up to three times, and reads both loose refs and packed-refs (cached by that file's mtime and size). A worktree's .git file is followed to its gitdir and commondir, so a member tree and the project checkout answer the same ref.

Anything it cannot answer exactly - a candidate under refs/tags/ (an annotated tag would need peeling), a directory that is not a repository, a ref no file names - returns null and tipOf (lib/wave-evidence.js:241) spawns the one git rev-parse. A ref update is atomic (git renames the new file over the old), so a reader sees the old value or the new one, never a torn one. The test compares the file answer against git rev-parse for a loose ref, a packed ref and a worktree (test 7).

One tip read per project per request: every worktree of a repository shares one object store, so tipScope resolves the ref in the project checkout and the per-request tips map hands that one promise to every member. A wave of twelve worktrees pays one ref read, not twelve.

One behaviour is new: a member whose recorded sha IS the tip

The old read answered unknown for a member whose recorded commit was already main's tip, because the diff against its own base is empty ("the recorded sha changes no files against its own base"). That is a fact, not blindness: if the recorded sha equals the tip, its content is main's content. It is now landed by identity (lib/wave-evidence.js:262), which also makes it cacheable - before, such a member was re-read on every call forever, because unknown answers are not stored. The fixture happened to hold three of these and they were 10 of the 15 spawns on every warm read.

5. The fan-out: parallel, under one budget

The base build read members one at a time (the old comment said so: "promising a hundred git children at once would make the Initiatives tab the busiest thing on the box"), then a four-wide pool was added, each member still carrying its own 15 s timeout. A wave of sixteen members against a dead host was therefore sixteen timeouts, and a read that ran long could hold the route for minutes.

a member that cannot start or finisherror, not a guessbudgetEvidence, lib/wave-evidence.js:853: error is the sentence a gate reports verbatim, and readWaveGate treats it as cannot tell

The failure is fail-closed by construction: readWaveGate (lib/waves.js:939) answers unknown for a member whose evidence carries error or is missing, and unknown blocks a gate; it never becomes met. The budget is not a promise that every read finishes - it is the promise that a read finishes, tells you what it could not reach, and does not spend a timeout per member to do it.

8. What this does not fix

  • The cold read still pays the fan-out. The first read of a process, or the first read after a ref moves, measures every member: 5 git spawns each, 28 for the fixture. That is the honest cost of judging content, and the cache's job is that it is paid once.
  • The queue fold is now the largest remaining phase of a warm read (phases.queues 29 to 113 ms). It reads four assistant queue files and builds a view per assistant on every request. A cache there is a separate decision, and a wrong one is easy: the queues are the facts a wave is folded from.
  • /api/state still carries 25.8 percent of bytes no page code reads (section 6). This branch does not change the frame. The report exists so the next cut does not have to re-measure it.
  • The budget is a ceiling, not a target. A wave of forty members on a slow host will spend 15 s and answer cannot tell for the tail; that is deliberate (fail closed) and it is visible in the gate's sentence, but it is a real limit.

9. Reproduce

What the harness does, in order:

1. copy the live stores into a sandbox: initiatives.json, waves.json, assistants.json,
   hosts.json, roles.json, todos.json, projects.json, tree-cache.json, labels.json and
   every assistants/<id>/queue.json. Never the jobs store.
2. write a config.json with its own port, dataDir = the sandbox, matrix.autoStart = false,
   fetchSeconds and refreshSeconds long, and scanRoots left as the reader's.
3. seed the fixture: N task rows (state running, project agent-worktree-gui, waveId wave-perf,
   pipelineRun.assembly.commit = that worktree's HEAD) folded under
   { id: "wave-perf", exitGate: { check: "main-moved", remote: "origin", main: "main" } }
4. spawn: node --cpu-prof --cpu-prof-dir=<prof> server.js
   with PANEL_CONFIG, HERMES_HOME, GIT_TRACE2_EVENT=<trace> and API_SERVER_KEY=""
5. wait for /api/health and for rows on the board, then sleep 31 s so the base build's 30 s memo expires
6. one cold GET /api/waves?initiative=init_perf&profile=1, three warm ones, one more 31 s later
7. count "event":"start" lines in the trace around each call, and read measure.json

The route's own answer carries the load-bearing numbers: profile.phases.evidence, profile.operations["git.calls"], landing.cache.hit, landing.cache.miss, ref.disk, evidence.skipped, evidence.timedOut. A reader who only wants the before-and-after can run the same fixture against git archive 4c256c79 and against this branch; that is how section 3 was made.
