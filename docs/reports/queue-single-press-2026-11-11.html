agent-worktree-gui - the Queue reply press - one PR

One press puts the reply in flight

The Queue reply button held the reply, then left the card exactly as it was: an empty editable box and a live button beside one held entry. The box took the same text again and the next press held it a second time. Now the press closes the card behind it - button off, box read-only, "queued, waiting" - and a repaint draws the same face from the same predicate, so the two cannot drift apart. Every claim below is from the shipped build driven in a real browser.

What the base build did

public/app.js:3843 in queueReplyFromBox read the box, cleared it and called queueReply with no guard. The rebuild that followed drew an empty box with contenteditable="true" and a live Queue reply button. Two presses on the same text were therefore two entries, and the drain would send both.

The observed fault was the second of the two the brief names: the box took more input while the first reply was still held, and because of that a second press on the same text created a second identical held entry. The first press emptied the box, so a press made before any retyping held nothing; the box simply let the text back in.

What the fix does

  • queueWaitingOn(thread) is the one question: does this thread hold a reply? The press, the box's keys and the card's render all ask it, so none of them can disagree.
  • queueReplyFromBox asks it first. A press that reaches the function while an entry is held - a stale node, or Enter from a box the repaint has not replaced - holds nothing and returns false. Enter already called this same function, so the guard is one path, not two that can drift.
  • paintQueueWait(thread) applies the face to the live DOM: the button disabled plus aria-disabled, the box contenteditable="false" plus aria-readonly, the note "queued, waiting" visible.
  • The card's render (public/render-jobs.js) draws the same face from the same predicate: a repaint cannot reopen the box. The queue's length is already in conversationSignature, so when the drain takes the entry out and sends it the card repaints, the predicate answers "no", and the box opens again.
  • The keydown handler returns early for a box that holds a reply, so no key - Enter included - is a gesture on a closed box.

The gate

tools/verify-queue-single-press.mjs boots a sandbox panel, fabricates a running turn in the page's own state.jobs so the shipped renderer paints a real worker card, and drives the real button and real key presses. It asserts: one press holds one reply; the button is disabled and the box read-only while held; the queued state is visible; a second click (real mouse and a click event dispatched straight at the disabled button) holds nothing; the box takes no input; the Enter path holds one entry and draws the same closed face; and the state clears when the held reply is drawn.

What was not touched

The clarify card's caret and links code (1.82.0) is untouched, the panel was not restarted, and no other repository was read or written. The only files this change adds or changes are the press, its render, its stylesheet face, the new gate, the new test, and one existing test's function list so it carries the two new functions it now calls.
