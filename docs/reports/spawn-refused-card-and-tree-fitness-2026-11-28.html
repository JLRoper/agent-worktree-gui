1. The two absences this closes

A SPAWN line the panel refuses used to leave one journal entry in a 300-entry ring. The row stayed queued, no thread appeared, and no card existed, so the only evidence was an absence the reader had to notice. Row 401's report measured the consequence: two long SPAWN lines refused into that hole read to the reader as lines that never happened (docs/reports/spawn-line-record-and-tree-fitness-2026-11-28.html, section 2.1).

The pre-flight had the matching hole in the other direction. spawn-check answered ok for a queue row, but its facts about a named tree came from the board's scanned row. A tree the scan had not reached, or whose row was minutes old, answered { ok: true, checks: [] } and the cut refused it a beat later. Measured on the live panel at port 7331 (the base build, before this branch): a tree 4 commits ahead of main with 2 uncommitted files answered:

{ "ok": true, "reason": null, "remedy": null, "checks": [], "treeState": null }

That is the drift. The cut's own fitness refusal existed (lib/jobs.js tree_unfit) and the pre-flight never asked it.

The card is drawn by the panel's existing alert renderer (public/assistant.js:2753): a red is-bad card with the rule chip, the title, the detail and one labelled evidence line each. No new UI was needed, and the card has no Start button because there is nothing left to start. It is filed on the assistant whose line was refused (assistant-1 here), and state() includes it in the list the page reads.

One card per row or tree, and it closes itself

The key is spawn-refused|task-<id> for a line carrying a row and spawn-refused|<tree> for one carrying a tree (lib/assistant.js:2661). A boot re-reading the turn, or a second line refused for the same row, rewrites the same card instead of stacking another. When the same row or tree is finally carried out, closeSpawnRefusalCard (lib/assistant.js:2710, called at lib/assistant.js:8771) marks it done and journals spawn-refused-cleared. A red card left open after the fix reads as a refusal that is still true.

The same path covers every refusal the cut makes: the row check in the harvest and in startSpawn (lib/assistant.js:8652), the held tree (tree_busy) and the unfit tree (tree_unfit) at lib/assistant.js:8718. jobs.create now carries err.reason beside err.remedy (lib/jobs.js:4281, lib/jobs.js:4336) so the card quotes the obstacle and the fix separately, never a whole sentence chopped in half.

Three cases are kept apart, deliberately:

  • Dirty or stale: a REFUSAL (tree_dirty / tree_stale), built by treeFitnessRefusal (lib/spawn-check.js:331), the same function jobs.create throws. The reason quotes the uncommitted file count AND the unlanded commit count.
  • Clean but ahead of main: allowed, as the cut allows it, with the count and branch under tree-unlanded. The test fixture for this case is 7 commits ahead and answers ok: true with ahead: 7.
  • Held by a live run: refused, naming the job and the thread, and treeState.holder carries the same run as a fact ({ id: "job-5962", thread: "t-hold", dead: false } in the test). A run the runs API calls DEAD stays the re-issue case it was, and reports dead: true.

The project's own checkout is the exception the cut already makes: jobs.create skips the fitness refusal there because its dirt is the reader's, so the pre-flight skips it too and only reports the counts in treeState. Without that, the route would refuse a line the cut accepts. A directory git cannot answer for (read: false) falls back to the scanned row, and is never called clean.
