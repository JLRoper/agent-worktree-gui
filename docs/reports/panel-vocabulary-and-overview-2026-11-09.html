1. The panel in one pass

The panel is two things: the Node server started from server.js, listening on port 7331, and the browser board that server serves. The server scans the projects it was told about with worker threads, keeps the result in ~/.wag, and pushes each change to the open page over SSE as one patched table row. The HTTP layer never runs git itself; a slow scan cannot stall a request (docs/architecture.md).

The gateway is Hermes on port 8642, and it is the half that executes a run. The panel POSTs /v1/runs and gets a run id at once, reads the run's events over a server-sent stream, and posts a steer or a stop to the same run. The gateway owns the model, the tools and the turn; the panel owns the handle (lib/jobs.js, lib/hermes-runtime.js).

What the panel records is what it can draw again after a restart: every job, every queue, every TODO, every lock, the naming ledger and the pipeline records. All of it lives under ~/.wag, outside every checkout, so replacing or re-cloning a repository does not take the board's history with it (lib/paths.js). On boot the page is redrawn from those files, not from the gateway's memory.

The one-sentence version. The panel records what happened in ~/.wag and draws it back; the gateway executes the runs; the board is the shared view of both.

2. The vocabulary

Nineteen nouns, each defined against the file that owns it. Where two nouns are usually confused, the entry says which one is the record and which one is the activity.

panel

The Node server started from server.js, plus the browser board it serves on port 7331. It scans projects, stores rows and jobs under ~/.wag, and pushes changes to the page. Its HTTP layer does not run git; the scans run in worker threads (docs/architecture.md). Port from config.json.

gateway

Hermes' HTTP Runs API, default http://127.0.0.1:8642 (lib/hermes-runtime.js). It executes a run: POST /v1/runs returns a run id, GET /v1/runs/<id>/events streams the tool and message events, and steer and stop are separate POSTs. The panel supervises; the gateway does the work.

assistant

A named agent the panel runs as a real Hermes thread: a charter, notes, its own queue, its own settings, and a set of sentry rules that watch the board. Assistant #1 runs on the thread panel-assistant; the others are separate assistants with their own directories. An assistant reads the board and files or starts work through the panel's own routes; it never runs git itself (README.md, lib/assistant/).

queue

One assistant's task list, kept at ~/.wag/state/assistants/<id>/queue.json. Every assistant has one, #1 included; there is no legacy second list. The file holds the tasks, their order, their holds and the run each open task is on (lib/assistant/queue.js).

task

One row of a queue, carrying id, title, detail, state, owner, thread, threads, runId, worktree, files, lane, hold, order, attempts and reason, with the created, started and done stamps beside them. state is queued, running, parked or done; stale and conflict are derived at read time and never written to the file. The id is monotonic per queue (lib/assistant/queue.js).

row

The board's record of one worktree: branch, head, ahead and behind counts, dirty files, verdict, mergeable and sync state. Store.putRow is the one place a row is assembled, and a row is keyed <project>::<path>. It is a claim with the evidence attached, not a database record (docs/architecture.md).

hold and park

A park is a task in state parked with a reason. The hold is the testable half of that park: {kind, value, since}, where kind is thread, job, task, path or manual. The panel releases the row when the named thing stops being true. A manual hold, or no hold at all, is never released by the panel: "needs a decision" is not a condition that becomes false (lib/assistant/queue.js).

run

One attempt executed through the gateway, recorded as a job in jobs.json. Its id is the gateway's run_ id, or the panel's job id when the gateway gave none, and a task's runId names the run carrying it now. A run has one status and one ending; a task can outlive several runs (lib/jobs.js, lib/assistant/queue.js).

turn

One exchange inside a run: the input, the tool calls it makes, the streamed output and the terminal event with its usage. The usage readout above the reply box is a turn's readout, not a thread's; a thread is many turns (README.md).

thread

A Hermes session id, and the panel's name for that conversation: wtgui-<words>-<tag> for a worker, panel-assistant for #1. A reply is a new run on the same session_id, in the same directory, so the conversation continues instead of starting again (README.md).

session

The gateway's record of one conversation, the thing hermes sessions list lists. In the panel a thread name IS the session id, so thread and session name the same object from two sides (docs/architecture.md).

card

The drawn unit of the board. A queue card is one task with its state, chips and actions; a job card is one run with its console, turns, usage and its approval or clarify boxes. Each job card is a conversation, and the console under it is the turn being drawn (README.md, public/queue-cards.js).

tree

One git worktree on disk: a directory with a branch checked out, and the unit a run's cwd points at. A row is the board's record of a tree, and a tree is dropped only after two consecutive discovery passes omit it, never because one listing failed or came back empty (README.md).

branch

The git ref a tree has checked out. The panel names its own branches wtgui/<slug>-<tag>, and the pipeline's kind (local, investigation, turnover) says what a branch may do: commit and stop, commit and report, or push and land through a pull request (docs/pipelines.md).

pipeline

A named definition of ordered stages. The panel reads two shapes: the ladder in pipelines.json over pipelines.seed.json (a kind, stages, exit checks) and the PDL document in pipeline-bundle.json (stages, gates, handoffs, artifacts). The two do not share ids, and neither validator accepts the other's document (docs/pipeline-sources.md).

stage

One ordered step of a pipeline. In the ladder a stage carries a title, a prompt and an exit check; in a PDL document it carries an artifact, an owner role, its inputs and a done list. The ladder refuses a stage with no exit check at save time; a bundle refuses a stage with no name, prompt or artifact at load time (lib/pipelines.js, lib/pipeline-bundle.js).

gate

A PDL record that ends a stage: its id, the stage it follows, who decides, what it reads, what it refuses, and the artifact the decision is written to. The ladder's equivalent is the stage's exit check, a named test in a closed vocabulary (lib/pipeline-bundle.js, lib/pipelines.js).

bundle

One authored PDL document set, imported as a whole: ~/.wag/state/pipeline-bundle.json, shaped {bundleVersion, name, pipelines[]}. parseBundle refuses a bad bundle whole, with a code and a locator, because half a bundle is a stage order that disagrees with its own gates (lib/pipeline-bundle.js).

catalogue

The ladder definitions: pipelines.json over the committed pipelines.seed.json. validatePipeline drops a bad definition by id and keeps the rest, because a reader hand-edits that file and one typo must not empty the board. The Settings pipeline tab draws both lists from GET /api/pipelines: PDL first, then the built-in ladders (lib/pipelines.js, docs/pipeline-sources.md).

3. How a task becomes a run

The path is four objects and one decision. The decision is the verdict: a run ending is not the same fact as the work landing, and the panel settles a task on the second one, not the first.

  1. task filedA queue row is written in state queued, by the reader or by an assistant's own QUEUE line. It gets the next id in that queue, and optionally its files, its lane and its project.
  2. assignedThe task may be put on a bundle pipeline and a stage. The assignment writes pipelineRun and stamps enteredAt; assigning the same stage again changes nothing, including the stamp. This is a read of the bundle, not a rewrite of the task's history (lib/task-pipeline-assign.js).
  3. run startedThe panel starts a run through the gateway. The job gets a thread (the session id) and a run id, and linkTaskRun writes that run id on the task and moves it to running (lib/jobs.js, lib/assistant/queue.js).
  4. card drawnThe job card renders the run's turns, console, usage and any approval or clarify box. The queue card renders the task's state and the agent chip for the run carrying it; one task can show a dead attempt and a live retry on the same thread, because the chip reads the named run, not the thread name (public/queue-cards.js).
  5. verdictWhen the named run ends, the panel settles the task. Run done plus a tree whose row reads MERGED, or no tree to land: the task is done. Run done but the row is not MERGED: the task stays running and reads stale, and landing it is the assistant's judgement. Run failed: the task goes back to queued with attempts + 1 and the reason (lib/assistant/queue.js, settleTasks).

The two pairings that get confused

task is not run

A task is the work item: one stable id, its own history (threads[], movedFrom[], attempts). A run is one attempt: one run id, one status, one ending. One task can outlive several runs. That is why runId exists, and why a live retry on the same thread must not settle a row whose own run has failed.

thread is not tree

A thread is a conversation (a Hermes session id). A tree is a directory with a branch. The board keys a row by the tree and the run by the thread and its run id. Renaming a tree moves the directory and the branch and keeps the six-hex tag; continuing a thread starts another turn in the same session. A tree can host a repair turn on another thread, and a thread's record outlives any one tree.
