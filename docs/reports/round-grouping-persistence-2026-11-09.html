Where a round's grouping lives, and why a restart lost it

agent-worktree-gui, branch wtgui/round-c-how-a-round-names-its-trees-stage-1-probe-294b21, on top of 68c7bf5d. State root in this report: C:/Users/roper/.wag/state.

The finding

A round names two things about its trees: what each row is called, and which row it hangs under. The name was moved onto the queue task in the names cut. The grouping never was, so the two facts come from different stores and only one of them is read on every snapshot. After a full node restart the names are still painted because the snapshot reads them from a file; the group is missing because the edge is a field a scan writes, and a freshly discovered row has not been scanned yet.

Where the names are stored

<state>/tree-names.json
the naming ledger (not the chart's title)		 trees["<project>::<tag>"] with name, dir, branch lib/tree-names.js forTree(), stamped as row.named; it says what the tree's directory and branch were named, and stops the auto-namer touching the tree again

The queue read is keyed by the normalised tree path (roundTreeKey: forward slashes, no trailing slash, lower case), so it matches the row on Windows and on Linux alike.

Why the grouping did not survive

Measured, not inferred

A sandbox with one repo, a round parent worktree, one stage worktree, a queue task naming both, and parents.json absent. The real panel was booted twice over that state dir:

boot 1: round-a-052254             round.display = "Round A: the parent-tree note"   parent = absent
        round-a-stage-1-probe-6632b6 round.display = "Stage 1: probe"                 parent = absent
boot 2: identical - both names still there, no grouping on either row

On the same state dir before the fix, the stage row carried no grouping field at all: the new boot test failed on round.parentPath with actual: undefined, expected: null.

  • The name is an overlay: withRoundNames() puts row.round on every row of every snapshot, so it is on the board the moment the process can read the queue file.
  • The grouping was a scanned field. parentFor() runs inside the per-row git read, so a row that was just discovered carries no parent until its own scan lands. A project parked on the old tier can wait an hour for that scan, and a board that has only just booted has every row in that state.
  • And when the book had no record for a stage tree - a round cut before the record existed, or a book write that failed - the grouping never came back at all, while the name did. The queue already held the answer; nothing read it for the chart.

What changed, on top of 68c7bf5d

The grouping now rides the same record as the name

  • lib/assistant.js cutPipelineTree: the stage tree record writes parentPath beside its parent branch, so the store holds both halves of the edge for every tree a round cuts. Records written before this change are still read correctly through the fallback below.
  • lib/round-tree-names.js: every entry carries parentPath. A round's parent tree answers null (it is a sibling of the checkout's own row); a stage child answers tree.parentPath || round.parentPath, so an old record and a re-homed tree both read right.
  • public/render-projects.js childTreeOf(): the round record's parentPath is the edge when a row has one, resolved by path against the project's own rows. The branch edge is the fallback for every other row. The old rules still hold: a parent must be a drawn row of the same project, a main branch is never a parent, and cycles are still broken.
  • lib/parents.js record(): parentName: null is now an answer, not a missing value. A round's parent tree cut from origin/main used to fall back to the ref and record parent: "origin/main", re-introducing the parent 68c7bf5d had just removed; it now records no chart parent, and only a caller that says nothing at all lets the ref answer.

The merge chooser is deliberately untouched: a stage tree still has nothing to roll into. Its parent tree is where the round assembles, not where a stage branch lands, so the grouping is a chart fact and not a landing claim.
