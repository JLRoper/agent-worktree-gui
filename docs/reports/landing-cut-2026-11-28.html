The landing cut: its own turnover branch, keyed to the task id

The reader's decision this page implements. "When a small landing task has no turnover branch, the panel CREATES one automatically, keyed to the task id, and cuts the worker on it - no ask, so a small task never stalls." And: "root trees are research or turnover, never implementation." The row that named TASK-405's branch while its own key had none, and the trees cut at the repo root with no recorded kind, are the defect this change removes.

What the cut does now

  • The brief decides the kind, and a landing verb always wins. A brief containing land, push, PR, merge, ship, release or a version bump is a landing brief whatever its first sentence says. A landing verb used as a description of the panel's own machinery ("the push guard", "the merge status", "a landing tree") is not an order and does not flip a research brief.
  • A landing cut makes its own turnover branch, keyed to its task id, with no card. From a plain cut with a code or landing brief, the panel derives YYYYMMDD_HHMM_TASK-<id>_<slug>, cuts the container, files it under task <id> in the project's registry, and cuts the child from it. The turnover policy governs a manual add; it no longer parks the cut.
  • One entry per key, accumulated. A key resolves only its own entry. A key with none resolves nothing, so a cut never borrows another feature's branch (the TASK-405 leak). A second cut for one key reuses the first branch.
  • A landed branch is not a container. A registered turnover branch whose tip main has moved past refuses the landing cut by name, with the two remedies (remove it from the project, or file under a new task id).
  • Implementation at the root is refused by the cut. A landing cut that names no key, and any implementation cut that would still start at the project's base, is refused with the sentence that says why and the line to write instead. A pipeline stage that declares its own artifact (a PR, a local commit, nothing) is not a landing task and is exempt.
  • The job record stamps the queue row. A SPAWN carrying a task id writes queueRow on the job, so the run can be matched to its row from the store rather than from the prompt.
