13143 - the precision fix, with the measurement kept

Resolved at 34e261d, in effectiveTimestamp at lines 39 to 43. Truncating to minutes removes the mixed precision this review flagged: pickup time parses as HHMM and the fallback status time as HHMMSS, so before this commit a fallback row at 16:55:30 sorted above a real pickup at 16:55:00. The scale of it is why this mattered rather than being a corner case: in a 20,000 row dev sample of TRACING.TRACE_HEADER, PU_TIME is blank on 10,018 rows, so the fallback carries the majority of the sort. Lefler raised the same question on GetOutboundStripShipmentsMapping.java line 141 and has since written that the DAL side is good to go. One residual: the DAL still parses STATUS_TIME at HHMMSS, so the one precision invariant now lives here only.

13144 - the tie is tested in one direction only

Minor, in sortOutboundShipments_statusSecondsDoNotBreakMinuteTie at lines 68 to 80. The tie is now exercised, but in one direction only: pickup-0852 asserts ahead of fallback-0852-45 because both keys truncate to 08:52 and Stream.sorted is stable, so encounter order decides. Swap those two entries in the input list and the test fails. Encounter order is pinned nowhere: neither select has an ORDER BY (GetOutboundStripShipmentsMapping.java around line 29, GetReturnShipmentsMapping.java around line 30), so Oracle returns whatever it likes and two shipments sharing a minute can swap between runs. Stability of the sort is sound; reproducibility of the tie order is not. Pick one: assert the tie independently of input order, add a secondary key such as PRO, or add ORDER BY to both selects.

13163 - the date present, both times null branch

Minor, in sortOutboundShipments_nullTimestampsLastAndInputUnchanged at lines 54 to 66. The shipment named missing passes null for the pickup date, so it exits through the pickupDate == null test at OutboundStripShipmentSorter.java line 39 and never reaches the date present, both times null branch at lines 39 to 41. That branch is reachable in data: 2 of the 20,000 sampled dev rows carry a pickup date with both PU_TIME and STATUS_TIME blank, and those rows sort last through it. The code handles it correctly, so this is coverage, not a defect. One more case with a pickup date and both times null, asserting it sorts last, would close it and pin the nullsLast contract where it is actually used.
