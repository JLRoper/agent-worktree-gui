The approval box, in every shape of the turn

Queue row #286, agent-worktree-gui 1.166.7, 2026-11-24. Row #277's own harness - a stub Runs API, a sandbox panel, a real Chromium - pointed at a flagged command instead of a clarify question: the same gate, run on the base build first and then on this one.

The box was not drawn badly. It was drawn only for a turn the reader had left open. An approval was the last two lines of turnBody, and turnBlock calls turnBody only for an OPEN turn. Fold the turn, freeze it to a snippet, page to another turn, or reload the page, and the card drew zero approval boxes while the run was still parked on a person - with the dock's corner as the only surface still showing it. That is the same mechanism, and the same argument, that made row #277 fix this for clarify questions after two worker cards timed out unanswered.

1. What the row asked for

"the approval box drawn by the turn block in EVERY shape of the turn (open, folded, frozen), with conversationHtml deciding its one place - the turn's own copy, the pinned copy when the turn is off-page, otherwise a block at the top of the card naming the turn - so there is never a second copy and never a missing one; turnLive counting an open approval, which it already does, must keep the block's guard from returning empty when the status leaves the running set; and an approval that EXPIRES must keep what it asked, the way row 277 made a timed-out question keep its question, choices and reason."

Three properties, in order: drawn in every shape, exactly once, and what it asked survives the window. The dock is explicitly not the answer - it is a second surface that draws every live permission, and it is the reason this has not cost an answer yet.

2. Reproduced with row #277's harness, not a second one

tools/verify-clarify-pane.mjs already boots a sandbox panel on a spare port, points it at a stub Runs API that plays a parked turn over real SSE, starts the agent through the panel's own POST /api/agents, and reads a real Chromium's DOM. The approval phases were added to that file: the stub now emits approval.request (a flagged command, the choices the host allows, and a window), answers the run's /approval route, and reports its pending_controls so the panel's reconcile keeps the park. Nothing invented, nothing answered: no approval is pressed anywhere in this gate, and the stub's own POST list is asserted empty at the end.

The gate runs the same 75 checks against a git archive of the base commit (--root) and then against this tree. Base: 54/75, the 21 failures all approval-shaped. This tree: 75/75. The clarify checks pass on both builds - they are the control that says the harness and the page still work, and that row #277's fix is untouched.

3. Where the box was lost, named in the code

3.1 An approval was a detail of the open turn

turnBody ended with approvalPrompt(turn, copy) + approvalDecided(turn), and turnBlock called turnBody only in its open branch. The folded and frozen branches drew a head, a peek or a snippet, and stopped. The pager made it worse: a turn on another page is not in the DOM at all, so its box could not be either.

public/render-jobs.js:209 (turnBody), :274 (turnBlock), before this change

3.2 Nothing landed it

updateJob merged the frame and repainted the card with the reader's scroll restored - right for output arriving in a console the reader is reading, wrong for a box that stops the run. Row #277 gave the question a landing (landClarifyQuestion); the approval had none, so a box 1 600 px down a long board was the dock's corner against a page that never moved.

public/render-jobs.js:866 (updateJob), public/app.js:2546 (landParkBlock), :2570 (landApprovalBlock)

3.3 An expired approval kept the command and nothing else

expireApproval nulls j.approval and writes approvalDone - and that record carried choice: "", the command, the reason and the waited time. The choices the host had allowed were gone with the prompt, so the card's one line could say a command went unanswered but not what the reader was offered when it was still open. Row #277's rule for a timed-out question was the model: the record keeps what was asked.

lib/jobs.js:1135 (expireApproval), public/app.js:2071 (approvalDecided)

4. What changed

  1. Drawn by the turn block, in every shape. turnBlock takes the approval's block as its own argument (park) and inserts it in all three branches - open, folded, frozen - exactly as row #277 did for the question's ask. turnBody no longer draws either.
  2. One place, decided in conversationHtml. The page copy draws it; a pinned copy draws it only when the turn is not on the page; a turn that is neither on the page nor pinned gets a block at the top of the card naming the turn. Three cases, one box - and the gate counts the boxes in the document, so a second copy is a failure, not an aesthetic.
  3. The guard still counts a park. turnLive already treated an open approval as a live turn; the box now rides that guard in every shape, and the gate forces a status outside LIVE_STATUS to prove the block does not empty when the run's status leaves the running set.
  4. An approval that lands is landed on. updateJob notices an approval it did not have before and calls landApprovalBlock - the same one-shot record, the same on-screen test and the same scroll the question's landing uses, now shared as landParkBlock.
  5. An expired approval keeps what it asked. expireApproval records the command, the choices the host allowed and when it was asked; approvalDecided draws that as a trace (head, reason, command, choices, when) instead of one truncated line, and draws no control on a wait that is over.

Nothing about the answer path moved. The box's choices still post to the run's own /approval route, the dock still draws its own card from its own record, and this gate answers no approval at all - the count of approval POSTs is one of its checks, and it is zero on both builds.

5. What this does not cover

  • The dock's record is a different store. state.approvals comes from the approval transport, not from the run's record. The gate proves the dock still draws its own card, command and choices under its own head; it does not reconcile the two stores, and this row did not try to.
  • A decided record is not pulled to the top of the card. Only a park still WAITING gets the off-page block: a trace belongs with the turn it describes, and following the reader across pages would be noise. This is a deliberate reading of "never a missing one" - the missing thing was a live box.
  • The fold book is not in the card's signature. Changing it alone does not repaint the card; the next job event does. The gate's frozen phase says so in a comment and forces the repaint a job event would have caused, because a freeze that draws nothing would otherwise leave the old card standing and the check vacuous. The same test now covers the clarify question's frozen phase, which had the same hole.

One sandbox panel of its own on a spare port (its own config, its own jobs file, the reader's store untouched), one stub Runs API on another, one headless Chromium at 1400x900. The extra stub turns the pager needs are created with anchorCwd: false so the panel's one-worker-per-tree fence does not refuse them - nothing runs in the tree; they exist to give the card six turns and two pages.
