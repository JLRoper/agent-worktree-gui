The reports chip on a wave task row

v1.159.0 - branch wtgui/read-your-queue-row-239-first-it-is-the-15e741 - queue row #239. A task row in the Initiatives tab's wave lane now carries a chip that lists the .html reports that task left, and opens one in a new tab.

What was asked and what is there. A chip on each wave task row; a list of the task's own .html reports read from two sources; a click that opens the report in a new browser tab; a view route that serves the file sandboxed and refuses to leave the task's tree. All four are in this branch, and the gate below drives a real browser over a real report: 39 of 39 checks.

What the reader gets, in order

  1. The chip sits after the state chip on the member row and reads reports before anything is read, reports N once it is, and no reports in a muted tone when the answer is empty. A task with no thread gets a disabled chip whose title says why: an id alone is per-assistant and would name the wrong row.
  2. A press unfolds the list under the row, one line per report: its title as a link, then its age, its path under the tree, and which of the two sources named it. The answer is cached for the page session, so closing and reopening a list is not a second read, and a lane repaint from a snapshot draws the same open list rather than shutting it.
  3. A click on a report is a new tab in the browser the reader is already using: target="_blank" with rel="noopener", over GET /api/reports/view, which serves the file itself.

The two routes

RouteTakesAnswers
GET /api/reports thread (required), task (corroboration), project (used when the thread alone is ambiguous) {reports: [{name, path, rel, title, at, source, url, why}]}, newest first, capped at 50, plus task and sources: {deliverables, tree} so a reader can see where the list came from.
GET /api/reports/view thread, task, path (relative to the task's tree) The file's own bytes as text/html; charset=utf-8, Cache-Control: no-store, and a sandboxing CSP.

The thread is the key, not the id: task ids are per assistant, so thread is authoritative and the two other parameters only have to agree when they are given. Both routes are mounted once, through the prefix table in server.js:2054, and the module is routes/reports.js (exported at :378).

Refusals are sentences, never an empty list

  • No thread - 400 "thread is required".
  • A thread no queue row carries - 404 naming that; a task that disagrees with the row - 404.
  • path holding .. - 400, and the sentence names the segment.
  • An absolute path - 400: the route takes a path under the tree, not a path on the disk.
  • A file that is not .html - 400. A missing file - 404.
  • A write - 405. The report routes read.

Path resolution realpaths every candidate and requires the result to sit inside one of the task's roots (routes/reports.js:117), so a symlink pointing out of the tree is refused by the same rule as ...

Where a report comes from: the union of two sources

The brief named both, and the interesting part is what they disagree about, so the list is their union, deduped by the resolved path:

SourceWhat it contributesWhy the title wins
the deliverables store
DELIVER lines harvested when a run settles		 Every .html file this task's thread (or its job) declared, whether or not the tree still has it. A declared report's title is the one the reader was handed, so it wins a dedupe against the same file found by the scan.
the task's tree
a scan of docs/reports		 The .html files this branch added or changed since its base, committed and untracked alike. The file's own <title>, read from a bounded head of the file rather than the whole of it.

The base's reports are not this task's. The scan reads what the branch added or changed (git diff --diff-filter=AM <base>...HEAD plus git status --porcelain --untracked-files=all), not the directory. A report committed to main before the tree was cut sits in the same folder and is correctly absent; both the route test and the browser gate pin that with a file planted on the base branch.

A file the panel cannot open is still a row. A delivery whose file is gone, or one outside the task's tree, is listed with a null url and a why - struck through, never given a link to a file that is not there. The rule is the same one the DELIVER grammar uses: a path not on disk is named with its reason, never turned into a url.

What is on the wire, verbatim from the gate

HTTP 200
content-type: text/html; charset=utf-8
cache-control: no-store
content-security-policy: sandbox allow-scripts; default-src 'none'; img-src data:; style-src 'unsafe-inline'; script-src 'unsafe-inline'; font-src data:
x-content-type-options: nosniff

The CSP is the load-bearing line: sandbox allow-scripts gives the report an opaque origin, so a report cannot call the panel's API with the reader's own session even though it is served from the panel's own host. default-src 'none' then leaves it no network of its own - inline style and script are enough for a self-contained page.

The one behavior that needed care: Escape

The rail already has a global Escape handler: when the caret is inside the assistant panel, Escape closes the whole panel. Folding a list with the same key would therefore have shut the panel the list was in. The lane's key handler consumes the press when it has a list to close (public/core/waves-lane.js:547, stopImmediatePropagation), the same way the pipeline window does. The gate asserts it separately: after Escape, the list is gone and #assistant is still open.

Enter needed the opposite check. A chip is a real <button>, so the browser synthesises the press, but a lane repaint from a snapshot replaces the node under the caret; the gate re-focuses and presses again rather than blaming the key, and says so when it has to.

Why two files the brief protected are untouched

public/assistant.js and public/style.css are both held by a live run, so neither is in this diff. That cost two things, and both are answered inside the lane module instead:

  • No click or key wiring was added to assistant.js. The lane installs its own two listeners on the document at load and delegates from there (waves-lane.js:578), so a chip drawn by any painter is live without that file's help. It is idempotent and a no-op in node, which is why the lane's unit tests still run without a DOM.
  • The twelve declarations the list needs live in REPORTS_CSS (waves-lane.js:447), injected once as a <style id="waves-lane-reports">. They are only what the shared sheet cannot give a second owner: the member grid gains a fifth column for the chip at a wide pane, the list spans the grid, and the chip's unfolded and empty states get a tone. Everything else is the existing .chip, .as-hint and .mono.

What this does not do

  • It does not read reports from a remote branch. Both sources are on this machine's disk; a delivered file that is gone stays a named row, never a url to a remote.
  • It does not scan outside docs/reports, and it does not list anything but .html. The brief's subject was the HTML report a run leaves; a PDF or a PNG beside it is not in this list.
  • It does not cap by age, only by count - 50 rows, newest first. A task with more than 50 reports shows the newest 50 and says the list is capped.
  • It is not merged. This branch is a pull request that is deliberately left open: the landing is the reader's call, and row #234 runs after this one.
