Part two: what the card knows about "which project, whose landing"

The record

FactWhere it is, and what it says
The task's worktree and project One of each on the task lib/assistant/queue.js:10-12, 794-803. A task is cut for one tree; a later run can move the row to another tree, and the field follows, leaving no record of the tree before it.
The task's board row row = {path, branch, project, verdict, ahead, pr}, attached at read time by matching the task's worktree against the scanned rows lib/assistant/queue.js:1437-1449. Live: 232 of 576 tasks with a worktree get one; the other 344 name a tree the board no longer lists.

The job store The only durable-ish thread-to-tree link: a job carries thread and cwd, and it keeps 80 conversations, newest first lib/jobs.js:208.
The landed status The scanned row's verdict plus its pr: the same word the board's chart column shows, for every kind.

So the per-agent line would be blank on 125 of 128 agent lines today, and on the three that resolve it would be right once. The alternative - print the task's own project and verdict on every agent line - would say a stage run is in a tree it never touched. This module's own rule forbids that: a project is a NAME the record knows, never one derived from a neighbouring tree, because a guessed project reads exactly like a fact lib/assistant/queue.js:83.

What it would take

One recorded fact, written where the panel already knows all three values at once - linkTaskRun has the thread, the worktree and the project in its hand at the cut lib/assistant/queue.js:1216: 

threadTrees: { "<thread>": { path: "<worktree>", project: "<name>" } }   // additive, capped to the 20 threads
  • Write it in linkTaskRun (and when a stage run is linked), the same place threads grows.
  • Decorate at read time: for each thread, match its path to a scanned row and attach {project, verdict, pr, branchKindLabel} - the same shape the task-level row already has.
  • Draw on the agent line: project <name> · <verdict>, plus PR #n <state> when the row has one. A thread with no recorded tree draws nothing extra.
  • Old rows stay blank until their next run is linked. The 55 multi-thread tasks already on disk will not fill in retroactively - their trees were never written down.

The three directions

DirectionWhat a reader would seeCost
1. Record and draw (recommended) Each agent line gains its own project and landed word as its run is linked; turnover lines also name their PR. Existing rows stay as they are. Queue schema + writer + decoration + renderer + gate. One new field, additive.
