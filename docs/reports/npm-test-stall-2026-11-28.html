1. Reproduced on main, under a timeout

The file was exported from main as it stands, so the run measures main's bytes and not the branch:

mkdir -p base-main && git archive 2338e54f | tar -x -C base-main
cd base-main && timeout 300 node --test --test-reporter=spec test/worktree-assistant.test.js; echo EXIT=$?

All eleven tests answer and the file's own summary prints (the reporter emits it when the tests are done, not when the process exits):

...
✔ a tree's FIRST row event carries the owner, before any snapshot has overlaid it (6181.9956ms)
ℹ tests 11
ℹ suites 0
ℹ pass 8
ℹ fail 3
EXIT=124

EXIT=124 is the cap killing the run: the file never exited by itself. The instrumented run in section 2 shows the worker still holding the same two children at +30 s and at +240 s, with nothing else in its handle list, so the stall is static rather than slow. The same command in the worktree at HEAD, before the fix, behaved identically; reading the process tree at that moment showed the worker for the file with two server.js children still alive under it, and taskkill /PID on those two made the runner print and exit 1 within 8 seconds, long before its own cap. That is the whole diagnosis in one line: the file is not waiting on anything, it is holding two children, and it leaves as soon as they are gone.

This is the same file nine earlier suite runs on this machine are still parked on: nine test workers whose argv names test/worktree-assistant.test.js are alive right now, started between 00:23 and 04:40 today, each waiting on a panel it will never be told to stop. That is what "every full-suite verdict on this board today is a half-run" looks like from the process table.

2. The stop point, named

A probe was injected into the test worker only (NODE_OPTIONS=--import, guarded on argv naming the test file), wrapping child_process.spawn and ChildProcess.prototype.kill and appending to a file, because a hung test file's stdout is silence. The file has twelve panel boots; ten are reached on this run (two restart boots sit behind assertions that throw), eight of the ten are killed, and two are not:

So the point it stops is the worker process for this file: two ChildProcess handles plus their six pipes keep its event loop non-empty, and node --test isolates each file in a child process (--test-isolation=process), so the runner waits for an exit that cannot come. Named precisely:

  • The await: none. The last test (:413) resolves and its assertions answer; the file's report is complete.
  • The child process: yes, two of them. tools/panel-testkit.mjs:147 spawns server.js with three pipes; :216 is the only thing that kills it, and it runs only from panel.stop().
  • The port: no. Nothing was waiting on a port: a failed boot throws at tools/panel-testkit.mjs:180 after 25 s and every row read throws at :271 after 30 s, and all eleven tests had already answered.
The panel's own parent-watch cannot break the tie. tools/panel-testkit.mjs:154 sets PANEL_PARENT_WATCH_STDIN=1, so a panel exits when its stdin closes - but its stdin is the pipe the worker holds, and the worker cannot exit while that pipe is open. Each side is waiting for the other's teardown.

3. Why those two tests are the two that leak

They are the two tests that throw before their own panel.stop() line, and they were the only two of the eleven that booted a panel without tying it to the test's lifetime with t.after(() => panel.stop()). A thrown assertion therefore skipped the stop, and the child outlived the test. The third failing test (:190) throws too and was cleaned up, because it does register the hook - which is what made the mechanism visible rather than the failure count.

The three assertions fail on main at the same lines (148, 200, 259) and this branch does not change them. The trigger is a read-freshness contract rather than a lost write: /api/state answers the last built text and rebuilds behind it (server.js:994, SNAPSHOT_REFRESH_FLOOR_MS = 3000; routes/state.js:64 answers snapshotText()), so the read that follows a 200 from POST /api/worktree/assistant can still be the previous board. One probe, one sandbox panel, one write, three reads:

set: 200 answer.row.assistant={"id":"assistant-2","name":"Assistant #2","label":"Manager 2","role":"Manager"}
state immediately: {"id":"assistant-1", ...}
state +1.2s:       {"id":"assistant-1", ...}
state +4.2s:       {"id":"assistant-2", ...}
locks.json: { ... "owners": { "proj::1a2b3c": "assistant-2" } }

The write is durable, the route's answer is right, and the poll catches up on the next rebuild. The assertions are left exactly as they are: they fail on main, and re-cutting them to pass is the one thing this row must not do.

4. The fix (commit 5329a3c8)

  • The three tests that booted a panel with no hook now register one on the line after it, matching the other nine (test/worktree-assistant.test.js:157, :270, :315).
  • All twelve boots go through a local boot() that records the child (:44-:52), and a file-level after stops whatever a failed test leaves behind. That is the part that survives the next edit: a throw between boot and a hook can no longer strand a panel.
  • The file's header now states the rule and the stall it prevents (:19-:27).

No product code changed and nothing was weakened: same assertions, same timeouts, same eleven tests.

6. What this does not fix

  • 46 more files have the same shape. Of the 64 files under test/ that boot a panel, 46 call startPanel more often than they register a t.after(...stop()) hook (paths-http 5 boots / 1 hook, panel-restart 4/0, push-permissions 3/0, pipeline-source 3/0, port-guard 3/0, and so on). Each can strand a child the moment an assertion throws before its own stop; that is the class this row found, not a defect in one file. The durable cure is one place - a registry inside tools/panel-testkit.mjs, or a boot() every file shares - and that is a separate cut, because the kit is shared by all 64 files and by every live tree on this branch.
  • The three assertions. Pre-existing on main at the same lines; named above so the next reader does not read the file's red as this row's work.
  • The environment reds on this box. A worktree has no config.json (gitignored), so test/gateway-permissions.test.js dies ENOENT before its first test, and pipelines.test.js / push-permissions.test.js read the same file; the suite's tally below carries them. A git archive of main has the same hole, so they are not the branch's.
  • npm run absolute-paths is red on this turnover branch for three files this row did not touch (docs/reports/landing-cut-2026-11-28.html, docs/reports/wave-lane-counts/lane-counts.json, test/maintenance.test.js).
