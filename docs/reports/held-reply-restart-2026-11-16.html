A reply queued behind a live turn now survives the panel - held on disk, replayed in order, run once

The message a reader queues while an agent is still turning used to live in one browser tab's memory. It is now a record the panel writes before any turn exists, and the panel itself starts it when the thread is free.

Measured 2026-11-16, in .worktrees/make-a-message-queued-behind-a-live-turn-2dede9 at 12443a06 (main, version 1.110.0), on Windows 11 with node 26.12.1. The kill test ran on port 55129; the failing-first half ran on 53138. Neither 7331 nor 18083 was used, and the live board's listener count on 7331 was read before and after both runs (1 before, 1 after).

1. What actually happened before this change

The queue the reader sees is state.replyQueue in public/app.js: a Map of thread to entries, filled by queueReply, drained by drainReplyQueue on every job event for that thread. Entry shape: {text, at, attachments[path,name,type,bytes]}. Nothing on the server knew the queue existed, and no route accepted a message that was not already a turn. Three failures follow from that, and each one was traced in the code and then measured.

failurewhy, from the codewhat the reader sees
a node restart drops it public/app.js keeps the queue in memory only (no localStorage, no route). The attachment paths it holds are files under the panel's attachmentsDir, and nothing else names them. the message is simply gone. A reload of the tab loses it too, and the files it pointed at stay on disk with no referrer.
a refused send loses it in main's drainReplyQueue (line 4396) the entry is spliced out of the queue before sendReply is awaited, and the send's failure is swallowed (catch { /* sendReply reports its own errors */ }). a 409 (tree_busy, tree_released, the gateway refusing) removes the message from the queue and shows an error, and the words are gone.
the thread busy forever a restored card whose job carries a runId comes back live and pending (lib/jobs.js:1262), so threadBusy(thread) stays true and the drain returns on its first line. Only a settle event or a manual action frees it. the queued reply never goes out; the card keeps promising "queued 4m ago" while nothing will ever send it. The same job also keeps its tree's other threads out (jobs.busyFor is thread-then-tree).

The one path this change leaves alone: the live-run re-attach path. A run the panel did not start, or one it was watching when it died, is re-attached and settled by lib/jobs.js exactly as before (reconcileRestored, stopStaleRuns, the orphan sweep). The held replay runs after that chain and never touches a live card - it only starts a record whose thread jobs.busyFor already calls free.

2. What the change is

2.1 The record (lib/held-replies.js, new)

state/held-replies.json, one file for the panel: {version, seq, savedAt, replies: [{id, seq, thread, text, attachments, at, state, jobId, why, sentAt}]}.

  • Written before the turn - persist() is a synchronous tmp-write plus rename, not the queued async writer the job store uses. A write that lands a few milliseconds later is exactly the window this record exists to close. The file is small, so the cost is sub-millisecond on the press that starts a turn.
  • Arrival order - seq is minted from the store's own counter and is what the replay walks; at is the page's clock, kept only for the card's "queued 3m ago" line (two presses in one millisecond share it).
  • Idempotent by id - add({id}) for an id it already has is a no-op that returns the existing record, so a retried POST cannot queue the message twice.
  • One claim - claim(id) flips held to sending synchronously and answers null to every later caller. That is the whole dedupe: the page's drain and the panel's own replay can both ask, and only one gets a record back.
  • States held, sending, sent, cancelled. sent carries jobId; held and sending are the two a replay may look at; an unknown state read off a hand-edited file reads as held.
  • Boot repair - reconcile(jobFor) settles the one window a crash can leave: a record sending whose id a job carries becomes sent with that job id (the turn happened, do not start another); one with no such job goes back to held with the reason named.
  • Caps - 200 records, and the newest 40 terminal ones; a record still owed a turn is never dropped. A file that cannot be parsed is left untouched and no hold is replayed out of it.

2.2 The routes (server.js)

routewhat it does
GET /api/held-replies[?thread=]the records, the counts (including open), the file path. Read by the page once after its first snapshot.
POST /api/held-replies {action:"add"}writes the hold. 404 for a thread this panel does not have, 400 for no words. Then fires a drain pass, so a free thread starts it at once instead of waiting for the clock.
POST ... {action:"edit"|"cancel"}the reader's edit and x, written through so the record the panel would replay is the message the reader last saw. A claimed record answers sending rather than pretending.
POST ... {action:"send"}asks the panel to start that record's turn. 202 with the job; 409 with gone:true when the record was already settled; 409 held-waiting when it could not start, with the reason.

2.3 The one acceptance

A replayed hold does not get its own way into a tree. It goes through startThreadReply - the same function POST /api/agents/reply uses - with the hold's id in origin.heldId on the job, and the attachments rebuilt from the record with inheritAttachments/inheritanceBlock (lib/attachments.js, the one attachment convention). The id is persisted with the job, which is what lets a later boot answer "is there a job for this record" without a second store.

startThreadReply gained two arguments, attachments and attachmentBlock, passed straight to jobs.create: the card's chips and the block the run's input carries. A page-started reply passes neither, so its text - which already contains the page's own block - is unchanged.

2.4 When it runs

  • On a settle - a job event whose status is no longer live, when the store has anything open (heldReplies.openCount(), a loop over a few hundred records and free when the store is empty).
  • On the clock - one pass every 2s only while something is open; the timer is cleared the moment the store is clear, so a panel with nothing held has no timer at all.
  • At boot - replayHeldReplies() after reconcileRestored and stopStaleRuns: repair, then start what can start, in seq order, one turn per thread per pass.

2.5 The page (public/app.js, public/core/sse.js)

  • queueReply POSTs the hold (fire-and-forget, kept on the entry as entry.held) and entry.heldId is the panel's id.
  • drainReplyQueue no longer takes the entry out before the send. It marks it sending, asks the panel to start the record (or sends the words itself when the write-through never landed), and removes the entry only when a turn exists - or when the panel answers gone, which means the panel already settled it.
  • The x and the empty-save now cancel the record; an edit writes the new words to it.
  • applyHeldReplies reconciles the page's queue with the panel's: settled records come off, records the page does not hold (a reloaded tab, a panel that replayed while it was away) go back on. It runs once after the first snapshot and on each held-replies event.

Why the restart is the hard case and not the easy one: the gateway is told the run finished while the panel is down. So the boot finds a record owed a turn and a run it must settle first - if the replay ran before the reconcile, or if it trusted its own memory of "busy", it would either start a second run on a live thread or wait for ever. The order in the boot chain is what makes that land: reconcileRestored -> stopStaleRuns -> the held replay.

4. The bug this work found in itself

The first draft of drainHeldReplies never started anything after a settle, and the kill test found it in one run: a pass that ends synchronously (every thread busy, which is the normal case behind a live turn) cleared the in-flight flag inside its own body, and the assignment that stored the promise then put the settled promise back. Every later pass returned that stale promise and did nothing. The fix is to clear the flag from the promise's own .finally, scheduled after the assignment, and the reason is written in the code so it is not undone.

This is the shape of failure a unit test cannot see: nothing threw, nothing logged, and the clock ticked every two seconds into an empty function.

6. What is deliberately not in this change

  • No push grant and no lifted record. Nothing here asks the panel to allow a push it would otherwise refuse; the branch is landed as a pull request.
  • No new UI surface. The card the reader already has ("queued") is the card; what changed is that its entry now has a record behind it. A settled-elsewhere record simply comes off the queue on the next reconcile.
  • No gateway-side change. The panel still refuses a second turn on a live thread; the hold waits for jobs.busyFor to say free rather than trying to make the gateway queue it.
  • The live panel on 7331 was never restarted, steered, or touched. Both runs measured its listener count before and after.

The answer

A message queued behind a live turn is now written to state/held-replies.json before any turn is accepted, replayed at boot in arrival order, and started through the same acceptance the reply route uses - with its attachments, and exactly once, on a port that is neither 7331 nor 18083, across the death of the node process that was holding it.

42 of 42 checks pass after the change; the same gate reaches 7 of 9 on main and stops at the first write, because main has no place to put the message.
