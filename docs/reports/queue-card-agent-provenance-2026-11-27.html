The queue card: whose project, whose landing

1.187.0 - each agent line now carries the project and the landed verdict of the tree THAT thread ran in, recorded at the link. Measured, and honest about the rows written before the record existed.

A task keeps ONE worktree, and every later link moves it. So the card could only ever name the tree the row points at NOW: on a task carried by five agents, four of their trees were simply not on the record. Each thread's tree is now written at the link (threadTrees), read back through the board's own row, and drawn on that agent's line as project <name> · <landed verdict> plus its PR when the tree is a turnover branch. A thread nobody recorded a tree for draws nothing - never the task's project as a stand-in.

What was built

1. The record, at the link

threadTrees: { "<thread>": { path: "<worktree>", project: "<name>" } }

Written by linkTaskRun, the one place the panel holds the thread, its worktree and its project at once lib/assistant/queue.js:1249-1282, called by the spawn path at lib/assistant.js:2845. Additive: a link with no tree leaves what was recorded for that thread alone, the map is normalised against the thread list (an entry for a thread that fell off the cap is dropped), and an entry with no path is dropped entirely. Absent on every queue file written before this cut.

2. The read, per thread

decorateTasks attaches agentRows, one entry per thread in the order of threads lib/assistant/queue.js:1616-1670: the project, the landed verdict (MERGED (n commits), UNMERGED (n), NO COMMITS, ON MAIN ...), the pr when the tree has one, and its kind label. A tree the board no longer scans keeps the project the link wrote and says nothing about the landing. A task with nothing recorded carries no agentRows at all, so six hundred rows do not ship six hundred arrays of nulls.

3. The line, and the meta line stepping aside

The sentence rides the agent's own line, after its thread and before its run pill public/queue-cards.js:462-476, 524, so a narrow card keeps the agent's name and loses the tail of the sentence first public/style.css:7026-7030. When at least one agent line carries the facts, the task-level meta line steps aside: it names the tree the row points at NOW, and printing it under lines that already say where each agent worked would be the same fact a second time. With no per-agent record, the meta line draws exactly as it did before, so no card regresses.

Three agents, two recorded trees in two projects and one thread nobody recorded: project agent-worktree-gui · UNMERGED (2 commits), then project poc-guidelines · MERGED (3 commits) · PR #373 open, and the third line bare. The meta line is gone because the lines carry it; the pipeline row stays under the facts block.

What a reader will see, and when

  • New rows: the first run linked after this cut records its tree, so its agent line carries the project from the first paint and the landed verdict as soon as the board has scanned that tree.
  • Old rows: the 55 multi-thread tasks already on disk have no threadTrees, so they draw the meta line exactly as before. Their trees were never written down and cannot be recovered from the 80-conversation job store - the card keeps saying nothing rather than something wrong.
  • Retries on one tree repeat the same project and verdict on each line. That is the cost of a self-contained line: a reader scanning one agent's row never has to look up to another row to know where it worked.
  • Research and implementation trees land by merging locally, and their verdict says so (MERGED (n commits)) with no PR; a turnover tree adds PR #n state. One word for the landing, whatever the kind - which is what the board's verdict column already means.
