1. The two verdicts

Picture Viewer: no. It cannot start a standalone oauth2-multi sign-in.

It can consume a gateway session that already exists when the page is opened top-level: GETAUTHMODE reports sso:true from the cookie's presence (PictureViewerActions.java:291-296) and the page then mints a Picture Viewer token through getTokenSso (login.js:50-53). What is missing is any way to create that session. There is no JwtAuthFilter in the deployment descriptor (WEB-INF/web.xml:3-16 declares only the PictureViewer servlet), no server-side redirect to /oauth2/login, and index.jsp never renders a window.SEFL_AUTH block; the only producer of that block is Menu (SsoAuthJson.java:75-102, seflSessionGuardian.js:500-515).

Where it stops: login.js:45-58. With no window.SEFL_AUTH in any frame and no cookie, getAuthMode returns sso:false; if the migration window is closed the same response has legacyAuthAllowed:false, and the code calls showSignInThroughMenu() (login.js:188-194). The login dialog's only button does the same thing (login.js:360-372). Inside the window the legacy branch needs a Menu opener with a stored password (login.js:60-67, 161-180), which a standalone visitor does not have.

The Menu path works when all three conditions hold: Menu is in SSO mode, Menu and the app are same-origin so window.top.SEFL_AUTH is readable, and the SEFL_AUTH_TOKEN cookie reaches the servlet so the server-to-server call to /oauth2/session succeeds. The third condition is the one I could not test here.

Picture Manager: no, and it cannot even consume an existing gateway session top-level.

The SSO branch in mounted() is gated on being framed: window.top && window.top !== window && window.top.SEFL_AUTH (src/App.vue:99). When the page is the top window that expression is false, and the else branch it falls to is also framed-only (src/App.vue:129-130). A top-level visit does nothing at all: no mint, no error, no domain list. With a valid gateway cookie on the request the page still does nothing, because getTokenSso() is only reached from the framed branch (src/App.vue:105) and re-checks the frame itself (src/App.vue:114-116).

Where it stops: src/App.vue:99, then 129-130. Framed by something that is not Menu, it shows "Need to access through Menu for authorization." (:132-134). That message is the whole standalone story.

The Menu path works only inside the Menu frame. The token is minted and then discarded: the success handler goes straight to getDocumentation(...) (:121-124) and never stores the token, and the seflMenuUsername key passed to axios (:174) is not a header, so axios ignores it. What actually authenticates the later upload is not established by this change (see finding 13).

5. Session and cookie handling

  • Nothing in either app creates or refreshes a gateway session. No call to /oauth2/session/renew, no /oauth2/session/app/register, no guardian-lite.js. The gateway's logout and revocation are invisible to both apps.
  • The app token outlives the gateway session. TOKEN_LIFESPAN is a fixed 20 minutes (PictureViewerJwtUtils.java:40); neither SsoSessionClient nor ValidateSsoUser carries the gateway's expiresAt. The worst case is a 20-minute window after logout or revocation.
  • Picture Viewer's Logout is local only. processLogout clears localStorage and the UI (login.js:321-328); it does not call /oauth2/logout and does not clear the cookie. The next Load finds the cookie and silently mints the same identity again.
  • A stored token wins over a different SSO user. checkForAutoLogin accepts any stored token whose exp is in the future (login.js:35-40, 399-417) without comparing it to the current claim. On a shared workstation the previous user's token, and the previous user's domain permissions, survive for up to 20 minutes.
  • Cookie lookup is name-only and plain-name-only. authCookie returns the first cookie called SEFL_AUTH_TOKEN and ignores path and duplicates (SsoSessionClient.java:91-102). The gateway can also issue SEFL_AUTH_TOKEN__<clientId> (SsoCookieHelper.java:42-68), which this code never reads. Menu uses the default client, so today this is latent.
  • The gateway is contacted over a URL derived from request headers. X-Forwarded-Host first, then getServerName() (SsoSessionClient.java:146). The cookie is then sent to that host (:115). A host value beginning with localhost keeps the scheme at http (:150-153), so a crafted value such as localhost.attacker.example would send the live token in clear text.
  • No HTTP session is involved. The servlet is stateless for this flow; web.xml:17-21 sets a 10-minute session timeout that the SSO path does not use. Good for fixation, irrelevant for revocation.

Why rank 3 matters more than its trigger suggests

Menu only emits window.SEFL_AUTH when the gateway stamped a SAM claim (SsoAuthJson.java:75-82), so in a healthy same-origin frame the claims and the cookie appear together. The dangerous cases are the ones where they do not: a cookie scoped to a different host, a cookie dropped by SameSite, a cookie cleared while the page stays open, or a Menu page rendered in SSO mode in front of an app on another vhost. In every one of those the client takes the SSO branch, gets an error, and the legacy path that would have worked is never tried. Picture Viewer's accessControl.js:334-337 has the same shape with an explicit OR.

Why rank 4 is a legacy break, not a retirement

Inside the migration window the server deliberately keeps GETTOKENOAUTH and GETCLIENTID alive (Actions.java:255-265, 300-309), but the page removes both entry points: the dialog no longer calls getOauthClient (login.js:360-372) and index.jsp no longer reads access_token (:38-41). landing.html:43 still builds ?access_token=..., so an old Azure redirect now lands on a page that ignores its token. The window's promise is "legacy still works until the date"; for the Azure form it does not.

11. Delta between the pinned commit and the PR head

The PR's current head is 37f19ca ("identity from the gateway employeeID claim, with SsoSessionClient tests"), one commit after the pinned 49f3ae7. The delta does not change either verdict.

  • Identity: preferredUsername is no longer used as an employee-id candidate; a pre-G3 session now goes straight to the LDAP lookup (SsoSessionClient.37f19ca:61-74). This removes the only use of preferredUsername and makes the PR description true at the head.
  • Null handling: a new optionalString treats a JSON null like an absent field (:100-108). The behavior at 49f3ae7 was already safe because trimmed(null) returns "", and my 1.5.4 probe shows optString does not produce the string "null". The guard is harmless; the comment's reason is wrong. This is finding 19.
  • Tests: UnitTest_SsoSessionClient adds 7 tests over the claim precedence, the missing-SAM and unauthenticated branches. It does not cover fetchSession, the URL construction, the cookie scan, or the servlet action. The suite is 18 tests at the head and green.
  • Style: the new comments use em dashes where the rest of the file uses hyphens. Cosmetic, but it is the only place in either change where the punctuation changes.

12. Bottom line

Neither app can sign in with oauth2-multi as a standalone consumer. Picture Viewer can reuse an existing gateway session when opened top-level, but it cannot create one; Picture Manager cannot even reuse one, because its SSO branch only runs inside a frame. The Menu path is the designed path and the code says so: the specification describes the browser as "Picture Manager inside SEFL Menu", and both clients read Menu's window.SEFL_AUTH rather than a token Menu hands them.

If standalone is a requirement, it is a design change, not a bug fix: install the gateway's JwtAuthFilter with a loginUrl so an unauthenticated top-level request is redirected to /oauth2/login, render the sefl.auth.* attributes into window.SEFL_AUTH on the app's own page, and remove the "sign in through Menu" dead end. That is the pattern the gateway's integration guide documents for a standalone consumer (sections 3, 3b and 5c of INTEGRATION-jwt-auth-filter; 5c is the gateway-served sso-guardian-lite.js that registers the app session and renews it top-level). I have not written that change, as instructed.

The defects that would bite before then are the fallback loss (3), the dead Azure form inside the window (4), the shared-browser token inheritance (5), and the 20-minute token that ignores gateway revocation (6). The rest are medium and low: error text, cookie presence, the fail-closed row, the two clocks, the LDAP dependency, the discarded PMW token, and documentation drift.
