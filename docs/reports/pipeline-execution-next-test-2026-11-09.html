Pipeline execution: the landing stages, and the terminal state without SEFL merge rights

What the shipped landing ladders do on git.sefl.com and GitHub, the furthest state a user without SEFL merge rights can reach, and the next test that would prove it. Measured against 15368d8f (1.76.24), 2026-11-09. No product code was changed to produce this page.

The short answer

On git.sefl.com the ladder can open the pull request and stop: without merge rights the merge POST is refused, and the panel has no terminal state for that refusal, so the row reads running and is shown STALE. On GitHub the same person reaches MERGED and main moved, because --admin is the repository owner's ruleset bypass. The next test is the SEFL approval-to-refusal walk: prove a wait that wakes on a comment, an approval at the head, one refused merge, and a parked row, not a stale one.

1. What ships

Three landing ladders are in pipeline-bundle.seed.json. They are not three versions of one shape: they have different stages, different last stages, and different words for "landed".

Sources: pipeline-bundle.seed.json lines 3803 (turnover), 4144 (github-force-merge), 4427 (sefl-review-loop); stage artifact kinds at lines 4471, 4500, 4530, 4594 and 4623. The turnover prompt is at its pr stage, line 3869.

The one word the driver acts on is the last stage's artifact kind.

All three ladders end on a kind: "pr" artifact. A stage that declares any other kind is finished by the driver on its own verdict; a stage that declares pr is left to the settle's landing rule, and that rule accepts exactly one verdict, MERGED (lib/task-pipeline-drive.js:30, :2196; lib/assistant/queue.js:1563). So the ladder that says "leave it open" cannot finish on an open PR either. That is the root of every terminal-state problem below.

3. What the executor actually tests

Four facts decide every terminal state below. Each is read from the code that runs, not from the prompt that asks.

  1. A stage advances on its run and its artifact, not on its gate. A gate is a barrier only when it carries a decision record: gateAfter finds a gate with isObject(gate.decision), and the driver parks until that file is written (lib/task-pipeline-drive.js:849). A gate with no decision is a pause, and a pause is not a check. Every gate in sefl-review-loop has verified_by but no decision, so every gate in that ladder is a pause.
  2. The PDL stage carries no exit, and the review timer reads only exit. reviewWaitFor starts with stage.exit.check and accepts only pr-comments, pr-approved or reviewers-exact (lib/pipelines.js:586, :667). A PDL stage declares an artifact, not an exit. The ladder catalogue the timer reads, pipelines.json, ships "pipelines": []. So the sentence "the panel re-checks on its own clock" in the wait prompt has no reader in the PDL path. The test that covers the timer says so in its own comment: the review loop is a PDL document, "a PDL stage names the artifact it writes, not the check that ends it, so the ladder timer has nothing to read for a PDL pipeline" (test/pipeline-wait.test.js:61, :144).
  3. The only host fact read at the end is the tree row's verdict. When the last stage's artifact is pr, driveTaskPipelines leaves the row to settleTasks; a run that ended done finishes the row only when the tree reads MERGED. Otherwise the settle returns the row untouched: if (!merged) return t; (lib/assistant/queue.js:1563). The row keeps state: running and the board derives STALE from the dead run. That is not a terminal state; it is the absence of one.
  4. The walk of the shipped SEFL document skips address. A walk with the panel's own nextStageOf gives branch → push → pr → wait → approve → merge → done. At wait the document offers H-04 (a loop to address) and H-06 (a sequence to approve); the rail rule takes the sequence, so H-04 and H-05 are never crossed. The design document says the loop is wait → address → wait → approve (docs/pipelines.md:319); the executable document does not draw that walk.
What a gate without a decision does. It is not a failure and it is not a wait: it is a sentence in the document that the driver does not read. The decider field says machine or reviewer, but the driver's test is the presence of the record, not the word.

4. The terminal states

"Terminal" here means a state the panel records and a reader can see: done, parked, or a host state the row names. "No terminal" means the run ended but the row cannot finish, so it reads running and is displayed STALE.

4.1 Why SEFL stops at OPEN

Bitbucket's permission model is the wall, and it is a wall of two different heights. Repository read lets a user clone, comment, and create a pull request when read is held on both the source and the target; repository write adds pushing and merging. On top of that, a branch permission can restrict who may update the target branch, so a user can hold repository write on a feature branch and still be the wrong person to merge into master. A merge POST from that user answers 401 or 403. The host may also refuse on its merge checks, for example when the required approval is missing; the status is different but the outcome for the panel is the same, because the merge stage has one instruction and no branch for a refusal.

The panel's own SEFL doctrine is stricter than the permission: "A human reviewer may take a day... report the PR id and its URL and stop there. Do not merge it" (hosts.seed.json:45). The review loop's merge stage is a reader-named departure from that doctrine, the same way github-force-merge departs from the GitHub doctrine. For a user without merge rights, the departure cannot execute: the doctrine and the host agree, and the ladder is the part that is wrong.

4.2 Why GitHub reaches MERGED

The GitHub ladder's merge stage says gh pr merge --rebase --admin. --admin is not a preference; it is the bypass actor on the repository's Owner only ruleset (id 25783530), and the owner's token reports current_user_can_bypass: "always" (docs/pushing-to-a-remote.md:214, :224). The same person who has no SEFL merge right can therefore land on GitHub, because the right that matters there is repository ownership, not SEFL group membership. If the ladder is run by an account without the bypass, it falls to the same stall as SEFL: the merge is refused, the PR stays OPEN, and the landing rule leaves the row running.

4.3 The generic turnover is the quiet case

turnover is the ladder that says "leave it open". Its last stage declares kind: "pr", so the last word is still the landing rule, and the landing rule still demands MERGED. A correctly open turnover PR is therefore not a finished row: it reads running and STALE on both hosts. The document's intent and the executor's finish condition disagree. This is not a SEFL-only problem, and a fix for the refused merge should cover it with the same word: a pr stage needs a landing outcome that can be OPEN by design, not only MERGED.

5. Two gaps the stage map exposes

5.1 The review loop cannot answer a comment

The design document describes the loop as wait → address → wait → approve, with the answer stage returning to the wait after every push. The executable document draws H-04 as a loop from wait to address and H-06 as a sequence from wait to approve. The driver's rail rule takes the sequence when both exist, so the walk is wait → approve and address is dead. No gate routes the other way: G4 carries no decision and no routes. A reviewer's comment can therefore arrive, be read once, and never be answered; the ladder walks on to the approval stage and then to the merge.

Evidence: nextStageOf on the shipped bundle returns wait -> approve H-06 sequence; docs/pipelines.md:319 names the loop the document does not draw; pipeline-bundle.seed.json H-04 and H-06 are at lines 4679 and 4696.

5.2 The conversion dropped four checks

The design's exits are stronger than the PDL gates. The PR stage is supposed to check pr-open, pr-head and reviewers-exact; the gate checks pr-open only. The wait is supposed to exit on pr-comments or pr-approved; the gate names pr-comments only. The address stage is supposed to check pushed and pr-head; the gate checks pushed only. The merge is supposed to check pr-merged and main-moved; the gate checks pr-merged only. Each dropped check is a fact a reviewer relied on: exact reviewer set, the PR head the approval belongs to, and the main branch the merge was supposed to move.

Evidence: docs/pipelines.md sections 2.1 and 2.2; pipeline-bundle.seed.json gates G3, G4, G5, G7; test/pipeline-wait.test.js:144 names the missing exit as a known gap.

6. The next test

The next test is the SEFL approval-to-refusal walk. It is the first test that drives the shipped sefl-review-loop through the panel's own clock, with a host that approves at the head and refuses the merge. It is deliberately the SEFL ladder, not the GitHub one: this delivery is itself a live run of github-force-merge (commit, push, PR, --admin merge), so the GitHub path is being exercised today. The SEFL path is the one with no evidence and no terminal state.

Setup

Harness: Assistant.sweepQueues on a temporary queue, the shipped pipeline-bundle.seed.json, a scripted seat that writes each stage's declared artifact, and a stub host. New files: test/pipeline-landing-sefl.test.js and test/fixtures/sefl-landing-host.mjs.

Host fixture: PR 42, state OPEN, head b7c1... (the pushed commit), two comments at 10:05 and 11:20, reviewers [code_review_java], an approval at the head at 12:00, and a merge endpoint that answers 403 with You do not have permission to merge pull request 42 into refs/heads/master. The live half uses a SEFL branch permission that excludes the worker from master; the fixture is the repeatable half.

Pass criteria

  1. P1 Reach: with no comment, the stage order is branch, push, pr, wait, approve, merge. With a comment newer than the wait's lastSeen, the next sweep enters address after wait, then returns to wait. No stage is skipped, and H-04 is crossed at most 3 times.
  2. P2 PR shape: exactly one PR is created, reviewers are exactly ["code_review_java"], the description has all four sections, and fromRef.latestCommit equals the pushed head.
  3. P3 Wait registered: the tree record carries pipelineWait with check: "pr-comments", every: 3600000, the thread and the branch, attempts: 0, and no live hold. A second sweep in the same stage does not restart the hour.
  4. P4 Comment answered: the address run pushes exactly one commit and replies on the comment's id naming that commit. A comment older than lastSeen does not start it.
  5. P5 Approval at the head: an approval at an older commit does not advance. An approval whose lastReviewedCommit equals the current head advances to merge, and the stage record names the reviewer and the sha.
  6. P6 Merge refused: exactly one merge POST is made. The 403 and its message are recorded in a machine-readable merge record. pr-merged is not written, and the PR is still OPEN.
  7. P7 Row terminal: the row ends parked with a reason beginning merge-refused: and the host's sentence. It is not running, not done, and not displayed STALE. The board still shows the PR URL.
  8. P8 Live half: on a real SEFL repo, master's sha before and after the run are equal, the PR is OPEN with the approval at its head, and the park reason quotes the host. This is the only criterion that needs a repo owner to set the branch permission.
Expected today. P1 (no-comment case) and P2 can pass with the current worker prompts. P1's comment case, P3, P4, P5, P6 and P7 fail: there is no wait registered, address is unreachable, the approval gate is a pause, the merge refusal is prose, and the row reads running/STALE. A test that passes all eight today would be testing the fixture, not the pipeline.

Falsifiers. Any of these fails the test: a second PR for the same branch; a reviewer set that is not exactly code_review_java; a merge POST retried after the 403; pr-merged written without a MERGED read; the row marked done; master's sha moved; or a final message that claims the work landed.

7. The work the test implies

Ordered, smallest useful cut first. W1 and W2 are what make the test's review half possible; W3 and W4 are what make the refusal terminal; W5 is the test itself; W6 is the live evidence.

  1. W1: bridge a PDL review gate to the ladder wait. Teach the loader or reviewWaitFor to derive an exit from a gate's verified_by when it is one of pr-comments, pr-approved, reviewers-exact; teach the task driver to register that wait on the row's tree when a stage with such a gate starts, so lib/jobs.js's timer can wake the thread. Files: lib/pipelines.js, lib/pipeline-bundle.js, lib/task-pipeline-drive.js. Test: test/pipeline-wait.test.js. Size: medium, because it is the first time a PDL stage feeds the ladder timer.
  2. W2: route a comment to address. Give G4 a decision record with outcomes comment and approved and routes comment → H-04, approved → H-06, or change the graph so the loop is the sequence and the approval is the conditional. Without this, address stays dead no matter what W1 does. Files: pipeline-bundle.seed.json, lib/task-pipeline-drive.js. Test: test/pipeline-truth.test.js (a walk of the shipped seed: wait → address on a comment, wait → approve on an approval). Size: small.
  3. W3: make the merge outcome machine-readable. Change the merge stage's artifact to JSON with status (merged or refused), http, hostMessage, pr, head, mainBefore and mainAfter. The worker writes it; the driver reads it. Files: pipeline-bundle.seed.json, lib/task-pipeline-drive.js. Size: small.
  4. W4: park on a refused merge, and finish an open-by-design PR. In the driver's finish path: a refused merge sets parked with merge-refused: <host sentence>, never pr-merged; a pr stage whose document says the PR stays open finishes done on OPEN, not only on MERGED. The second half also fixes turnover. Files: lib/task-pipeline-drive.js, lib/assistant/queue.js. Size: small, but it touches the settle, so it needs its own unit test.
  5. W5: write the test. The fixture host, the scripted seat, the eight assertions, and a ledger that names the run, the stage and the verdict at each step. Files: test/pipeline-landing-sefl.test.js, test/fixtures/sefl-landing-host.mjs. Size: medium.
  6. W6: run the live half. Pick a scratch SEFL repo, set a branch permission that gives the worker read on master and write on the branch, open one throwaway PR, record master's sha before and after, and let the refusal happen. This is the only step that needs a repo owner; it is also the only step that proves the 403 path against the real host. Size: small once the permission exists.

8. Limits of this report

  • The 403 is a code-path claim, not a captured SEFL response. The next test exists to replace it with a real one; P6 is the fixture half and P8 is the live half.
  • This report does not prove the current account lacks merge rights on any specific repository. The Bitbucket permission model is cited from the vendor's own documentation, and the branch-permissions endpoint answered 401 to the token used here, which is a read-scope limit and not a permission verdict.
  • It does not test github-force-merge. That ladder is being run by this delivery, and the PR it opens is the evidence; the report does not claim a separate test for it.
  • It does not fix anything. It names the gap, the test that pins it, and the work the test implies.
  • The stage count and the walk are from the shipped bundle at 15368d8f. A bundle edit changes the map; the test in W2 is what keeps the drawing honest.
