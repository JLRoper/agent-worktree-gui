1. What moved, and what stayed

The row is one cut of the module-separation plan: the initiative writes leave routes/initiatives.js for routes/initiatives-write.js, a pure move, with the parent still answering the same five exports. The plan's card for this file (entry 18 of docs/reports/module-separation-2026-11-28.html, read from 2ffacfef) names two files for two rows and gives the write half as lines 626-1,212 of a 1,212-line file: "the tag registry, create, the note log, the one write that asks, and archive". That range is the whole request dispatcher from the tag registry's own banner to the prefix's 404, and it is what this row moved.

The row's sentence about the dependencies is the seam: "the handler already receives every dependency through its options object". createInitiativesRoutes is that options object, so the new module is a factory that takes the same names and returns the same dispatcher, and not one line of the moved code had to be rewritten.

What stayed in routes/initiatives.js:

  • routes/initiatives.js:90 INITIATIVES_PATH and :92 TAGS_PATH, the two constants the prefix and the mount table match on;
  • routes/initiatives.js:147 initiativesView, the fold the tab draws, and :402 archiveBlockers, the liveness the archive refusal names;
  • routes/initiatives.js:438 createInitiativesRoutes, its option guards, and the read's memo - cachedView, rebuildView, dropView (:695) and viewStoreKey;
  • routes/initiatives.js:701 the composition, and :724-:731 the prefix guard and the one-line delegation.

What went to routes/initiatives-write.js: the tag registry's four verbs, the GET with its ?profile=1 branch and the method guards, the body parse, create, the words, the note log's add/edit/delete, the reader's order, the move that asks, archive and restore. routes/initiatives-write.js:21 is the factory, :43 the dispatcher, :44 the tag banner - the first of the 585 moved lines.

The GET travels with the dispatcher because the card's range takes it: it sits between the tag registry (whose four verbs are the reason the guard is not a plain GET guard) and the writes, and separating it would have meant reordering the handler, which is a rewrite rather than a move. The read's own half - the fold and the blockers - stays in the parent for row 516, which is the plan's other new file.
