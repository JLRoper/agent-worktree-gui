2. Why a long SPAWN line can be dropped with no record

It is not a length limit in the parser. Both stored lines were replayed through the REAL parser at the branch head's parent: each returns exactly one spawn action. The 2,987-character line yields a 2,000-character prompt ending in an ellipsis; the 2,245-character line yields 1,518 characters, uncut. So the grammar read both lines, and the drop happened after the parse.

- 5201acfb  prose len 4699  spawn 1  target "agent-worktree-gui" taskId 396  prompt len 2000  tail "...pus..."
- d4ffae65  prose len 4697  spawn 1  target "agent-worktree-gui" taskId 395  prompt len 1518  tail "...do not land."

Four separate holes made that drop invisible, and one of them made it likely:

2.1 The only per-line record is a journal line in a 300-entry ring

A started SPAWN writes spawned; a refused one writes spawn-refused, spawn-skipped, spawn-failed or spawn-draft. None of those raises a card. The journal is capped at 300 entries (lib/assistant/config.js:290, trimmed in lib/assistant.js:4328), and when this row was filed its oldest entry was 2026-11-27T23:58:18Z - after both turns had ended. The record existed; it had rolled out. From the reader's chair that is "no journal line".

2.2 The record that catches an unread line is switched off by default

The command audit journals an unparsed command and raises a red card for a parsed line nobody carried out, but auditMode() answers "off" unless the reader changes the setting (lib/assistant.js:7559), and openAudit returns null in that mode. The live store's commandAudits array is empty. So on the panel as it ships, a SPAWN line that parses to nothing leaves no card and no command-unparsed line.

2.3 The spawn watchdog only re-read turns on Assistant #1's thread

checkSpawns re-reads finished turns to find a SPAWN the harvest missed, and it filtered on j.thread === ASSISTANT_THREAD. Both dropped lines were Assistant #3's turns (panel-assistant-3), so the one pass that would have found them never looked.

2.4 A spawner that returns nothing was silent, and a long brief lost its tail

In the spawn loop, a spawner that resolved with no job and no card hit if (!j?.id) return;: the line settled as if carried out, and no journal line said otherwise. Separately, the parser clipped every SPAWN brief at 2,000 characters (clip(sp[2], 2000)), which silently cut the acceptance half off the 2,987-character line - measured above as the prompt ending in an ellipsis.

What settled them "skipped". The spawn intent is written before the line runs, and exactly two code paths settle it "skipped": the queue-row refusal and the spawn switch being off. The spawn switch was auto on Assistant #3 (assistants/assistant-3/settings.json), so the reachable path is the row refusal, which does write spawn-refused. That line is therefore the record that rolled out of the ring in 2.1. The exact refusal sentence is not recoverable from the store; what is recoverable is that the line was parsed, that the panel decided against it, and that the decision was written only into a rolling journal with nothing on the board.

3. Why a spawn can pick an existing stale tree instead of cutting

There is an explicit reuse recommendation, and it is where the short line went: lib/spawn-reuse.js reuseDecision, called from lib/features/spawn.js before a plain SPAWN cuts. Its rule is "an UNFINISHED tree whose task words overlap this one", and unfinishedTree counts a tree as unfinished when it has commits of its own, uncommitted files, or a live run. A dirty tree is therefore a candidate by definition. The fit of the tree to take a NEW worker - is it clean, has main left its base behind - was never asked.

For the #400 line the overlap was three words the two rows happen to share: the tree's directory is row-677-detail-is-in-the-queue-file and the brief says "Row #400 in my queue is the complete brief ... detail ... queue". The job record preserves the decision: origin.reused.shared = ["detail","queue","row"]. The tree was 0 commits ahead of its own base, 3 files dirty, and its base was weeks behind main - which is exactly the state unfinishedTree reads as "worth reusing".

The second half of the same trap is the base ref: a project that names a turnover branch was cut from it unconditionally (makeWorktree, turnoverStartRefOf), even when the branch had already landed and main had moved on. That is how children end up on a dead branch.

6. Not changed, and why

  • A refused SPAWN still raises no card; it is a journal line plus the digest. The row asked for a record, and a card per refused line would be noise. Making the digest line louder is a separate change.
  • The pre-flight route GET /api/assistant/spawn-check reads the queue, the job store and the scanned rows only; it does not run git. The fitness refusal is measured at the cut, where git is. A pre-flight field for "this tree is dirty" is a follow-up.
  • The stale threshold (50 commits) is a judgement written in one place, TRIVIAL_BEHIND. It clears same-day drift on a board that lands 20+ commits a day and still catches every weeks-old tree.
  • The parser still collapses whitespace in a brief (clip). A brief written on one line is unaffected; a multi-line brief is still flattened, as before.
