6. Two defects this round put on the table

D1. The wake runs the next stage in the wait stage's tree and thread

lib/jobs.js checkPipelineWait hands the wake the waiting stage's thread: wake({ tree, thread: claim.wait.thread || null, ... }). On this round that meant the address brief for comment 12789 ran as job 69458a89 with its cwd set to the stage-4-wait worktree and the wait thread's id. Its commit still landed (the round tree was fast-forwarded to it), but its failure was stamped on wait#2 and the ledger lost a whole stage. A stage's work should run in the stage's own tree. The evidence is one queue entry: wait#2 failed with job 69458a89, while address visit 2 is commit 6c2f7f2 in the same tree.

D2. A declined pull request cannot be found by the stage timer

lib/project.js prFor filters candidates through claimable(), which keeps only OPEN (or MERGED whose head still matches the row). A dismissed or declined PR is dropped, so readReviewForPipelineWait answers "no pull request for <branch>" and the wait backs off. The refusal the fix added is correct and unreachable on this path. Two shapes would close it: let the wait carry the PR number it was registered against and read that number, or let the lookup admit a DECLINED PR when the row is standing at the head the PR records. Until one lands, every decline leg will look like a stall.

D3 (minor). The wait registers with no branch

registerPipelineWait takes the branch from the job or from the thread's first turn. A stage whose tree is a wtgui/* workspace ref names neither, so the first tick after any wait stage answers "the wait record names no branch" - once at 00:03:00 in the first sitting, again at 02:55:14 here. One wasted tick per wait, and it costs a doubling of the backoff.
