6. The artifact: v1.76.12, and why it was the gate's fault

Two lanes bumped from the same 1.76.11 within 26 seconds. The 1.76.13 bump commit was authored first (09:51:13), the 1.76.12 commit second (09:51:39), and the 1.76.13 branch was merged after both (de0ba1e7af, 09:56:15, reading 1.76.13 on both sides). The walk is git log in commit-date order, so it listed 1.76.13 and then 1.76.12 and compared them - but no commit ever replaced a higher number with a lower one, and main's first-parent chain reads 1.76.11, 1.76.12, 1.76.13 in that order.

The fix is in the walk, not in a tolerance: tools/release-history.mjs:62 now records BOTH sides of the version line (read is the value the commit's patch replaced, written the value it wrote), and tools/verify-version-tags.mjs:87 compares those two. A commit whose patch genuinely replaces a higher number with a lower one is still a finding, and a commit whose diff shows no replaced line still falls back to the ordered neighbour, so nothing was dropped: test/release-tags.test.js:185 drives all three cases. The same correction removed six identical walk artifacts from this branch's own read (1.191.3, 1.192.0, 1.193.0, 1.194.0, 1.194.4, 1.196.1), each of whose own patches goes up.

7. The mechanism: a pin names one finding, and a stale pin fails

tools/version-tags-pins.json:1 holds 14 pins: 3 backwards, 7 wrong-commit, 4 missing. Each pin is a finding's identity (kind, version, the commit the finding is about, and for a wrong anchor the commit the tag points at), a written reason, and, for the eleven real ones, the repair command. Three properties make it a named exception rather than a silencer, and each is a test:

  • It is still computed and still printed. The gate prints every pinned finding with its why: and its repair:, and the count is on the gate's own lines. tools/verify-version-tags.mjs:589 is the block; the JSON carries pinned and stalePins beside findings.
  • It covers one finding and no other. The identity includes the tag's commit for a wrong anchor, so a tag moved onto a different wrong commit is a new finding. tools/verify-version-tags.mjs:386; the unit case is in test/release-tags.test.js.
  • A pin that names nothing fails. Repair an anchor and its pin must go in the same commit; until it does, the gate prints stale-pin ... no finding matches it any more and exits 1. tools/verify-version-tags.mjs:631; the end-to-end case is test/version-tags.test.js:352, which also proves the missing --pins file is exit 2 rather than a silent pass.

The pin file is validated, not trusted: a bad kind, a short sha, a reason that says nothing, a wrong-commit pin without its tag commit, or a duplicate identity is a problem line and exit 2 (tools/verify-version-tags.mjs:319). The disposition this writes down for each finding is the one docs/versioning.md:73 already names for an off-main tag: re-point it at the commit main carries, or delete it and name the branch that held it.
