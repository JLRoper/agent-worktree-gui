2. What puts a full snapshot on the stream, and how often

Two doors, one of them on a clock nobody sees:

  • Every attach. handleStream writes event: board (lib/http/transport.js:55-62) and then, on the next turn, event: snapshot (lib/http/transport.js:84). A reload, a reconnect, a second tab, a panel restart - each one pays both frames, and the pair duplicates the project list, the settings and the hosts. Measured: 1 board + 1 snapshot per attach, both a full state.
  • Every write. Twenty-five call sites call broadcastSnapshot() (server.js:975): a todo edit, a settings save, an approval, a collision ruling, a wave move, a release sweep, a round name arriving, a landing, a queue edit. Each one invalidated the snapshot cache, built the whole board, stringified it (3.2 MB measured here, 4.3 MB on the live board) and wrote it to every open tab. In a quiet 30 s window: none. In a working minute: as often as the reader's own writes and every agent's TODO updates.

So the answer to "how often it repeats" is: twice per attach, and once per write - and the second one is the one that lands on a page mid-read.

3. The cut

One pure function decides what a push has to say: given the state the tabs hold and the state now, the panes that moved, the rows that moved and the rows and cards that left (lib/snapshot-delta.js:74). Three details make it a cut rather than a shuffle:

  • A row travels whole, or not at all. The page replaces a row object wholesale when a row frame arrives (public/render-projects.js placeRow), so a field-by-field delta would draw rows with holes. A row that moved is sent entire; a row that did not is not sent.
  • The ledger of what each tab was told. Rows reach a tab by three routes - their own row frame, a drop, and a snapshot or delta. Every one of them records the row's print (server.js:959, :1079), and a push skips a row whose print has not moved (lib/snapshot-delta.js:116). Without it, a board being scanned re-sends on every write every row the scan has already delivered - measured at 1.9 MB of the 4.3 MB.
  • The job pane travels one card at a time. jobs is a list of summaries the page replaces wholesale, so a push carrying it re-sent every transcript on the board (1.2 MB of 75 cards). It now travels as the cards whose content moved, merged by the same updateJob a job frame uses (lib/snapshot-delta.js:134-159, public/settings.js:528).

The first load is not changed. On attach the board frame goes first, exactly as before, and the second frame answers "what did the board not carry": the job cards, the assistant, the approvals, the spawn transport, the skipped list, the paths - and the rows whose decorators moved. That is the same information a first load had before, without sending the project list twice. The shape is negotiated per client: the page asks with ?shape=delta (public/core/sse.js:63) and a client that does not ask (an older tab, a curl, a script) is answered with the full frame, byte for byte as before (lib/http/transport.js:84). A delta that would be larger than the full frame falls back to the full frame (server.js:989), so a push can never cost more than the old one did.

Why a fresh frame rather than a smaller field set: the page's row object is replaced, not merged, so trimming fields would change what a row draws. The one exception is ageMs, a number derived at build time (now - at) that made 189 of 190 rows differ between two builds milliseconds apart; the comparison ignores it (lib/snapshot-delta.js:34-40) and the age still refreshes from every row frame and every full read.

7. What was checked, and what is not cut

  • node --test test/snapshot-delta.test.js test/stream-delta.test.js test/state-during-boot.test.js test/snapshot-cache.test.js: 23/23. The load-bearing one replays every delta onto the previous state and asserts the result is exactly the full frame's state, rows, jobs, drops included.
  • One source-reading test named applySnapshot directly (test/assistant-reset-ui.test.js, "a new assistant becomes a choice on the next snapshot"); it now looks for the paint in the shared panes body and for the call to that body in applySnapshot, so the same guarantee covers both frame shapes. The behaviour is unchanged.
  • Not cut: the first load still carries every job transcript (1.16 MB of the 1.34 MB delta). A card's console is drawn from its record, so cutting it would change what a first load contains - the row's own limit.
  • Not cut: a reasoning line's think buffer (lib/jobs.js, 7.5 MB of the live 30 s). #255 is live in that file; it is the next 40% and it is measured here.
  • Not cut: a page that is already open across the deploy keeps the old client and therefore the old shape - it is answered exactly as before until it reloads. That is deliberate: a delta the old page cannot merge would be worse than a big frame.

8. Reproducing it

node tools/measure-stream-bytes.mjs --root <checkout> --label before --seconds 30 --writes
node tools/measure-stream-bytes.mjs --root <this branch> --label after  --seconds 30 --writes
node tools/verify-stream-delta.mjs

The measurement writes its JSON beside the sandbox it made and prints the summary; the two runs above are stream-before-final.json and stream-after-final.json. It reads a COPY of the reader's state and leaves running job records out of it (their pids belong to the live panel), so nothing it does can settle a run that is not its own.
