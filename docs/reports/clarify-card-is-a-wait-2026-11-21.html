agent-worktree-gui - the sentry's quiet-window stop - clarify and approval

A clarify card is a wait, not a stall: the sentry exempts it, and a wake waits for the answer

The sentry stopped every assistant turn that produced nothing for four of its own quiet windows, and let the queued wake go out when the stop landed. A turn parked on the clarify tool produces nothing at all - the wait is silent by design - so a card waiting on a person read exactly like a hung turn and was killed. The fix is two lines of rule and one helper: a turn whose record carries an open question or an open approval is exempt from the stop (its clock keeps running), and a wake that arrives during that wait is held in pendingWake and released by the answer. A turn with no open question is still stopped exactly as before, and that half is pinned on the pre-fix tree as well as on this one, so the exemption cannot quietly become a licence to hang.

The defect, read from the code

In supervise(), before this branch, every assistant's own turn was judged at its own quiet window and stopped when it had produced nothing for four of them; the queued wake went out when the stop landed (lib/assistant.js:4039-4043 on e8341c63, the four of them comment):

// Every assistant's turn is judged at ITS OWN quiet window and stopped when it has produced nothing
// for four of them; the queued wake goes out when the stop lands.
...
const quiet = Date.now() - (lineAt || startAt);
const limit = Math.max(300_000, num(this.settingsFor(rec.id).quietSeconds, this.settings.quietSeconds) * 1000 * 4);
if (!(quiet > limit)) continue;

Nothing in that path asked whether the turn was waiting on a person. The same file already states the correct rule for the Element room, in its own words, at lib/assistant.js:8696 on this branch: "What travels is ONLY a wait a person can answer - a clarify card, a run's approval, the panel's own". And the worker-side quiet alert keeps it too: lib/assistant.js:4438 reads j.status === "running" && !j.question before it fires. Only the sentry did not apply it.

Two facts make the silence structural rather than slow:

  • a parked run emits no events at all; the gateway only touches its own activity clock, so no line ever reaches job.lines while the card is up;
  • the stop was filed as the reader's own: jobs.stop calls terminate(j, "reader") before it posts to the gateway (lib/jobs.js:6230), so a card the sentry killed is indistinguishable on the board from one the reader cancelled.

At the reader's default quietSeconds of 240 the window is max(300 s, 240 x 4), sixteen minutes, so any clarify wait longer than that was stopped by the panel, not by the gateway.

The fix

A. The exemption, where the four-window rule is written

lib/assistant/read.js:180 adds the predicate the rule was missing, beside the module's other facts about a turn:

export function awaitsPerson(j) {
  return Boolean(j) && Boolean(j.question || j.approval);
}

lib/assistant.js:4065 applies it before the clock is read, and the comment above the loop (lib/assistant.js:4045-4050) now says so where the four-quiet-window rule is written: "Four quiet windows are evidence of a stall only when the turn has something it could have said... Such a turn is exempt and its clock runs; what releases it is the answer, not a watchdog. A turn with NO open question is still stopped exactly as before." Nothing else about the turn changes: it is answered, resumed and settled by the path every turn takes.

B. The wake is held, and the answer releases it

A parked turn keeps its run live: the store writes clarify.request onto the job record without touching its status, so the turn stays running, and isLive() already answers true for any record carrying an approval (lib/assistant/read.js:171). That is what makes the existing hold in lib/assistant/wakes.js:233 do the right thing: flushWakes puts a batch back on pendingWake while that assistant has a live turn, so a wake that arrives during the wait is held, not dropped and not started, and the end of the answered turn is what calls it again. That comment now names the rule (lib/assistant/wakes.js:227-232) instead of leaving it as a side effect of a status word. The behaviour is proved end to end below, including the sentry pass in the middle of the wait, which was the moment the wake used to get out.

Why the rule did not get loose

  • The control test is the same on both trees. A turn with no open question, silent for thirty minutes, is judged, stopped, and journalled with the same stall line; the fix does not touch that path, and the test fails if it does.
  • The predicate is a fact about the record, not a mood: question or approval present on the job, both of which the store writes on arrival and clears the moment the prompt settles (lib/jobs.js:4697, 6208, and settle's own close at 4832). There is no clock in it, so a turn cannot become exempt by being slow.
  • The exemption is in the sentry's assistant-turn loop only. The worker-side quiet rule already carried !j.question, and it is unchanged; the other sentry rules are untouched.
  • The fifth test of the same file (a question is a wait, an approval is a wait, and a finished card is neither) pins the predicate itself, so a later edit that widens it to "any record" fails a test rather than quietly exempting every turn.

Two readings matter, and they point in different directions:

  • The sentry can kill this card, and the panel cannot tell you it did. At 240 s quiet windows the stop lands after sixteen minutes, and it is filed as the reader's own stop (lib/jobs.js:6230). That is the defect the row names, and the tests above prove the old code did it and the new code does not.
  • These eight cards did not die that way. None of the cards in the table carries a termination record, and each closed at 89 or 90 seconds with the panel's own deadline an hour away (clarifyWindowSeconds() reads 3600 s, from the default: no clarify.timeout is written in the gateway config). The wait ended on the gateway's side, the turn went on to its end, and the panel closed the question with "the turn ended". That is a second cause of the same symptom - a card dying unanswered - and it is named below rather than folded into this fix.

What this does not fix

A question with a 3600 s panel deadline is being withdrawn by the gateway after about 90 s. The panel never asked for that: its countdown says an hour, the card is drawn with an hour, and the reader loses it in a minute and a half. The sentry exemption does not help (the sentry had not fired), and the wake hold does not help (the turn was never live long enough to matter). It needs its own row: either the gateway's clarify wait is raised to the window the panel reads, or the panel stops promising a window the waiter does not honour. This report names it, and the question on this row's card offers it as the first next direction.
