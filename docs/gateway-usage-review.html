Hermes gateway usage: what the measurements show

Measured on the live board, 2026-11-02 17:29–17:48 EST (22:29–22:48Z): panel 127.0.0.1:7331, gateway 127.0.0.1:8642 (Hermes 0.22.5, code_sha bf0203a), branch wtgui/research-whether-our-her-f16888 at 9d4e9b8. Every figure below was produced by the command printed beside it; nothing is estimated. Memory figures are MiB (Get-Process bytes ÷ 1,048,576); byte counts and character counts are exact. Anything I could not measure is listed as unmeasured in §8.

Verdict

More RAM would not help. The gateway's working set was 747.7–786.8 MiB while 8, 12 and 18 runs were live, and it does not rise with the number of live runs (18 runs: 786.8 MiB · 12 runs: 747.7–769.7 MiB · 8 runs: 786.5 MiB). Private bytes stayed at 944.6–980.7 MiB. This is a 32,213 MiB host with 2,185–3,381 MiB free; the gateway is about 2.4% of RAM. The resources actually being spent are CPU (1.15–1.30 of the machine's cores) and tokens (43 assistant wakes in the last hour; $30.71 across the two assistant threads).

What is actually wasteful is what the panel sends on every wake. One measured wake was 36,434 characters of preamble wrapped around an 81-character question — 99.8% of the message the model reads is the standing context, and 53% of that context is a charter file re-sent in full (19,720 bytes) plus a board digest (7,975 bytes, 22%). It repeats 43 times an hour: 1,794,889 characters of preamble in the last 60 minutes.

The three changes worth making, in order: cap assistant wakes at the rate the board needs (30/h/assistant today → 10), stop re-sending the unchanged charter on every turn (−19,720 B/turn), and send the board digest only when it is due (−7,975 B/turn). Together they remove roughly three quarters of the per-turn preamble and about half the turns.

6. Would more RAM help?

No — and the measurements say why in three ways.

  1. Memory does not track the work. 18 live runs: 786.8 MiB. 12 live runs: 747.7–769.7 MiB. 8 live runs: 786.5 MiB. The 8-run figure is higher than the 12-run figures. If live run contexts were the cost, the direction would be monotone. It is not.
  2. Nothing is near a limit. The gateway's private bytes peak at 980.7 MiB on a 32,213 MiB host with 2,185–3,381 MiB free; it is ~2.4% of RAM. There is no evidence of the working set being trimmed to fit (WS64 and private move together within ~200 MiB).
  3. The pressure is elsewhere. CPU: 1.15–1.30 cores busy. Tokens: 43 wakes/hour, each carrying 36–44 KB of preamble, $30.71 already spent on the two assistant threads (1.58 billion cache-read tokens). A RAM upgrade changes none of those numbers.

Where the memory actually goes: a fixed Python interpreter plus gateway machinery (about 748–787 MiB, stable), the panel (about 230–243 MiB, of which 776 KB is retained transcript lines), and a 2.0 GiB on-disk state.db that is streamed from disk rather than held whole. The live run contexts are visible as context_used per run — 100,714 to 310,154 tokens in §2 — but they do not translate into a working-set curve.

What would change if RAM were raised: nothing measurable in this data. The only honest statement is the converse: the gateway's RSS is already under 1 GB, so a machine with more free memory has nothing to give it. If someone wants a memory-shaped answer, the target is the panel's 2.93 MB /api/jobs serialization and the 2.0 GiB store, not the resident set.
