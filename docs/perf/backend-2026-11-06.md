changed. Every finding carries a `file:line` on `9078bb9` (1.36.2), the cost measured here or
inferred from the code (and labelled as such), and what it would take to remove it.

## The answer in one paragraph

Every route's own work is milliseconds: `Jobs.list()` over 80 jobs is 11.45 ms, serialising the
869 KB job payload is 1.96 ms, gzipping it is 4.70 ms, a static 404 is 0.6 to 1.0 ms and the shell
is 7.5 to 13.4 ms. The seconds are not spent in the routes. They are spent waiting for the event
loop, which on the live board is never idle: one trivial route (`/api/health`, a `sendJson` of six
fields) measured 0.54 s to 6.69 s across seven samples, and one 3.4 MB `/api/state` in flight
inflates a 1 ms 404 to a 137 ms median in the sandbox. The board generates that load itself: a
3.36 MB snapshot is serialised for every new SSE client, a 255 KB assistant frame for every alert,
a 1 MB job store rewritten with `writeFileSync` every 700 ms of job activity, and a quiet alert
re-raised on every sweep for a thread whose last console line carries no timestamp (8 s apart in
the reproduction), each one writing the 268 KB assistant store again. The static path is a
separate, harder failure: on the live process `/`, every existing
asset and `/api/build` never answer at all, because all of them await one memoised bundle scan
(`lib/build-version.js:182`) that has no timeout and never settles.

## 1. `/api/jobs`: 18 ms of work, 0.16 s to 8.7 s of waiting

Route: `server.js:4579`.

```js
await jobs.probe();
return sendJson(res, 200, { jobs: jobs.list(), transport: jobs.transportInfo(), defaultCwd: config.defaultCwd });
```

`jobs.probe()` (`lib/jobs.js:771`) is a `/v1/capabilities` fetch to the gateway: cached for 15 s
(`lib/jobs.js:773`) and aborted after 4 s (`lib/jobs.js:780`). `jobs.list()`
(`lib/jobs.js:1252`) sorts the whole map and builds a `summary()` per job
(`lib/jobs.js:1110`), which copies the last 60 console lines (`TAIL`, `lib/jobs.js:74`;
`lib/jobs.js:1229`). `sendJson` (`lib/http/transport.js:33`) stringifies and gzips anything over
2 KB.

Measured, live (3.44 MB board; the job payload was 965,084 bytes at 116 jobs when the front-end audit measured it; 869,314 bytes
for 80 jobs in the sample store used here):

| path | samples (s) | reading |
| --- | --- | --- |
| `/api/jobs` | 0.16, 0.83, 1.69 | a free loop |
| `/api/jobs` | 5.44, 5.91, 0.96, 1.23 | same route, busy loop |
| `/api/health` | 0.54, 1.13, 2.18, 1.49, 2.43, 5.36, 6.69 | the floor is the loop, not the route |

Measured, sandbox, own cost on the served store (`bench-list.mjs`):

| operation | cost |
| --- | --- |
| `Jobs.list()`, 80 jobs, 60 lines each | **11.45 ms** |
| `JSON.stringify` of the 869,314-byte payload | **1.96 ms** |
| `gzipSync(level 6)` of the same bytes | **4.70 ms** (869 KB -> 50,368 bytes, 6 %) |

So the route's own ceiling is about 18 ms. Two things move it to seconds:

- **The probe holds the request for up to 4 s.** With a gateway that accepts the connection and
  never answers (stub on 7397), `/api/jobs` measured **6.4 s and 8.7 s**; with the probe cached it
  dropped to 25 to 90 ms. The 15 s cache means a page polling every few seconds pays that 4 s
  every third poll, and two overlapping polls pay it twice: `probe()` has no in-flight memo, so N
  concurrent requests start N fetches.
- **Head-of-line blocking.** The same route measured 28 to 32 ms in a settled sandbox and 3.58 s in
  the same sandbox a second later, with nothing changed but what else the loop was doing.

The payload itself is the second-order problem: `lines` is 46 % of it (the front-end audit measured
476 KB of 965 KB), it is re-serialised in full on every GET, and `/api/state` carries the same
`jobs` array again (`server.js:2767`), so a page that polls both transfers and parses the console
text twice.

Serialising and gzipping 3.4 MB is about 8 + 19 ms at the rates measured in section 1, so the

## 3. The static path: a 404 is cheap, the shell is not, and on the live process it never answers

`serveStatic` (`lib/http/static.js:30`) reads the file first (`:38`) and only then awaits
`build.current()` (`:42`). That ordering explains the shapes measured:

| path | what it does | measured |
| --- | --- | --- |
| `/nope.js` | `readFile` throws ENOENT -> 404 (`lib/http/static.js:70`) | **0.6 to 1.0 ms** settled; 2.26, 2.75, 2.76, 4.86, 7.18, 7.46, 9.43 s live |
| `/deep/nope/x.css` | the same 404 | 0.6, 0.8, 1.0 ms settled; 2.95 to 5.51 s live |
| `/` | `readFile(index.html)` 113 KB, `build.current()`, `rewriteShell`, gzip | **7.5, 8.3, 13.4 ms** settled; **000 at 25 s and 40 s** live |
| `/app.js`, `/index.html` | the same read, no rewrite | **000 at 5 to 6 s** live |
| `/api/build` | `build.info()` -> the same `build.current()` | **000 at 5 to 6 s, 8 s, 30 s** live |

The 15.6 s static 404 is queueing, not file I/O: a missing file is a `readFile` that fails, and it
does not touch the bundle at all. Measured against a live board it took 7.46, 7.18 and 6.93 s in
three consecutive requests while `/api/jobs` answered in 0.16 to 1.69 s. In the sandbox the same
404 costs 1 ms idle and a **137 ms median (102 to 251 ms) behind one 400 ms `/api/state`** - the
100x that turns a trivial route into a visible stall when the blocking work is 5 to 10 s.

`/` is a different failure. On the live process it does not answer at all, and neither does any
asset or `/api/build`; API routes and 404s still answer. The only code those share is
`build.current()` (`lib/build-version.js:182`):

```js
function refresh() {
  if (!pending) {
    pending = scan().catch(...).finally(() => { pending = null; });
  }
  return pending;
}
async function get() {
  if (pending) return pending;
  if (!current || !current.version) return refresh();
  if (await stale()) return refresh();
  return current;
}
```

- `pending` is a permanent memo: every waiter returns the same promise, and it is cleared only
  when that promise settles (`lib/build-version.js:165` to `:180`). A scan that never settles
  therefore wedges every static request for the life of the process.
- Nothing bounds the scan. There is no timeout on `readBundle`/`stampOf`, no fallback to the last
  good bundle, and no log line when a scan does not return: the panel logged its last successful
  scan at 17:12:02Z ("static bundle changed on disk: b4c4157b11e1 -> f7e22a60345d") and has been
  silent on the subject since, while `/` has answered 000 at every ceiling tried.
- `stale()` (`lib/build-version.js:156`) `stat`s every bundle file on **every** static request, so
  the cost is paid per request even when nothing changed, and one hung `stat` takes the whole
  static path with it.

The exact syscall that hung cannot be named from outside the process (the process exposes no
handle list), and the same `createBuild` module run from a scratch process against the same
`public/` directory answers in 12 ms. What is proven is the consequence: one stuck fs call inside
a scan permanently disables the UI, and the code has no deadline that would recover from it. This
is a correctness bug with a performance audit's clothes on: a 25 s page load that never completes
is not a slow page, it is a dead one.

## 4. What the broadcast costs

`broadcast` (`server.js:639`) builds the frame once and writes it to every client:

```js
const frame = `event: ${evt.type}\ndata: ${JSON.stringify(evt)}\n\n`;
for (const res of clients) { try { res.write(frame); } catch { clients.delete(res); } }
```

Sharing the string is right. The problem is what the events carry. Measured on the live board, one
client, 30 s:

| event | frames | bytes | avg frame | max frame |
| --- | --- | --- | --- | --- |
| `snapshot` | 1 | 3,364,484 | 3,364,484 | 3,364,484 |
| `assistant` | 1 | 255,035 | 255,035 | 255,035 |
| `row` | 40 | 200,011 | 5,000 | 36,825 |
| `job` | 12 | 128,523 | 10,710 | 15,192 |
| `jobline` | 17 | 5,038 | 296 | 548 |
| `heartbeat` | 5 | 2,019 | 404 | 403 |
| `deliverable` | 1 | 150 | 150 | 148 |
| **total** | 77 | **3,955,260** | | |

That is **132 KB/s (about 475 MB/hour) for one idle tab**, and 85 % of it is the single connect
snapshot. The sandbox shows the same shape with a smaller board: 1,633,424 bytes in 40 s
(41 KB/s), of which `snapshot` 1,339,894 and `row` 117 frames at 2,465 bytes each.

Two costs follow from `snapshot()` being called at event time, not at paint time:

- Every `broadcast({type:"snapshot", data: snapshot()})` site - there are 19 of them in `server.js`
  - builds and stringifies the full 3.4 MB object before it knows whether any client is listening.
  With `clients` empty the stringify is still paid.
- `assistant` frames are `assistant.state()` in full (`lib/assistant.js:2620`, emitted at
  `lib/assistant.js:2716`): 255 KB of alerts, assistants, rules, watches, journal and digest for
  every alert, every journal line and every assistant change, whether or not the reader has the
  Alerts tab open.

## 5. What the job-store rewrite costs

`Jobs.schedulePersist` (`lib/jobs.js:938`) debounces 700 ms (`lib/jobs.js:1021`) and then rewrites
the whole store synchronously:

```js
writeFileSync(this.storePath, JSON.stringify({ savedAt: ..., jobs }, null, 0));   // lib/jobs.js:1017
```

It keeps the newest 80 jobs (`KEEP_JOBS`, `lib/jobs.js:75`), and every job event calls it
(`lib/jobs.js:1266`, `:1588`, `:1670`, and ten more). Live `jobs.json` is **1,017,200 bytes**; sampled
over 20 s it was rewritten **2 times** - about 6 MB/min of synchronous disk writes while the board
is moderately active. A `writeFileSync` of 1 MB blocks the loop for the write's whole duration, so
each one is a stall every request behind it waits for.

The assistant store is the same shape with a 400 ms debounce (`lib/assistant.js:511` to `:519`,
`writeNow` at `:521`) over **268,902 bytes** (sandbox) and 300,875 bytes (live). Measured with
`fs.watch` over a 40 s window in which the board had **one** stuck thread: **10 writes** - the quiet
loop alone rewrites 268 KB roughly twice per sweep.

Both stores are written in full on every change. A job line arriving every 120 ms (`TEXT_FLUSH_MS`,
`lib/jobs.js:80`) is 1 MB of rewrite per 700 ms; a single alert is 268 KB.

## 6. The quiet rule that fires every 8 seconds on one thread

The rule is `lib/assistant.js:3178` to `:3194`:

```js
const lastLineAt = lines.length ? Number(lines[lines.length - 1].at) || age : 0;
const quietFor = lastLineAt ? now - lastLineAt : age;
if (j.status === "running" && !j.question && quietFor >= this.settings.quietSeconds * 1000) {
  this.fired("quiet", `${j.thread}|${j.id}|${j.runId || ""}|${lastLineAt || 0}`, { ... });
```

The subject is meant to be the silence, so that one unchanged run is one alert. It is not, in one
case: `age` is `now - Date.parse(j.startedAt)` and `now` is the sweep's clock. When the last line
has no numeric `at`, `Number(undefined) || age` falls back to `age`, the subject changes on every
sweep, and the rearm dedupe in `fired()` (`lib/assistant.js:3026`, `:3045`: same `key` and open, or
younger than `rearmSeconds`) can never match. A line with no timestamp is not hypothetical: the
revive path pushes one (`lib/jobs.js:4716`, `j.lines.push({ kind: "text", text: last })`).

Measured, sandbox, 8 s sweep (`settings.seconds` 8; the live board runs 5 s,
`lib/assistant.js:2774`), `quietSeconds` 60, `rearmSeconds` 900:

| job | last line | alerts in 77 s | gaps |
| --- | --- | --- | --- |
| `probe-quiet-loop` | `at: null` | 3, then one more | **8 s, 9 s** |
| `wtgui-live-with-lines` | `at: <ms>` | 1 | - |
| `wtgui-live-no-output` | no lines at all | 1 | - |

The two control jobs fired once because their subject is stable. The untimed one re-fired on every
sweep, which is the "every 8 seconds on one thread" report: it is not the reader's settings, it is
one line without a timestamp. Each firing costs an `alerts.push`, a `journalAdd`, a `persist()`
(268 KB) and an `emit()` -> a 255 KB `assistant` frame per connected client.

On this board the rule is escalated: `~/.wag/state/assistant.json` carries `quiet: "wake"` with
`sweep 5 s`, `rearmSeconds 900`, `quietSeconds 240`. So each firing does not stop at the alerts
list - `fired()` calls `this.wake(...)` (`lib/assistant.js:3086`), which starts an assistant turn.
The retained alert list held 8 quiet alerts today, several threads with two each 8 to 12 minutes
apart, and the panel's log shows the `panel-assistant` runs they started (17:21:35, 17:22:23,
17:28:24, 17:28:45 and more). A run whose last line has no timestamp would take that path every
5 s instead of every 15 min, which is the "every 8 seconds on one thread" report with a turn -
and a full 3.4 MB snapshot - behind every firing.

## 7. What repeats on a timer, and what scales with what

| timer | period | source | cost |
| --- | --- | --- | --- |
| heartbeat frame | 5 s | `server.js:2800` | 404 bytes per client, one stringify |
| assistant sweep | `settings.seconds` (5 s live) | `lib/assistant.js:2774` | `evaluate()` over every live job, plus one persist + one 255 KB emit per alert |
| job store rewrite | 700 ms after a job event | `lib/jobs.js:1021` | 1 MB `writeFileSync` |
| assistant store rewrite | 400 ms after a change | `lib/assistant.js:517` | 268 KB `writeFileSync` |
| scheduler scan | 5 s worktree / 5 s live | config | git children, row events, row broadcasts |
| title sweep | 10 s | `sweepTitles()` | a `sessionInfoFor` read per unnamed job |

Scaling: `/api/jobs` and the `jobs` half of `/api/state` grow with job count and with the 60-line
tail per job; `/api/state` and the `snapshot` frame grow with projects and worktrees (1.95 MB over
176 projects here) and with the alert list; every broadcast frame is paid once per connected
client; the quiet loop grows with the number of live jobs whose last line has no timestamp.

## 8. Caveats

- **Shared host.** Other agents' suites (`node --test` on several trees) were running throughout;
  the same live route moved by more than 3x between samples. Quote the ranges, not one sample. The
  lowest reading is the least-contended one, and it is the one closest to the route's own cost.
- **The live process is not this exact build.** It booted at 10:10 from the main checkout and its
  served bundle changed under it twice (16:44 and 17:12 UTC) as other agents edited `public/`. Its
  in-memory code is therefore older than `9078bb9`; its job store and payload sizes are real, its
  code paths are the ones described here only where `server.js` and `lib/` are unchanged since.
- **The synthetic store is uniform.** 80 jobs of 60 identical lines, which matches the live byte
  count (869 KB against 965 KB) but not the live mix.
- **The 404 floor is the loop.** On a quiet sandbox it is 1 ms; no measurement here claims a static
  404 costs seconds by itself.
- **The hung scan's syscall is inferred, not proven.** The stuck `pending` is proven by the
  behaviour; which fs call never returned is not, and the same module from a fresh process is
  healthy.

## 11. What to fix first, in order

1. **Bound the bundle scan.** Give `refresh()` a deadline and a fallback to the last good bundle,
   and log when a scan does not return. Without it one stuck file read turns the panel into an
   API-only process until someone restarts it - the state the live board is in now.
2. **Stop rebuilding on the sweep.** A quiet alert about a run that has printed nothing should be
   one alert, keyed on `startedAt` when the last line has no timestamp (`lib/assistant.js:3178`),
   and the revive path should stamp the line it pushes (`lib/jobs.js:4716`).
3. **Take `snapshot()` off the request path.** Serve `/api/state` from a snapshot built once per
   change (and once per second at most), and let SSE clients receive the deltas they already get
   (`row`, `job`) instead of a 3.36 MB full frame on connect.
4. **Append to the job store instead of rewriting it.** 1 MB every 700 ms is a stall per write;
   the store only needs the last 80 jobs.
5. **Make the probe free.** One in-flight probe shared by all callers, a shorter abort than 4 s,
   and never block a GET on the gateway's health.
