# Where the panel's time goes: the routes, the board's render and refresh loop, the assistant frame, the pipeline modal, and the CSS that forces layout

Deep read-only study of the panel this worktree carries. No product file was changed; the only
file written is this report. Every number is either measured here (and says where and on which
board) or derived from the code and labelled as such. `file:line` is on `0be4c06`.

The server half of the same board is `docs/perf/backend-2026-11-06.md`; the client half written
before a browser could be held on the page is `docs/perf/js-cpu-and-time.md`. This one is the
measurement those two could not make: the route's own cost against the loop's, the board's first
render and its idle refresh loop in a real Chrome, the `assistant` frame, the pipeline modal, and
the cost of a restyle on this stylesheet. It also puts a date on each cost, which is where the
last section starts.

## Method

| what | how |
| --- | --- |
| a route's own cost | `bench.mjs` imports this tree's `lib/build-version.js`, `lib/http/transport.js` and `lib/jobs.js` and times each piece on the served store, warm filesystem, median of 5 to 20 runs |

## The answer in one paragraph

No route does more than about 24 ms of its own work: `/api/jobs` owns 22.4 ms (list 9.50,
stringify 1.93, gzip 10.97) and the shell 5.0 ms. The same routes are observed at 0.1 to 10 s,
because they await the event loop about 25 times (a read plus a 23-stat bundle sweep) and every
await is a re-queue behind whatever the board is doing. On the client the first render is 268 to
345 ms of script and then a 446 ms long task at 1.85 s; after that the idle board spends its time
answering 59 row events and 19 job events per 30 s, with `renderJobs` alone taking 634 ms of that
to re-run its preamble for a list whose markup it then does not rebuild, and the renderer's main
thread busy 3.7 s in every 30 s (measured on the smaller sandbox board, so the live board is worse
than that). The single largest named cost on the page is the chart's total order: 526 ms of the
8.7 s load profile, and 1,262 calls per 30 s idle, because `rowTopHidden` sorts a project's rows
again for every row it draws. That is the 2026-11-03 top-N landing, not this week's. This week's
landings cost about 1 ms (the pipeline modal) and one 1.2 s stall in the worst case (the bundle
deadline); the board was already this slow.

## 1. `/api/jobs`: 22 ms of work, observed at 19 ms to 7.5 s

Route `server.js:4579`, `jobs.probe()` then `jobs.list()`. Own cost, measured in a scratch process
against the copied store (80 jobs, 851,779-byte payload, 132,587 bytes gzipped):

| operation | median | min | max |
| --- | --- | --- | --- |
| `Jobs.list()` (80 jobs, 60-line tail) | **9.50 ms** | 7.71 | 10.74 |
| `JSON.stringify({jobs:list})` | **1.93 ms** | 1.59 | 3.30 |
| `gzipSync(level 6)` of it | **10.97 ms** | 9.99 | 29.55 |
| `sessionInfoFor()` over the same 80 jobs | 11.72 ms | 9.29 | 22.36 |

`list()` is `summary()` per job (`lib/jobs.js:1252`, `:1110`), and `summary()` calls
`sessionInfoFor()` (`lib/jobs.js:4604`), which is an index lookup with a 60 s cache and, for a
thread the index does not hold, a **3 s** cache that re-opens Hermes' `state.db` with
`DatabaseSync` (`lib/jobs.js:4612`, `lib/session-usage.js:81`). On this store no thread is missing,
so the 11.72 ms is the cheap path; a board with one adopted thread re-reads every session row
synchronously on the event loop every 3 s. `lines` is 47% of the live 1.03 MB payload and is
re-serialised in full on every GET.

Observed, same route, same minute:

| where | samples |
| --- | --- |
| sandbox, settled | 19, 20, 30, 50, 374 ms (862,240 bytes) |
| live | 222, 313, 477 ms, 7.49 s (919,266 bytes) |

So the route is 22 ms and the rest is the loop: `/api/health` in the same window was 13 ms to
1.9 s. `probe()` is the other half: it is cached for 15 s and aborted at 4 s, but it has no
in-flight memo, so two overlapping polls start two fetches, and every third poll pays whatever the
gateway takes up to 4 s.

## 2. The static path: 5 ms of work, a 23 ms gzip, and 25 awaits that expose all of it

`serveStatic` (`lib/http/static.js:30`) reads the file, then awaits `build.current()`, which
awaits `stale()` and, on a miss, the scan. Own cost:

| operation | median | notes |
| --- | --- | --- |
| `build.current()` cold (read 22 files, hash, 23 stats) | **41.9 ms** | once per change |
| `build.current()` warm (23 `stat`s, sequential) | **1.74 ms** | max 18.97 ms; paid on **every** static request |
| `readFile index.html` (113,417 bytes) | 0.30 ms | |
| `rewriteShell` over it | 0.49 ms | 113,417 -> 113,770 bytes |
| `gzip` of the rewritten shell | **2.50 ms** | 113,770 -> 31,364 bytes |
| `readFile app.js` (1,130,357 bytes) | 0.97 ms | |
| `gzip(app.js)` | **23.37 ms** | max 30.90 ms, on the event loop, every request |
| `readFile style.css` (331,389 bytes) | 12.55 ms | min 7.05; this disk, not the code |
| `gzip(style.css)` | **9.46 ms** | |
| `readFile` of a missing file (the 404 path) | 4.29 ms | min 0.16 ms; no bundle work at all |

Observed (`/`, `/app.js`, `/style.css`, `/nope.js`), which is own cost plus queueing:

| route | sandbox | live |
| --- | --- | --- |
| `/` | 103, 303, 410, 445 ms, 2.47 s | 12 ms, 3.03, 3.64, 5.30 s |
| `/app.js` | 42, 362, 517 ms, 2.05, 5.62 s | 64 ms, 2.55, 4.87, 12.72 s |
| `/style.css` | 1.12, 1.14, 3.86, 9.82 s, then no answer at 30 s | 86 ms, 2.61, 3.44 s |
| `/nope.js` (404) | 92 ms, 2.58 s, then no answer at 30 s | 79, 118 ms, 2.93, 4.19 s |

Two causes, and they are different in kind.

- **The awaits are the latency multiplier.** `/` is the one route that touches the bundle: one
  `readFile`, then `build.current()` -> `stale()` -> **23 sequential `stat` calls**, each an
  `await`. A route that awaits 25 times re-enters the loop 25 times, and on a loop whose stalls
  were 0.3 to 0.5 s at that moment it lands behind 8 to 10 s of other work. `/nope.js` awaits
  once (a read that fails) and answered in 92 ms in the same window. The 404 was never slow; the
  shell was, and only because of how many times it yields.
- **The gzip is on the loop.** `sendJson` and the static gzip both call `zlib.gzipSync`
  (`lib/http/transport.js:33`, `:31`). `app.js` is 1.13 MB of text, so 23.4 ms of a 26 ms request
  is `gzipSync` blocking every other request. It is not cached anywhere: the URL carries the
  version (`?v=2173031cfb04`), which is exactly the key a cached gzipped body would need.

**The wedge is still reachable, and the new deadline is what says so.** On the sandbox the log
printed, four times in six minutes:

```
19:30:00 the static bundle staleness check did not answer within 1200 ms - serving the last good bundle
```

and in the same state `/style.css` took 45 s and then never answered, `/nope.js` never answered,
and `/api/health` went from 7 ms to a 10 s timeout, while a fresh `node` process read the same
331,389-byte file in 0 to 1 ms five times in a row. That is not the filesystem and not the route:
it is the process, and the code it named as waiting on files was the bundling layer (the deadline
above is that layer's own log line).
`3cdbe0c` (landed today) bounds the scan and the staleness check, so this is now a 1.2 s stall and
a 10 s cool-off instead of a permanently dead UI. It is a real improvement and it is also
evidence that the stall is still happening: the deadline fires, then `get()` serves the held
bundle until `stuckUntil` passes (`lib/build-version.js:242`), so every static request in that
window pays 1.2 s and gets a possibly stale shell.

## 4. The refresh loop: 1,262 sorts and 15 list renders every 30 s on an idle board

Live board, 30 s, no interaction, one SSE client. Times are inclusive of callees, so
`chartTopSplit` contains `chartTopOrder` and `queueRow` contains `placeRow`; do not sum the column.

| function | calls | total ms | max ms |
| --- | --- | --- | --- |
| `updateJob` (`:6517`) | 19 | **806** | 105.0 |
| `renderConversation` (`:6789`, called by it) | 19 | 660 | 104.7 |
| `queueRow` (`:11848`) | 59 | **638** | 236.5 |
| `renderJobs` (`:6392`) | 15 | **634** | 104.5 |
| `placeRow` (`:11867`, inside `queueRow`) | 59 | 389 | 231.7 |
| `chartTopSplit` (`:8774`) | 1,262 | 286 | 226.1 |
| `chartTopOrder` (`:8761`, inside it) | 1,262 | 279 | 226.1 |
| `reorderProjects` (`:10837`) | 62 | 252 | 31.1 |
| `heldRowCount` (`:8792`) | 616 | 34 | 7.5 |
| `rowTopHidden` (`:8784`) | 59 | 24 | 7.3 |

Sandbox board, 60 s, same method (142 row events): `queueRow` 142 calls / 973 ms, `placeRow` 645,
`reorderProjects` 409, `chartTopSplit` 554 / 372, `heldRowCount` 243 / 177, `rowTopHidden` 90.
Both boards give the same shape and the same per-event cost: **about 10.8 ms of `queueRow` per row
event**, 6.8 ms on the smaller board.

Three causes, each with a number:

- **The chart order runs per row, per project, per render.** `rowTopHidden` (`:8786`) filters all
  rows for the project and calls `chartTopSplit`, which calls `chartTopOrder`, for **every row it
  places**. `heldRowCount` does it again for every project header, and `chartDrawOrder` again for
  every project body. On 175 projects and 368 rows that is 1,262 sorts per 30 s. The sort itself
  is fixable: on the same 368 rows, `chartTopOrder` measures 2.9 ms, the same comparator with
  precomputed activity keys 0.9 ms, a numeric-only sort 0.3 ms, and `rowActivityAt` over all 368
  rows 0.3 ms. The comparator re-parses three dates and builds an `Intl` collator
  (`localeCompare(..., {sensitivity:"base"})`) per comparison.
- **`renderJobs` pays its preamble whether or not it repaints.** The markup is guarded by
  `listSig` (`:6431`), and the guard works - the `innerHTML` is skipped - but before it runs the
  function builds `conversations()` twice (`:6398`, `:6401`), prunes four maps, and builds a
  signature string for every card. That preamble is the 15.7 to 17.8 ms a lone `renderJobs()`
  call measures on the live board, and it ran 15 times in 30 s.
- **A hidden tab is not batched.** `queueRow` flushes inline when `document.hidden` (`:11863`),
  because rAF never fires there. That is correct for correctness and expensive for cost: 59 row
  events in 30 s each did one `placeRow` and one `reorderProjects` synchronously, and
  `reorderProjects` itself captures selection and typing and re-ranks 175 projects. The tab in
  this measurement was hidden, so these are the numbers a background panel pays - and the panel
  spends them while nobody is looking.

Chrome's own counters, same idle shape, visible tab, 30 s: **250 layouts (142 ms)**,
**1,035 style recalcs (218 ms)**, `ScriptDuration` 296 ms, `TaskDuration` 3,710 ms. That is 12.4%
of the main thread busy, and 0.36 s per minute in style and layout alone, before any paint. The
counters were taken on the sandbox board (141 rows); the live board has 368, so this is the low
end.

## 5. `assistant.js`: the frame is not the cost

The `assistant` event is the biggest frame on the wire after the snapshot (250,609 bytes here,
79 alerts), and that is where the earlier audit expected the client cost. It is not:

| operation | payload | time |
| --- | --- | --- |
| `applyAssistant(state.assistant)`, panel closed | 250,609 bytes | 1.1, 0.5, 0.3 ms |
| `applyAssistant(...)`, assistant panel open (862 nodes) | 250,609 bytes | 0.6, 1.1, 0.6 ms |

`applyAssistant` (`public/assistant.js:556`) is cheap because the expensive half is guarded:
`renderAssistantChat` (`:968`) rebuilds only when a chat's signature moves, so a steady-state
frame only filters alerts for the badge, repaints the spawn strip and syncs the tabs. The cost of
a frame that *does* change a session is the rebuild of that chat, which this study did not time
(the function is inside the module's IIFE and is not reachable from the page). The panel's own
timers (`paintWatchClocks` 1 s, the messages and bridge polls at 15 s) are the ones the earlier
audit counted at about 68 callbacks a minute; they were not re-measured here.

## 6. `pipeline-modal.js`: 48.6 ms the first time, 0.8 to 5.1 ms after

The real path (`openPipelineFlow()` -> `PipelineModal.open`), six opens of `sefl-review-loop`
(7 stages, 41 nodes in the card):

| open | ms |
| --- | --- |
| 1 (cold: the card's rules resolved for the first time) | **48.6** |
| 2 | 5.1 |
| 3 to 6 | 1.2, 0.9, 0.9, 0.8 |

`open()` rebuilds the card wholesale (`paint()` at `public/pipeline-modal.js:200`) and then
`readView` (`:279`) measures it: `shapeOf` reads `clientWidth` once, and `wrapRows` (`:259`) reads
`offsetTop` twice per stage and writes `data-row-end` plus a notch `left` per stage. For 7 stages
that is 14 layout reads and 14 writes, which is why a warm open is about 1 ms and why the first is
48.6 ms (it pays the card's style resolution, not the loop). The scroll and resize listeners
(`wireFlow`, `:298`) re-run `readView` on every scroll event and are removed only on the next
`paintFlow`, so a dragged or scrolled drawing measures on every frame it scrolls. This is the
landing that added 211 lines to this file today, and at this size it is not a cost worth acting
on; it becomes one at 13 or more stages, where `wrapRows` does 26 reads per scroll event.

## 7. The CSS that forces layout: 13 to 17 ms per document-wide restyle

`public/style.css` is 331,389 bytes, 4,641 lines, 2,020 rule blocks (after stripping 498
comment blocks), with 10 `:has()` rules, 22 `animation:` declarations, 69 `box-shadow`, 7
`position: sticky`, 199 `display: flex`, 12 `display: grid`, and 15 universal selector parts (2
bare `* { }` resets and 13 descendant or compound universals that match a whole subtree).

Measured on the live board (13,505 nodes), one class toggle plus one forced layout read:

| selector shape | cost per toggle |
| --- | --- |
| `.perf-a .job { color }` (targeted) | **0.5 to 3.3 ms** |
| `.perf-c .job * { outline-color }` (subtree universal) | 9.1 to 71.8 ms |
| `.perf-b * { text-decoration-color }` (document universal) | **13.3 to 17.1 ms** |

So the difference between a targeted rule and a universal one is about 15 ms per invalidation on
this board, and the idle board invalidates styles 1,035 times per 30 s. The `:has()` rules are the
ones that cannot be answered without looking at children: `.job-head:has(> .pipeline-chip)`
(`style.css:1060`), `.reply-row:has(.warnline:empty)` (`:1013`), `#projects tbody tr.row:not(:has(~
tr.row))` (`:3073`), `.as-body:has(...)` (`:4185`), `.agents-block:has(+ .sessions-block)`
(`:756`), and four more. The row one is on the board's hot path: it is a `:not(:has(~ tr.row))` per
row, and the board re-renders rows on every event. None of the 10 is this week's; they are all in
the file before 2026-10-30.

## 9. What to fix, ranked

1. **Take the chart's total order out of the per-row and per-project path** (`public/app.js:8784`,
   `:8792`, `:8800`). Compute the split once per project per scan tick and pass it to
   `placeRow`/`renderProjectRows`, and make the comparator cheap: precompute `rowActivityAt` into
   a `Map` and compare a precomputed name key instead of `localeCompare` per comparison.
   Measured: 2.9 -> 0.9 ms per full sort with keys, 1,262 calls per 30 s down to one per project
   per tick, and the load's 526 ms of comparator time is that call pattern. Risk: medium - the
   order decides the top-N slice and the "show N more" label, so a stale memo draws the wrong held
   set.
2. **Gate `renderJobs` before its preamble** (`public/app.js:6398` to `:6431`). Keep the markup
   guard and add a cheap input signature (job count, newest `lastEventAt`, per-thread status) so
   `conversations()`, the four prune passes and the signature string do not run when nothing they
   read has moved. Measured: 634 ms per 30 s, 15.7 to 17.8 ms a call, 30 calls a minute. Risk: low.
3. **Batch row events in a hidden tab** (`public/app.js:11863`). A 250 ms timer instead of the
   inline flush still applies every event, but one `placeRow` batch and one reorder per timer
   instead of one each per event. Measured: 59 events, 638 ms plus 252 ms of reorder, per 30 s.
   Risk: low - updates land 250 ms later while the tab is not visible.
4. **Stop gzipping the bundle per request and stop statting it per request**
   (`lib/http/static.js:42`, `lib/build-version.js:204`). Cache the gzipped bytes keyed by
   `?v=`/version (the URL already names them) and move the 23-stat staleness check to a 1 to 2 s
   timer instead of the request path. Measured: 23.4 ms of `gzipSync` per `app.js` request, 9.5 ms
   per `style.css`, 1.74 ms (max 18.97) per static request in stats, and a 25-await route that
   turns a busy loop into an 8 to 10 s TTFB. Risk: low - the version is already the cache key.
5. **Trim `/api/jobs`** (`lib/jobs.js:1252`, `:1229`). `lines` is 47% of a 1.03 MB payload;
   stringify plus gzip is 12.9 ms of the 22.4 ms the route owns. Send the 60-line tail only for
   live jobs, or let the queue pane ask for it. Risk: medium - a card's console draws from the
   tail, so the client needs a fill-in path.
6. **Replace the universal and `:has()` selectors on the row and card paths** with a class the
   render keeps (`public/style.css:1060`, `:3073`, `:1013`). Measured: 13 to 17 ms per
   document-wide restyle against 0.5 to 3.3 ms targeted, on a sheet that invalidates 1,035 times
   per 30 s. Risk: low to medium, but it is 10 `:has()` rules and 13 descendant universals to
   audit - do it with the restyle probe, not by eye.
7. **Nothing for the pipeline modal or the assistant frame.** Both are measured and both are
   below a millisecond in steady state; the modal's 48.6 ms first open is style resolution, not
   the loop.

Two things not to do, because the measurements say so: do not replace the wholesale `innerHTML`
rebuilds (the signature guards already skip them, and the rebuild is not in the top six), and do
not touch `applySnapshot` (8.5 ms of a 446 ms long task).

## 10. Caveats

- **The host was busy.** 36 node processes and several other agents' suites ran throughout. The
  same live route moved from 222 ms to 7.49 s between samples. Every route number is a range, and
  the lowest reading is the least-contended one, which is the one closest to the route's own cost.
- **The live process is older than this branch.** It booted from the main checkout, so its
  in-memory `lib/` code is not this branch's; `public/app.js`, `public/assistant.js`,
  `public/style.css` and `public/pipeline-modal.js` are byte-identical to this branch (only
  `pipeline-map.html` differs), so every client number here is this branch's code.
- **The hidden tab is not the visible tab.** The JS counters in section 4 were taken with
  `document.hidden` true, which is why `queueRow` flushed inline and why there was no paint. The
  `Performance` counters in section 4 and the restyle probe in section 7 were taken on a visible
  tab; they are the only numbers here that include layout.
- **The sandbox copy is a snapshot.** Its job mix differs from live (80 jobs against 104), and it
  was still running its boot discovery for the first 133 s, which is why its first minute is not
  quoted anywhere.
- **The wedge is proven by behaviour, not by a syscall.** The log line, the 45 s static request,
  the 10 s `/api/health` and the 0 to 1 ms read from a fresh process are consistent; which fs call
  never returned inside the server is not named, and the same module from a fresh process is
  healthy.
- **One assistant chat rebuild was not timed.** `renderAssistantChat` is inside the module IIFE
  and not reachable from the page; the frame apply was timed, the rebuild was not.
