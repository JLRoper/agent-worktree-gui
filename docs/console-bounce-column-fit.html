The console that bounces up and back down, and loses your place

Measured against main at c4a0093 (0.46.8). That is the build the board on 127.0.0.1:7331 serves: /app.js sha256 cd5df6626e4c…c179a, build id c6d5de5f4ce0. The fix is on branch wtgui/i-m-constently-trying-an-8a3c3c, and every number below was read on one of those two builds. Written 2026-11-01.

Answer

The bounce comes from the worktree table measuring its own columns. After every row repaint the panel asks what each column would be "with nothing constraining it" (naturalColumnWidths()). It answered by laying the live table out at table-layout: auto; width: max-content for one synchronous layout. That table's detail rows hold the agent cards. A console is a white-space: pre-wrap box, and at max-content it has no line breaks, so a paragraph that wraps over five lines becomes one line. For that one layout, every console in the table shrank to a fraction of its height. The browser clamped each scroll offset to the shorter box. When the styles went back the transcript was tall again, but the offset stayed clamped.

  • A console that was following its run was painted near its first lines. The next streamed line, or the 400 ms sweep, put it back. That is the "bounces up and quickly back down in a split second".
  • A console you had scrolled back in has nothing that puts it back, so it stayed wherever the clamp left it. That is the "loses my place and jumps somewhere else in the scrollbar".

A second, smaller defect made losing your place worse. setScroll() flagged every write as "the panel's own scroll", including writes that moved nothing. A write that moves nothing fires no scroll event, so the flag stayed set and swallowed your next scroll. The place you scrolled to was never recorded.

Both are fixed on the branch and measured. The real-browser gate went from 18 of 18 measurements moving a console (by 604–1139 px) to 0 of 18. On your own board, read-only, one measurement dropped two real consoles by 69 px and 86 px on the served build, and by 0 px with the fix in the same page.

2. The mechanism, step by step

  1. A worktree row is repainted (placeRow). That happens on every row event from the scanner (live rows every liveSeconds, 5 s here), on a file appearing in a worktree, on a removal. It ends in scheduleColumnFit(table), which runs fitColumns(table) in the next animation frame. fitAllColumns() does the same on a window resize, a zoom change and a column-grip double-click.
  2. fitColumns skips the work only when columnSignature(tbody) is unchanged. That signature includes tbody.textContent.length, and the tbody holds the detail rows, so it holds every console's text. While any agent in that table writes, the signature changes and the measurement runs.
  3. naturalColumnWidths(table) set table.style.tableLayout = "auto" and table.style.width = "max-content", cleared each header's width, and read th.getBoundingClientRect(). That read forces a synchronous layout of the whole live table, consoles included.
  4. In that layout the detail cell spans every column, and its max-content width is the longest unwrapped line of its transcript (thousands of px for an agent's paragraph). Every console in the table is laid out that wide, so its content height collapses. Chromium clamps any scroll offset that now exceeds the new scrollHeight − clientHeight.
  5. The styles are put back. The transcripts re-wrap and are tall again, but nothing restores the clamped offsets. This runs inside a requestAnimationFrame callback, so the frame that follows paints them.
  6. A following console is written back by the next stickSoon (the next streamed line or pacer tick, one or more frames later) or by the 400 ms stickConsole sweep. A finished turn's console streams nothing, so it waits for the sweep, up to ~24 frames. A console the reader parked is never written back.

3. Why it survived so many attempts

  • There was no writer to find. Every instrument in tools/ wraps the scrollTop setter, the scroll APIs and the DOM primitives that move a console. A layout clamp calls none of them. The repo already recorded the symptom as an unexplained "no-writer class": a pinned console falling 77 → 0 with "no scrollTop write, no scroll API call, no DOM primitive that carries the console, and no mutation of the console's own subtree" (docs/console-frames-7393-0461.md).
  • The thing that changed was an ancestor's style. The writes are style changes on the <table> and its <th>s, outside the subtree every MutationObserver was watching.
  • The fixtures could not show it. The stub gateways stream short lines. verify-console-independence.mjs breaks a line every 11–15 words, and a short line is already its own max-content width, so laying it out wider changes nothing. A real agent writes paragraphs. The new gate streams 70–130-word paragraphs, which is what makes the clamp visible.
  • It repairs itself. A following console is written back within 1–24 frames, so a slow sampler sees nothing. A fast one saw falls it filed under other names: "one painted frame, 3–6 rows (51–121 px) short of the newest line, every 2–4 s", and "87 px off their newest line 15–18 times per 100 s". On your board this measurement drops real consoles by 69 px and 86 px, the same envelope (4.2).

5. The fix

Fix 1: measure a copy, never the live table (naturalColumnWidths, public/app.js)

-  table.style.tableLayout = "auto";
-  table.style.width = "max-content";
-  for (const th of ths) th.style.width = "";
-  const natural = ths.map((th) => Math.ceil(th.getBoundingClientRect().width));
-  table.style.tableLayout = layout;
-  table.style.width = width;
-  ths.forEach((th, i) => { th.style.width = kept[i]; });
+  const probe = table.cloneNode(false);              // the table's own classes and inline style
+  if (table.tHead) probe.appendChild(table.tHead.cloneNode(true));
+  const body = document.createElement("tbody");
+  for (const tb of table.tBodies)
+    for (const tr of tb.rows) if (tr.classList.contains("row")) body.appendChild(tr.cloneNode(true));
+  probe.appendChild(body);                           // worktree rows only: no detail, no confirmation
+  probe.style.position = "absolute"; probe.style.visibility = "hidden"; /* … left/top 0, no pointer events */
+  probe.style.tableLayout = "auto";
+  probe.style.width = "max-content";
+  for (const th of headerCells(probe)) th.style.width = "";
+  table.parentNode.insertBefore(probe, table.nextSibling);   // same wrapper, so the same selectors size it
+  const natural = headerCells(probe).map((th) => Math.ceil(th.getBoundingClientRect().width));
+  probe.remove();

The copy is out of flow and hidden, and it leaves the page in the same task, so it is never painted. The live table's layout is never invalidated, so no console is laid out at another width and there is nothing to clamp. It is also cheaper. The old path re-laid out every open transcript twice per measurement, once unwrapped and once re-wrapped. The copy lays out only the header and the worktree rows.

Fix 2: only a write that moved the box claims a scroll event (setScroll, public/app.js)

-  selfScrolled.add(el);
-  el.scrollTop = v;
+  const from = el.scrollTop;
+  el.scrollTop = v;
+  if (el.scrollTop !== from) selfScrolled.add(el);

Most panel writes move nothing: the follow path re-sticks a console that is already on its newest line every frame. A write that moves nothing sends no scroll event, so the flag it set was left for your next real scroll, which the handler then discarded as "the panel's own". Reading scrollTop there costs no extra layout, because assigning it already lays the box out to clamp the value. Everything else in the handler is unchanged: the pin still follows your own gesture onto the newest line (2 px), and the record keeps its 32 px "was at the bottom" tolerance.

6. A side effect: the columns stop moving

A detail row spans every column. In an auto table layout its max-content width (the longest unwrapped line of the open transcript) used to be shared out over the columns, so the column split changed when a row opened and kept changing while agents wrote. The gate reads the split with the row open and then shut:

7. What this does not fix

  • One-line lag stays. A pinned console can sit 3–40 px (one or two lines) behind a row that grew, for a frame, until its stick lands. The count is the same before and after (17 and 16 frames in 30 s). It reads as the console catching up, not as a jump up.
  • The red gates in 4.4 stay red. They fail the same way on 0.46.8 and need their own work. Two of them cannot even start on main (pickFreePort). The 68 px "painted off its bottom" in verify-console-jitter's 🌊 run is a card outside any table, so the column measurement does not reach it. It is a separate, smaller lag and it is not explained here.
  • Cards outside a table were never affected. The unattached agents list and the assistant float do not live in a worktree table, so a bounce seen there would be a different mechanism.
  • Sideways-scroll mode was safe already. Below the columns' floor width (846 px), .detail-inner is pinned to the visible width, so the transcript could not widen during the measurement. The bug was desktop-only.
