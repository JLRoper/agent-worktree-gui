# Perf round 1 — is 0.78.1 slower than 0.75.0 on the same board?

- **Versions:** **0.78.1** from `origin/main` `fd36130` (this worktree, `wtgui/measure-whether-0-78-1-i-564931`) against **0.75.0** exported from `35b3c82` with `git archive 35b3c82 | tar -x` — never checked out over any worktree.
- **Run:** two panels per run, one at a time. Each has its own `PANEL_CONFIG`, its own `dataDir`/`scratchDir`/`jobs.json`/`assistant.json` under a scratch folder, its own free port (run A: 0.75.0 on `:62937`, 0.78.1 on `:53128`; run B: 0.78.1 on `:58525`, 0.75.0 on `:53853`), and a stub Runs API of its own. The reader's `:7331` board was never touched and its logs were never read. Every scan clock is pinned to 3600 s, `scanMode: all`, `threads: 5`, `refreshSeconds: 30`.
- **Method:** `node tools/perf-075-vs-078.mjs` (`--reverse` for run B). The probe builds the store, boots both panels through `tools/panel-testkit.mjs`, drives a real Chromium through `tools/browser.mjs`, and reads every number from the running panel's own HTTP routes and the page's own DOM. It was run twice, once in each order, because the second panel of a run reads slower than the first — so the verdicts below compare **position against position** (0.75.0 first in run A vs 0.78.1 first in run B), never a run's two halves against each other.

## Verdict per metric

| Metric | Verdict | The number that decides it |
| --- | --- | --- |
| `/api/state` median | **real delta — 0.78.1 is slower** | Position-matched: 66.6 → 83.6 ms (**+25.5%**) when both went first, 92.4 → 121.4 ms (**+31.4%**) when both went second. A repeat pair with the same probe (before the stream counter was rewritten) read 89.1 → 98.0 ms (+10.0%) and 81.6 → 101.1 ms (+23.9%). **Four of four position-matched comparisons are positive; median +24.7%.** The payload is not the cause: the body is 245–250 KB (+2.1%) and `JSON.stringify` of it costs 2–3 ms in one process. |
| `/api/state` max | **noise** | The max is a single-call statistic and it points the other way: 0.75.0 had the worst call in three of four runs (214, 323, 360 ms vs 155, 192, 187 ms). Neither tail is stable at 20 calls; the median is the number to trust. |
| Board first paint (cold) | **real delta — 0.78.1 is slower** | Position-matched: 6087 → 8922 ms (**+46.6%**) going first, 9804 → 11970 ms (**+22.1%**) going second; the repeat pair read +52.8% and +2.8%. **0.78.1 painted later in all four position-matched pairs**, though the cold scan makes the absolute time swing 2× (6.1–13.0 s), so the percentage is load-dependent. |
| DOM node count | **real, but trivial** | 0.75.0 read 8032–8046 nodes, 0.78.1 8081–8092 — ranges do not overlap, **+0.6% / ~45 nodes** on the same 200 rows. Real, small enough not to explain anything else. |
| Live intervals / timers | **no delta at all** | **16 intervals and 0 pending timeouts on every side of every run.** Nothing in 0.78.1 leaked a timer on this board. |

## What the two real deltas add up to

On an identical 200-row store, **0.78.1 answers `/api/state` about a quarter slower and paints the cold board later**, and nothing the page does afterwards — DOM size, timer count, stream churn, console render, idle RSS — is measurably different.

The state gap is not the payload. The two bodies are within 2.1% of each other, carry the same per-row key sets, and cost 2.0–2.8 ms to stringify in one process; the 80–120 ms is spent elsewhere in the snapshot path or in the process's own scheduling. `lib/scheduler.js` is the one changed file on that path — `ctxFor()` became `async` and now awaits `resolveBaseRef()` **per row scan** (`lib/scheduler.js:141`, `:511`) — but a per-row promise resolve on a 60 s remote cache costs microseconds, not 30 ms, so this document does not claim that as the cause. It is the first place to look; the measurement above is what needs answering.

The paint gap includes the initial scan, so it inherits the same per-row work and is the noisier of the two numbers. The warm reload paints — 462–770 ms across both builds — do not separate.
