The answer

The document loads and drives. The studio's own importer reads the YAML, its own exporter writes the bundle, and the panel's own loader accepts it without a warning: 24 stages, 42 handoffs, 4 gates, one loop edge carrying cap: "3 rounds, then a person reads the blocking set".

As written, the row visits 10 of the 24 stages — S180, S181, S191, S192, S198, S199, S200, S201, S202, S203 — and parks three times, always on a gate (pipeline-gate), each released by the record's own arrival. The nine-way fork at S180 is walked as one edge, so the eight method lanes (S182–S189), the ledger keeper (S190) and five of the six question lanes (S193–S197) never run.

The declared loop is never taken. H-200-201 (sequence) sorts before H-200-191 (loop), so crossings["H-200-191"] = 0 and no pipeline-cap park can happen. With those two rail edges removed, the loop runs: 3 crossings, a cap park, the reader's release (3 → 0), re-entry, and a second cap park.

Every route used one tree, cut once and reused by every stage run; git worktree list shows two entries at the end (the repository and the one tree).

Seven things went wrong in the executor (two structural limits, five defects). The two that matter most: from the 20th thread the record stops naming the run, so every later stage settles against a stale finished job; and the last stage's settle is never written, so the row sits running at S203 forever with its final stage run still null.

The run did not end where the design says it ends

Neither route finished the document. The document route stops at S203 with the last stage settled in memory and dropped (pipeline-settle-unwritten); the loop route stops on pipeline-cap at S200, which is the designed park — but the rounds that reached it were already settling against a stale job (finding 5).

What was routed

Three readers, in order, and each is the real one:

  • the studio — core.importDocument() reads the YAML subset the document is written in; core.exportBundle() writes the pipeline the studio's own export button writes;
  • the panel — parseBundle() (lib/pipeline-bundle.js) accepts or refuses it whole, before a single sweep;
  • the panel's clock — Assistant.sweepQueues(), which is driveTaskPipelines, settleTasks, the one writeQueueFile, the journal, the tree cut through jobs.makeWorktree, the gate barrier's decisionPathOf, and the reader's pipeline-release. Nothing in lib/ is stubbed.

A seat wrote each stage's artefact and committed it (tools/pipeline-exec-stage-seat.mjs); a gate seat wrote each decision record only after a park had been observed. The model is scripted — there is no gateway — but the routing, the trees, the commits, the pins, the barrier and the release are the panel's own code.

The loop, the cap and the release

A loop that shares its stage with the rail is unreachable (finding 2), so the control route is the same document with exactly two handoffs removed: H-200-201 and H-200-202. Everything else — 24 stages, 42 handoffs minus two, 4 gates, the loop's cap — is the document's own.

Did the cap release?

Yes, mechanically. H-200-191 went from 3 to 0, waitingFor was cleared, the row returned to queued at S200, and the loop resumed: three more crossings and a second cap park at sweep 26.

It did not release into a working round. The release requeues the stage that parked (S200), so the row re-ran S200 at the same visit — the ledger carries two S200#4 entries — and by then the twentieth thread had been reached, so the stage was settled against the stale job (finding 5). The release moved the record; it did not put a worker back in the loop.

The release record, verbatim from the ledger: {"edge": "H-200-191", "from": "S200", "to": "S191", "limit": 3, "used": 3, "ok": true}.

1. A fork is one edge, not many

The executor takes ONE edge out of a stage: edgeOutOf sorts by kind (sequence, return, loop) and then document order, and nextStageOf follows that one edge. S180 has nine sequence successors; the row took H-180-181 and never entered S182–S189, S190, or S193–S197. 10 of 24 stages ran. The document's own comment says the fourteen lanes cannot be declared concurrent — the executor does not merely fail to run them at once, it runs one of them.

task-pipeline-drive.js:150 task-pipeline-drive.js:673

2. The rail out of S200 shadows the declared loop

S200 has three edges: H-200-201 (sequence), H-200-202 (sequence) and H-200-191 (loop, cap: "3 rounds, …"). EDGE_ORDER puts sequence first, so the loop is never a candidate: crossings["H-200-191"] = 0 after the whole route, and the pipeline-cap park never happens. A document whose loop shares a stage with its rail cannot loop, whatever its cap says.

task-pipeline-drive.js:148 task-pipeline-drive.js:700

3. A per-round artefact path resolves to round 1, every round

decisionPathOf matches a {{hole}} segment with readdirSync(dir).filter(…).sort()[0] — the FIRST name in sorted order. Every artefact in this document carries r{{round}}, so every visit reads r1. S191 was visited 7 times; the ledger records ea429fd4… at all seven, and the seven files on disk are seven different 160-byte files. The ledger's unchanged: true on every loop visit is this resolver, not the work.

task-pipeline-drive.js:201 task-pipeline-drive.js:1099

4. Every artefact is pinned as uncommitted work, with no blob

artifactCheck feeds relInTree found.shown — the path built from the DECLARED segments, holes included — instead of found.path, the file that was actually found. git rev-parse <commit>:out/{{run_id}}/site-ranking.json fails; git rev-parse <commit>:out/run-1/site-ranking.json answers 47abd1269f52907a23a8de7ff6fc14548245c5c6. All 9 document-route artefacts record uncommitted: true and blob: null, and the next stage's prompt says so in words.

task-pipeline-drive.js:1099 task-pipeline-drive.js:185 stage-pin.js:57

5. After 20 threads the record stops naming the run, and stages settle on a stale job

TASK_THREADS_MAX = 20: normThreads drops every thread after the twentieth, so currentThread(task) returns loop-20 for the rest of the row's life. The loop route started 38 workers; the record names 20; 19 of the 30 surviving stage runs name loop-20 — and the last 18 of those are stages that ran AFTER it, each settled on that finished job without waiting for the worker that was actually running.

assistant/queue.js:54 assistant/queue.js:130 assistant/queue.js:144

6. The last stage's settle is never written

sweepQueues writes the queue file only when something moved or a start was asked for. At the last stage the driver has nowhere to move (S203 is the end) and asks for no start, and settleTasks will not close a row with a tree until its PR reads MERGED — so the settle the driver computed in memory is discarded on every pass. After 16 sweeps the row still reads running at S203, the stage run still reads status null, and the job that did the work reads done.

assistant.js:1201 assistant.js:1191 assistant/queue.js:1182

7. A gate's per-round record is not re-asked in the next round

G51 declares ledger/gates/G51-{{run_id}}-r{{round}}.json. Once G51-run-1-r1.json exists, the same first-sorted-match rule finds it in every later round: G51 was crossed 11 times and parked 1 time, on round 1's decision. The per-round record the document declares is written once and read forever.

What this does not prove

  • Nothing here is a model's work. The seat is a script; the findings are about the executor's routing, records and file resolution, not about whether a stage's prompt is any good.
  • The document route's numbers describe the graph the executor walks, not a claim that the document is wrong: it is a document written for a reader and a drawing, and the executor reads one edge out of it.
  • The loop route is a derived document. It removes two rail edges to reach a loop the original cannot. Its rounds 1–3 are real work; from the twentieth thread its later stage runs are settled against a stale job, so the counts after that point are the executor's, not a worker's.
  • The stage-run ledger is capped at 30. The loop route produced 38 stage-run entries (37 distinct visits); the writer kept the newest 30 and recorded runsDropped: 8. The first eight (S180–S200 of round 1 and S191 of round 2) survive only in visits, crossings and the journal.
  • No PR was opened and no merge was simulated. The last-stage row therefore never reaches the landing rule that would close it (finding 6).

Reproducing it

node tools/pipeline-exec-poc-rounds.mjs --route both --verbose

The harness writes its ledgers under docs/reviews/poc-rounds-execution-<date>/, one directory per route, and copies nothing from the panel's own state. The fixture repository holds the document under test at docs/pipeline/poc-breaking-rounds.yaml, so the tree's own history shows every artefact commit beside the document that asked for it.
