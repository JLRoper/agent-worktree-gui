The one-page answer

Nine fixes were ranked. None of the nine has landed. Five are code (1 to 5) and four are process (6 to 9). Every code-level verdict below was produced by calling the module that owns the behaviour and printing what it returns today, not by reading the round-4 prose again.

The two that killed stage 2 are fix 1 and fix 2. Fix 1 is the stamp guard that refused stage 1's record before the drive read the graph, so the pipeline never cut its own second stage. Fix 2 is the park that writes a decision and no run status, so the run it parked on could not be read as finished by any later pass. Fix 1 is the trigger; fix 2 is why the refusal was unrecoverable. Details, with the measured output, are in the next section but one.

The suite is green and says nothing about any of this. test/task-pipeline.test.js and test/assistant-queue.test.js pass 49 of 49 as the tree stands, and not one of the nine paths has a case. Worse, three existing cases pin the shape the fix would change: the visit counter, the reused stage-run id, and the retry that reuses an entry.

The next commit is fixes 1 and 2 together. They are one behaviour: a record the guard accepts, and a park that settles the run it parks on. Until both are in, the next ping-pong round reproduces the round-4 shape - a person cuts stage 2 by hand. Fixes 3 and 4 follow, because they are what makes the ledger readable afterwards.

Every line number in fixes 1 to 5 in round 4's table had moved by the time this page was written (the park moved 62 lines). This page gives the anchor as it stands, beside the function name, so a reader can find it after the next shift. The round-4 page's sha256 column still verifies at main; its blob at 3facbfd column does not, because the rebase merge re-created those commits.

Which two killed stage 2

Plainly: fix 1 and fix 2. The order matters, because only one of them is the trigger.

fixwhat it did in the roundthe code that did ittoday
1 The trigger. The hand-off read stage 1's finished record, the stamp guard refused enteredAt, resolveTaskPipeline returned unresolved, and the drive parked the row before it ever reached the settle or the handoff. The pipeline's own stage 2 was never cut. task-pipeline.js:36 task-pipeline.js:56-62 task-pipeline-drive.js:1481 Refused, identically. A six-digit fraction still fails the pattern and still gets the "no zone" sentence.
2 Why it could not be recovered from. The park wrote a decision through recordStageDecision, which is settleStageRun with only a decision. Status stayed null, so no later pass could read stage 1's run as finished and advance it: the repair had to be a person writing status: done by hand, 22 minutes later, on a different row. task-pipeline-drive.js:1459 task-pipeline.js:287-313 Still null. The same call, unamended, returns {"status":null,"settledAt":null,"hasDecision":true}.

Why both, and not one: with only fix 2, stage 2 still does not run, because the guard refuses the record 60 lines earlier. With only fix 1, stage 2 runs, but the ledger still cannot say that the run it advanced from finished - which is the defect the draft was written to prove. The pair is what turns "a person cuts stage 2" into "the drive cuts stage 2".

The refusal names the wrong cause, and that is fix 1's second half

Two different inputs produce the same sentence today: a stamp with no zone at all, and a stamp whose fraction is too long. Measured this run, both print is not a UTC instant - the panel stores Date#toISOString(), and a local-time stamp has no zone to subtract from. The six-digit stamp carries a zone; the message names a cause that is not there. That is why the round-4 decision survives in the record reading as a contradiction.

Process gaps

Four of the nine are about how a round records itself, not about the pipeline's behaviour. They are here, short, because they fail differently: no suite can catch them, and each one costs the next reader a search.

gapwhat it looks likewhat would close it
The waiver is silent
fix 6		 The gate refuses; --no-verify sends the branch; the only record is a sentence in a run log that was itself edited afterwards. A PR body then offers a policy the versioning page does not state ("a docs-only branch lands at the base version"), which sends the next reader to a rule that does not exist. Write the waiver on the row and in the log at the moment of the push, or do not push. The gate's own refusal line is the thing to quote, not to skip.
The PR body freezes at creation
fix 7		 gh pr create --fill writes once. Three commits landed after it in round 4 and the body still lists three of five. The body is the record a reviewer reads first, and it is the least current artifact in the landing. What this does not prove

  • No probe drove a pipeline end to end. Fixes 1 to 5 were measured by calling the module that owns the behaviour (elapsedInStage, settleStageRun, startTask's state writer, visitOf) and printing the result. The drive's own path was read, not run. The end-to-end instance of each failure is round 4's record, which this page did not re-run.
  • Fix 2's scope is narrower than round 4's sentence suggests. The done path already settles with a status; the open case is the park that has no run settle in front of it. That is stated per-card above, and it is the one place this page corrects the brief.
  • Fixes 6 and 7 are manual acceptances. There is no gate to run for either; the card names the check a person would run, and the tree is green on neither because neither exists.
  • Fix 9's acceptance cannot pass yet. job.startedAt >= tree.cut is false by construction; the card says so rather than presenting an unattainable test as the bar.
  • The suite reading is two files, not the whole suite. 49 of 49 in test/task-pipeline.test.js and test/assistant-queue.test.js, the two files nearest these paths. That is the claim: green, and blind to the nine.
  • This page changed no product code. It is a record of measurements taken at 1b03f0a, and its own branch carries the page plus the version bump.
