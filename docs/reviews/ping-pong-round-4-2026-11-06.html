The answer

Two stages ran. The pipeline cut one of them. The drafter worked 14:30:33 to 14:48 and left a 928-word design note in ledger/ping-pong/draft.md (4826ed9), plus the log (cdf0ea4). At 14:49:44 the drive read the finished job, refused the row's record and parked #211 with pipeline-unresolved. It never cut the critique. A person created row #214 at 14:56:14, and that worker ran 14:57:31 to 15:11:31, wrote ten notes (five blocking, verdict not accepted) and left ledger/ping-pong/critique.md plus two more commits.

Both workers succeeded; the record of them does not. The draft stage run settled 6.5 seconds after the critique it precedes. Both rows report startedAt equal to doneAt, stamped after the job had already ended, so a 20m21s run reads as 0s. The id ping-pong/draft#1 names two different runs on the two rows, with different threads, jobs and statuses. visits.critique reads 2 while the ledger holds one critique entry at visit 1.

The push is the one part of the round the ledger argues with itself about. Stage 1 refused it, in its own final message. Stage 2's hand-written brief ordered it in five words. The refusal quotes a stamp that passes its own guard

The parked row's reason reads: enteredAt "2026-11-06T19:28:20.426Z" is not a UTC instant - the panel stores Date#toISOString(), and a local-time stamp has no zone to subtract from. That string carries a zone, and the guard's own pattern accepts it (RE.test("...426Z") is true; the same stamp with six fraction digits is false). Whatever was refused, the message names the wrong cause, and the reason survives in the record after the stamp was repaired.

What the hand-off did, and what it refused

"The hand-off" is the panel's drive between stage 1's settled job and stage 2's start. Its whole input is the queue row and the bundle; its whole output is a park, a new stage run and a job. Here is what it did with this row.

It did

  1. Cut one tree from main and reused it for both stages. git worktree list holds one entry for this tree, and both jobs record the same cwd.
  2. Stamped the pipeline on the row before the turn began (enteredAt 19:28:20.426Z) and the stage run's thread and job (19:29:47.318Z), so the ledger knows which worker ran.
  3. Waited for the worker instead of racing it: the row stayed live for the job's whole 20m21s, and the drive acted 3.6 s after endedAt.
  4. Parked the row with a manual hold and wrote a decision on the stage run in the same write (lib/task-pipeline-drive.js:1392-1394).
  5. Left the tree, the branch and the ledger intact. The critic read the same commit range in the same directory, and the draft it reviewed never moved (git diff cdf0ea4..HEAD -- draft.md is empty).
  6. Pinned both artifacts to a commit and a blob, on the second row, 22 minutes late but exactly: both sha256 values equal the file on disk today.

It refused

  1. The record. resolve(task) failed on enteredAt and the drive never reached the graph (lib/task-pipeline-drive.js:1518).
  2. The next stage. No critique entry on #211, no second thread, no second job. The pipeline's own stage 2 was never cut; #214 is a separate row that a person wrote.
  3. The settle. recordStageDecision passes only a decision (lib/task-pipeline.js:347), and settleStageRun writes settledAt only when a status is present (:310-316). #211's entry kept status: null, no settledAt, no artifact and no commit pin for 22 minutes.
  4. The terminal word. The job ended done; the row's sentence says the record is unresolved. Nothing on the row said the worker had succeeded, and the draft's own subject - "a failed stage run" - never happened here.
  5. The job's pipeline. The hand-cut job carries pipeline: null. The row knows it is a stage; the job store does not.
  6. The push, twice. Stage 1 refused it in its final message ("committed locally, not pushed"); the hand-written stage-2 brief ordered it; the version gate refused it; --no-verify overrode the gate.

What worked

  • Both workers finished on their own terms. Exit 0, status done, 20m21s and 14m00s, no turn budget hit, no approval left open (jobs.json).
  • The artifact pins are exact. Row #214 records draft.md as sha256 5cae569d... at blob d7e534d6... and critique.md as b3d61096... at blob 8cc4cd4f...; sha256sum and git show HEAD: answer the same values today, and the draft's blob is identical at cdf0ea4 and 3facbfd.

Ten notes, five blocking, four citations in the draft that do not survive contact with the code, one missing actor (settleTasks retries a failed row automatically), and a verdict that refuses the draft rather than praising it. It also corrected its own arithmetic in 3facbfd.

  • The tree was kept, not recut. The draft's invariant 7 holds: one tree, no reset, no clean, and the critique ran in the directory the draft was written in.

1. A six-digit fraction reads as "a local-time stamp"

STAMP_RE accepts a fraction of one to three digits: (?:\.\d{1,3})?Z (lib/task-pipeline.js:37). A stamp written from a microsecond clock - six digits, which Date.parse itself accepts - fails the test, and the failure message at lib/task-pipeline.js:61 is about a missing zone. Measured against the guard's own pattern: "2026-11-06T19:28:20.426Z" passes; "2026-11-06T19:28:20.426123Z" fails. The row detail for #214 says the stored record carried a six-digit fraction, and that is the only value the pattern refuses; the decision's own reason, read today, quotes the repaired three-digit stamp and therefore contradicts itself.

Effect. The hand-off stops before it reads the graph, on a record that is otherwise complete. Here that cost 6m30s (park 14:49:44, replacement row 14:56:14) and the pipeline's own stage 2 permanently.

2. The parked branch writes the decision but never the run's status

stop() parks the row and calls recordStageDecision (lib/task-pipeline-drive.js:1392-1394), which is settleStageRun(task, { decision }) (lib/task-pipeline.js:347). settleStageRun sets settledAt only inside the status branch (lib/task-pipeline.js:310-316), so a park writes the decision and leaves status null. The done branch passes the status and settles properly (lib/task-pipeline-drive.js:1561).

Evidence. #211's draft entry at 19:49:44 has the decision and nothing else: status: null, no settledAt, no artifact, no commit. It stayed that way until 20:11:42, when the hand repair wrote status: done and a settle time. This is the draft's central finding, and the run the draft was written from demonstrates it.

3. One stage-run id names two different runs

stageRunId is <pipeline>/<stage>#<visit> with no attempt ordinal (lib/task-pipeline.js:186-192), and settleStageRun finds its target by stage and visit alone (lib/task-pipeline.js:295-300). So any later settle for the same visit rewrites whichever entry it finds last, whatever thread that entry ran on. Row #214's draft entry is exactly that write: thread ...adbec0, job 65101f07, status done - the critic's thread and job on the drafter's entry. The string "settled by hand" on it appears in no module (grep -rn over lib, public and tools finds it only in an unrelated comment in public/app.js), so the entry was edited outside the stage-run writers.

Effect. The same id answers two different questions depending on the row a reader opens. The draft's invariant 6 - two entries never share an id - is not merely unimplemented; the panel's own repair is what broke it.

4. Every row reports zero duration, stamped after the job ended

In the done transition, startedAt is backfilled with the settle clock: updated.startedAt = t.startedAt || atIso; updated.doneAt = atIso (lib/assistant/queue.js:678-681). A row that was never set running therefore records its finish as its start. #211: 19:59:11.069Z for both, while its job ran 19:29:19.534Z to 19:49:40.989Z (20m21s); the row starts 9m30s after the work ended. #214: 20:12:30.846Z for both, while its job ran 19:57:31.628Z to 20:11:31.758Z (14m00s). The correct stamp already exists for the spawn path (lib/assistant/queue.js:739); these rows were never taken through it.

5. The visit counter and the ledger disagree

assignPipeline with enter: true increments visits[stage] (lib/task-pipeline.js:367) and enterStage increments it again (:398), while visitOf reads it (:213) and stageRunId mints the id from it. Row #214 reads visits: {critique: 2, draft: 1} and holds one critique entry, visit 1. The second increment came from the re-press after the repair, which wrote no entry. A later settle on that stage would mint #2 and leave #1 untouched, so the row would hold two critique entries for one critique that ran once.

6. The push was waived past the version gate

Stage 1's final message reads "Stage 1 is committed locally, not pushed", and its run log's first version of the push line (line 21) gives the reason. Line 37 then reverses it: the project's config reads remoteBranchPolicy: allow, so the branch "goes out with this commit". The chained gate refused the push at 15:06 ("Nothing was pushed. The bump belongs in the same PR as the change"), and line 43 records git push --no-verify, which is gate 5's named waiver. The PR body then offers a policy the versioning page does not state: "A docs-only branch lands at the base version (docs/versioning.md)". That page says the number is anchored by an annotated tag at the commit that first declares it (docs/versioning.md:12-27); it has no docs-only exception. Measured at 3facbfd, before this branch's own bump: node tools/version.mjs check exits 1 with "this branch's version is behind origin/main's" - branch 1.41.0, base 1.41.1 at db8a9bf.

9. The job starts before its tree exists

Job ee265bc1 stamps startedAt 19:29:19.534Z; the tree's cut record is 19:29:29.323Z, and the row's start is 19:29:47.318Z. Either the field is the request's stamp or the worker was asked for before its tree - the run log flagged the same anomaly at line 23. 10. The row's rendered sentence carries U+2014
