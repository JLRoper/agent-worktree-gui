The flow press works. The form behind it lies about what it will draw.

A real Chromium session against the live panel on 127.0.0.1:7331: Settings → Pipeline → open the flow. The dialog is the same one a queue row's flow press opens, it is never empty for any of the seven definitions the panel holds, and every measurement below comes from the DOM it actually painted. What it exposed is one step earlier: add stage and remove stage change the draft without repainting the form, so the drawing and the form disagree — and the drawing is the honest one.

2 · Is it the same dialog the row's flow press opens?

yes One overlay, one card, one renderer. The queue row's press is openTaskPipelineFlow() (public/assistant.js:3925), which calls the same PipelineModal.open() with mode:"position" and draws from PipelineFlow.fromBundle() / fromWindowModel() instead of fromDefinition(). The dialog's own header states the contract (pipeline-modal.js:1–10): “The callers differ ONLY in mode.” The two modes differ in three visible ways — the kicker (pipeline flow · definition vs · position), the marks (a definition has no position, so every stage is not-reached), and the preview select, which only position mode draws.

This capture could not press a row: the live board carried 0 [data-as-qflow] controls during the run (no assistant had a queue task on screen). So the equivalence here is by call site and by element identity, not by a second photograph — stated plainly rather than implied.

4 · What is wrong

Wrong

“add stage” and “remove stage” change the draft and never repaint the form. Both handlers set pipelineDraftDirty = true and then call paintPipelineEditor(), whose first act is to return when the draft is dirty (public/app.js:17748). The reader gets a status line describing an edit that has no row to make it in.

Measured, in order: two presses on #pipeline-add-stage → the editor still shows 1 stage row while the status reads “unsaved changes — a new stage has no id or prompt yet” and the draft holds 2 stages (the flow press draws “2 stage 2”). One keystroke in the stage title → updateDraftFromForm() rebuilds the stage list from the DOM rows (app.js:17833), so the invisible stage is silently dropped and the draft is back to 1. Pressing remove on the only stage → the row stays on screen while the draft holds 0 stages and the flow says “this pipeline holds no stage, so there is nothing to draw”.

Should be

A press that changes the set of stages rebuilds the stage rows — a forced repaint that keeps pipelineDraftDirty true and does not print “no unsaved changes” underneath it. The no-repaint guard exists for read-driven repaints (a timer or a catalogue re-read must not eat the caret); a button press the reader just made is not that, and has no caret to protect.

Why this matters beyond the two buttons

savePipelineEditor() (app.js:17867) calls updateDraftFromForm() first, and that function rebuilds pipelineDraft.stages from the same DOM rows (app.js:17833). So Save would write the form as it appears — silently discarding an add and resurrecting a remove — which makes the two controls no-ops rather than merely confusing. And because addPipelineStage() also calls updateDraftFromForm() before appending, a second press cannot add a second stage: it reads the single row back and appends to that.

The flow press is how this was found, and that is the point of the round: it is the one surface that renders the draft instead of a form widget, so it disagreed with the form in exactly the state the form cannot show.

5 · What is right, measured

  • Escape is scoped. Escape in the dialog closed the dialog and left Settings open — #settings still visible, #pipeline-modal hidden.
  • Focus returns. After the close, document.activeElement was #pipeline-flow-open — the control that opened it.
  • A dirty draft is announced. With an unsaved edit, the dialog's subtitle reads “unsaved changes” and the header carries the draft's stage count, not the saved one.
  • The count line only appears when it has something to say. At 1440/1100/900 px: “all 7 stages and 7 notches in view”, the status row hidden. At 760 px: “showing stages 1–6 of 7 — 1 of 7 stages and 2 of 7 notches out of view”, status and fit shown.
  • “not reached” is not a bug. A definition has no position — a task carries it — so every stage is drawn data-mark="not-reached" and the legend says “not reached 7 stages”. The marks-from attribute names the rule it used (data-marks-from="index").
  • No page errors and no console errors across the whole run (pageerror 0, console.error 0).

6 · Why no code landed with this report

The brief allows a one-line fix and asks for a report first. This is not one line, and the honest version touches the file's own caret guarantee: a force parameter on paintPipelineEditor(), the terminal setPipelineStatus("no unsaved changes") conditioned on the dirty flag, and the two call sites passing it. Written out, that is the patch below — deliberately not applied, because the guard it opens is the one the tab's header comment spends a paragraph defending, and a half-tested change to it is worse than a report.

// public/app.js — proposed, not applied
function paintPipelineEditor({ force = false } = {}) {
  ...
  if (pipelineDraftDirty && !force) { paintPipelineFindings(); return; }
  ...
  setPipelineStatus(pipelineDraftDirty ? "unsaved changes" : "no unsaved changes");
}

function addPipelineStage()    { ... pipelineDraftDirty = true; paintPipelineEditor({ force: true }); ... }
function removePipelineStage(i) { ... pipelineDraftDirty = true; paintPipelineEditor({ force: true }); ... }

Two smaller routes were considered and rejected: disabling the two controls while dirty leaves a definition uneditable for the rest of the session, and writing the row straight into the DOM duplicates the markup builder that paintPipelineEditor() owns.
