The six oversized files

Where this tree can be cut, what each cut buys, and what it costs — folded from four documents written by two agents over three rounds, with every disagreement either decided or left standing in the open.

Snapshots: cc61bb9 (0.84.0) · 0.85.3 · anchors re-checked at 0.102.0. No source file was modified by any round: the review is five documents and a version bump.

The one-paragraph answer. The server half is a clean acyclic library (85 modules, 187 edges, zero import cycles) hanging off a 5,435-line composition root that is also the whole HTTP API; the client half is sixteen classic scripts with no imports at all, sharing one namespace and one mutable state object, so a client "module" is a cut through names rather than a dependency edge. The work that pays is not "split the big files": it is (a) move the server's route chain and its header helpers out, once, serially, (b) move one client vertical at a time, beginning with the settings tail, and (c) accept that the division of labour is bounded by one three-line file — package.json — that every landing must touch.

The route chain, and what the existing factories really are

The dispatcher is a linear if sequence inside one request callback, not a table: 123 branches at cc61bb9 (122 route === comparisons plus one route.startsWith prefix branch), 3,215 of the callback's 3,233 lines being branch bodies. At 0.87.1 the same count is 127. The branches are interleaved, not contiguous — the worktree group spans the assistant and settings branches — so the chain is ordered by arrival, not by subject. B1 A1

The idiom already exists three times, and it is one-path RPC rather than group dispatch: each factory guards a single path and dispatches on an action field, taking its transport helpers as named arguments and returning false to fall through. A route group has 13, 14 or 23 paths, so the first group factory needs a method-and-path table that the existing three do not have. That is one small design decision, and it should be made once, on the first group. B2

Verdict — the count to use

75 branches migrate; 48 stay in server.js. 123 total, minus the 48 that belong to the process and the SSE entry. The three existing factories do not appear in the chain at all — they are intercepted before the dispatcher — so they are precedent, not progress, and must not be subtracted a second time. B2 corrects A2's 72 here, and B2 is right; see §10.

Mount point is part of the contract. authorised is called once, and the boot-pass flag bootPassCanSatisfyReload is cleared, both before the factories mount. A factory mounted at the same point inherits both; one hoisted above those lines silently loses them. B2

4. The client half: no modules, one call-time loop, one mutable object

Sixteen classic scripts, 30,055 lines, zero static imports. Their graph is the global namespace: which top-level name of one file appears in another. That is a weaker measure than an import — a mention in a comment counts — so every client number below is a reference count, not an edge count. B1

What "cycle" means on this side

Verdict — the sentence that must never travel

"The tree has no cycles" is true of lib/ and false of the product. The two documents are not disagreeing: they measured different graphs. The server graph is ESM imports — 85 nodes, 187 edges, 0 SCCs. The client graph is name references — 16 files, and one loop of 9 files: app.js ↔ dom-format, console-format, console-markdown, sse, transport, attachments, hot, paste-chips. The other seven — model-menu, stream-merge, liveness, steerable, type-stream, update-check, assistant — read app.js and are read by nothing.

B2 refines the word further: on the client there is no import graph, so every edge is a call-time back-edge. sse.js's reads of app.js all sit inside connect(), and connect() is called by app.js after every name it needs already exists. dom-format is stricter still — it loads first of all sixteen and executes nothing at load, so its back-edges cannot be "broken by load order" at all. The invariant is not "load order breaks cycles"; it is "no top-level statement may read a name another file provides", which is the load contract in §4.

The load contract — phase 1 and phase 3

public/app.js carries 222 top-level statements, 24 of which assign a state.* property. A region that carries one of those cannot move before app.js, because state is being built there. A1 B1 reproduced both numbers independently and exactly.

Verdict — it is a phase, not an exception

A2 first called the after-app.js slot "a fourth phase nothing else uses". B2 is right and A2's framing is withdrawn: two scripts already load after app.js — core/update-check.js and assistant.js — so adding a third line is the cheapest change available, and it is the correct home for every region that executes at load. The contract is two-sided: phase 1 (before app.js) is pure declarations; phase 3 (after) is anything that executes. Stated that way the 24 writes stop being a list of exceptions and become the definition of a phase the page already has two examples of.

The markers are an API, and one range is pinned by an anchor, not a marker

Fourteen test and tool files slice public/app.js through sliceRegion / sliceBetween; nine more cut their own indexOf("// ----") anchors, for a union of 22 files of the 40 that read app.js at all. B2 counts higher — 19 through sliceRegion once tool files are included, 29 once own-indexOf cuts are added — and the three definitions are reconciled in §10 rather than averaged.

The sharpest failure mode either document found B2

test/ahead-behind-cell.test.js pins two ranges that are not section slices: one from const CHART_COLUMNS = [ to the // ---- end chart columns closer, and one from function verdictHtml to the // ---- end merge control closer. verdictHtml belongs to a different section than the marker that bounds it. These ranges depend on what sits between an anchor and an unrelated closer, so a vertical cut that moves either symbol changes the slice without touching either marker — and the failure is a failed assert.match, not a thrown "missing region". Making the markers honest does not fix it; the anchors are positional. Both ranges must be re-expressed as section slices before any vertical move that crosses them.

The one costed statement A2

A cut buys the commits that stop sharing a file and costs the names that must stay visible across the new boundary; collision relief is bought by the number of parts (100% → 39% at K=12 → 28% at K=24) and is nearly independent of where the boundary falls (equal-line K=7 is 51% against 56% for a hand-placed partition), while surface cost is bought by where it falls (444 names equal-line against 320 hand-placed at the same K=7, a 28% saving) — so boundary choice is a cost decision, part count is a benefit decision, and the two are separable.

The knee is in the marginal rate. From K=8 to K=12, 8 points of relief cost 20 names — 40 points per 100. From K=12 to K=24, 11 points cost 77 names — 14 per 100. Same direction, a third of the rate. That is B1's "stops improving past 16" seen from the other axis, and it is why "more files" stops being the lever while "a better boundary" never does.

The limit both drafts hit: neither measured a true vertical. Every cut in the table above is a contiguous band of lines — B1's at marker boundaries, A1's at hand-chosen ones. A vertical takes a feature's state, renderer and handler out of three separate places, and its collision advantage is a hypothesis with a plausible mechanism (a median app.js commit edits 3 of 143 sections) and no measurement behind it. A2

7. The landing lock: package.json

The guaranteed shared file is not the one anyone expects. package.json is touched by 124 of the last 200 non-merge commits (B1 measured 120 on its window), and it cannot be avoided: the pre-push hook runs the version gate, which refuses a branch that carries commits without a bump, and the repo's own versioning doc makes even a document a patch. B1 A2

The landing-concurrency rule A2

Landing concurrency is 1, and package.json is the lock. Bump on the landing tip, in the landing commit, after the rebase — never at branch cut. A branch that carries a bump taken from its cut is a guaranteed conflict for whoever lands next, and every branch is the next landing. Serialize on the bump, not on the code.

The demonstration is this very branch. Round 1 cut from 0.84.0 and bumped to 0.84.1 in the same commit as its document. Main moved to 0.85.2; the pull request came back CONFLICTING on package.json alone, with the document merging cleanly. The fix was a rebase and a re-bump to 0.85.3 — one extra conflict resolution, on one file, for one PR. At 124 of 200 commits the repository pays that constantly, which is why the project has a landing-turnover model rather than a merge bot.

Three consequences that follow from the measurement rather than from taste:

  • The bump is a rebase-time edit, not a commit-time edit. It belongs in the commit that is about to be pushed onto the current tip.
  • Two landings cannot be truly parallel. A module split changes what conflicts, never whether the landing serializes.
  • The version is read once, at boot, so a stale version is a board-config-line bug, not a running-process bug. That is why "bump at landing" needs no restart story.

9. Dropped, and still contested

Dropped: the chart / ranking cut (A2)

B2 would drop it as a unit, not defer it, and the numbers support that. Its sub-region beside the chart-columns section carries 34 hunks while the 119-line chart-columns section itself carries 0; its surface is the worst in the file (58 names, 76 outer dependencies); and it contains one of the two anchor-to-closer test ranges. A cut that produces "the same file with a longer relative path" — A1's own phrase — is not a seam. The honest entry is no entry; the churn band beside it may be re-measured as its own candidate before anyone signs it. A2 had it last; adopting the drop.

Four things A2 will not concede

  1. That a vertical split buys collision relief. Neither document measured one. At the same part count, a responsibility-aligned contiguous partition is worse on collision (56% vs 51%) and better only on surface (320 vs 444 names).
  2. That public/core/dom-format.js is a leaf or a cut point. It sits inside the 9-file loop — it reads state, normPath, panelFor and isRowLive back out of app.js, as its own header declares — and it is already a separate 183-line file. Its real property is that it is the cheapest member of the loop.
  3. That the cold substrate is healthy. 50 of 83 modules untouched in 49 hours proves they are not where this weekend's contention is; it cannot prove they are sound.
  4. That the 78-name client surface is a number. It is 66 with comments and strings stripped and 78 with them counted; the plan needs the lower one.

Three things B2 will not concede

  1. The client cannot be the last thing done. A plan whose first six landings leave the three busiest files untouched has optimized revertibility at the cost of the complaint.
  2. The marker API is larger than 14 files. Own-indexOf cuts and the anchor-to-closer ranges pin text that no sliceRegion count sees.
  3. The header is the other half of server.js. A routes-only plan fixes 35% of the hunks and adds five lines to the block 14 commits already edit.
