What the drive did

  • Started a stage from a record the panel's own route wrote. The assignment was 4.339 s old when the entry was written; the job was 15.951 s behind it. Round 4's park came from a record a person had written by hand; this round's record was never touched outside the route.
  • Wrote the ledger before the worker existed. startingAt and the entry are written in the same pass that asks for the start (lib/task-pipeline-drive.js:1868-1906), so a restart between the ask and the link still names the attempt. The thread and job were filled in at the link, 27.5 s later.
  • Held the row live for the whole turn and settled it once. The row stayed running for 42m15.8 s, then the entry gained status, settledAt, commit, artifact and decision in one write.
  • Pinned the artifact instead of trusting it. The entry records the file's sha256, its git blob, the blob's sha256 and the commit; all four agree with the tree at 42656fa (see the evidence table).
  • Built stage 2's input from the handoff. The critic's prompt names the artifact, the commit, the blob, the writer and the edge H-01, and tells it to read the file at that commit. Nothing about the draft was left to the critic to infer.
  • Moved the row itself, twice. queued -> running at the start; running -> critique at the settle with visits.critique and crossings["H-01"] written in the same record; critique -> draft visit 2 on the loop edge.
  • Settled a cancelled run properly. The failed branch passed the run's status with the decision, so the entry reads cancelled and settledAt and the row is parked with the sentence that says why (:1599-1612). 1.585 s after the cancel was recorded.

1. A park written during a start is erased by the link

At 05:39:23 the reader parked #235; the row read parked with a manual hold and a sentence. At 05:41:11 the spawn that had already been asked linked its thread, and linkTaskRun wrote state: "running", reason: "" and hold: null - the park, its sentence and its hold are gone. The same thing happened again at 05:48:04, this time on a park the drive had written. The function has no branch for a row that is not queued: it is the tail of the start path, and it assumes the row is where the start left it.

2. The gate after the critique cannot be asked

The pipeline's picture draws a verdict after critique, and the critique produced one: nine notes, five blocking, "not accepted in this round". The driver never read it. gateAfter finds a gate only when the gate object carries decision, and the bundle's G1 has none, so the function returns null and the loop edge is taken. The critic's verdict is prose in the artifact; the record that would route it does not exist. The round's own artifact says the same thing in its closing line: the verdict is a sentence, not a decision.

3. The settle waits on the card, not on the run

The draft's settle lagged 2m17.9 s; the critique's lagged 12m52.3 s. The second number is almost all card: the gateway's run ended at 05:25:04.511, but the panel's job card read running until the panel restarted at 05:37:51 and reconciled it at 05:37:55. The drive's own tick is 10 s (server.js watchdog) and the sweep is cheap; the wait is the card's liveness, not the driver's clock. A panel that never restarted would leave the row live until its next reconcile.

4. The stage worker's push met no version gate

The drafter ran git push -u origin HEAD at 05:07:04 and gh pr create --fill twenty seconds later. The repo has a pre-push that refuses a bump-worthy branch at a stale version, and the drafter had already seen it refuse when run by hand ("branch 1.44.2, base origin/main 1.45.0"). It never ran on the push, because the worktree answers no core.hooksPath: the guard is installed per tree by the panel, and this tree was cut by hand. PR #504 is now MERGED (05:53:07Z) with one file and an empty body, and main reads 1.45.0 at that merge - no number was spent for a landing that carried two commits. A stage branch is also, by rule 5, meant to stay local.

5. The row's clock answers a different question than the round's

After the loop, pipelineRun.enteredAt reads 05:37:56.827Z - the moment the row entered draft visit 2. The round began at 04:24:23.419Z, which now survives only as the first entry's at. This is by design (enterStage restamps on every entry), but a reader who takes "time in stage" as "time in the round" is off by 1h13m. The entries are the only place the earlier clock still exists.

6. The park's sentence does not say who stopped it or why

The row's reason reads "ping-pong - draft ended cancelled with no final message - the pipeline waits for a decision rather than re-running the stage". That is exactly what the record knows: a run ended without a final message. The cancel's cause - the reader stopped the loop's second visit - is in the journal as a queue action, not on the row. A reader opening the row afterwards has the ending and not the reason.

7. One stage-run id, two entries, and a link that wrote onto the wrong one

ping-pong/draft#2 exists twice: the visit that was cancelled at 05:44:01.538Z, and the attempt made when assistant-2 requeued the row at 05:47:01.049Z. stageRunId is <pipeline>/<stage>#<visit> with no attempt, and settleStageRun matches by stage and visit alone, so the landing worker's link at 05:48:04 wrote its own thread ...7d7fd2 and job ce240516 onto the second entry - a draft visit no draft worker ran. A reader of the ledger sees one id, two outcomes, and a thread that belongs to neither run.

What this does not prove

  • It does not prove the loop converges. No gate record exists, so "not accepted" has no route; visit 2 is the default out of critique, not the critic's verdict. Whether the note improves in a second round is untested - the second drafter was cancelled 3m48.8 s in.
  • It does not prove a live card settles promptly. Stage 2 settled on a restart's reconcile, not on a tick. The 10 s tick and the 2m18s draft lag are consistent with the card being the delay, but one sample cannot separate the card's poll from the driver's pass.
  • It does not prove the artifacts were landable in the sense the repo means. They did land - PR #504 merged at b0a382f, and main carries both files with the same blobs the ledger pinned - but the landing spent no version number and main read 1.45.0 at that merge, and its body is empty. What the round proves is that the bytes reached main, not that a pipeline stage's output is a well-formed landing.
  • It does not prove the push gate's rules in general. Only that this tree had no hook at all. A tree the panel booted carries one.
  • It is one round, one machine, one panel, one restart. The numbers are a reading, not a benchmark.
