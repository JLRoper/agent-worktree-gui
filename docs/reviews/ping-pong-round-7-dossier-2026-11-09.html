How a queue task moves through a pipeline stage

A task with a pipelineRun is driven, not started by its card. driveTaskPipelines in lib/task-pipeline-drive.js passes over the rows in lib/assistant/queue.js and returns what it wants done; lib/assistant.js does the git and the spawn.

The tree cut. The cut happens only when unattended: unattended is settings.spawn === "auto" (lib/assistant.js), so on ask or off no tree is cut and the row waits. On auto the front queued row's stageTreeLookup gives three answers. needed returns an ensureTree request; cutPipelineTree writes pipelineRun.tree; lost, a recorded path now gone, parks pipeline-tree-gone and is never cut again; no tree and no project parks pipeline-no-target. A cut is not repeated: the next pass starts with existing: true.

The stage run. stagePrompt builds the prompt; beginStageRun in lib/task-pipeline.js creates the entry before anything runs (id <pipeline>/<stage>#<visit>, thread, job, status and decision null). The pass stamps startingAt on the run and calls settleStageRun with the commit, tree facts and input manifest, no status. On admission linkTaskRun in lib/assistant/queue.js writes thread, worktree and run id and flips the row to running in one write; linkSpawnTask fills the entry in the same write.

The settle. The driver's pass is the fallback, not the owner. The link stamps a hold in the tree's pipeline record (pipelineWait.kind: "run"); the run's end stamps it and fires the sweep at once (stampPipelineHold to onStageSettled to tickPipelineWaits), so the book reads the settle and advances. heldByBook skips a row held on the same stage and visit inside HOLD_OWNER_MS; past that, or with the hold gone, the driver takes it. It prefers the open entry's thread; a settled one, or one from before the link, falls back to the row's newest, possibly a retry's. A done run gets settleStageRun: status, settledAt, the artifact (presence, hash, commit pin), tree facts and a stage-settled decision; an absent declared artifact parks before the graph is read.

The loop edge and its cap. nextStageOf takes at most one edge, in kind order, loop last. enterStage increments visits[stage] and, when an edge is crossed, crossings[edge]. capOf reads the number opening the cap and treats a progress label like "2 of 3 rounds", or anything unreadable, as a CAP park. At used + 1 > limit the row parks on {kind: "cap"}, a manual hold; releaseCapPark zeroes the count, or a requeue re-parks.

The gate. gateAfter puts a decision between the stage and its edge. A missing record parks {kind: "gate"}, the one wait the driver re-reads first each pass. A present record at a routed gate has three answers: a route to an edge releases the row to queued and moves it in the same pass; a route to null ends the pipeline, finishing a non-PR stage on its own verdict and returning a pr stage to running for the landing rule; one the gate cannot route (not JSON, no outcome, missing handoff) parks pipeline-verdict and is re-read like a gate wait. A last stage with no edge out is closing: nextStageOf answers done before the gate, and the settle finishes the row. The seed's G1 is a barrier (its last stage's only edge is the loop), and its accept routes to null, ending the row.

The surprise. The loop keeps two counters that disagree: {{round}} in a gate path is the stage's visit; the cap counts crossings. A cap of "3 rounds" allows three crossings and four drafts, so the gate on the fourth critique asks for verdict-r4.json, and a revise there is the crossing that parks.

Unsure: the hold and sweep race is untested from the modules.
